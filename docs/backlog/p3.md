# Backlog detail: P3 — hardware variants and later stages

Detail kept out of [`docs/BACKLOG.md`](../BACKLOG.md), which holds a short line per item linking here. Each item's text is as it stood in the backlog when it was split out (2026-10-16); add new findings here, under the item's id, and keep the backlog line short.

### p3-001

* **The YT6801's first run on the N150 box** (`docs/roadmap/networking.md`,
  the YT6801 section's checklist, 2026-10-15, `net-yt6801`): the driver and
  the core logic are proven on host models only, and the kernel's held-off
  MSI-X path on QEMU's `e1000e`, not on the chip (the consultant's D7, ledger
  line 1097). The run must show the devices line with `1F0A:6801`, MSI-X
  Enable 0 and an aperture over BAR 0's `0x1000`-`0x1FFF`; one MSI vector
  whose deliveries count under traffic; and the MSI capability and MSI-X
  control read with `device_config_read` before and after the chip's
  `SYS_RESET`. A re-mint after a reset that cleared the MSI capability needs
  a design review of its own. Needs the PO's hardware approval and the box.

### p3-002

* **xHCI's first run on a PC** (`docs/XHCI.md` §9, 2026-10-10,
  `xhci-driver`): the driver is gated against QEMU's `qemu-xhci` and a model
  only, and §8 lists what neither showed -- the hand-over from firmware,
  scratchpad pages, 64-byte contexts, a BAR cut around its MSI-X table,
  real reset and link-training times, transaction translators, a low-speed
  device. `test-usb` shows two input claims held on the xHCI node at once,
  not the eight `L.device.21` allows (the consultant's X9 and Y7). And on
  QEMU's AArch64 `virt` under EDK2 the function is left with memory decoding
  off, gets no aperture, and the driver exits, so no AArch64 boot shows the
  driver at all (the row below). After INSTALLER.md's H0, on the customer's PC, by
  the product owner's decision and §9's list. Owner: the product owner.

### p3-003

### p3-004

* **A PCI function firmware left with memory decoding off gets no
  aperture** (`device.rs`, deliberately: nothing says firmware placed its
  BAR): QEMU's AArch64 `virt` under EDK2 leaves `qemu-xhci` that way, so
  `usbhid` exits `stopped at Registers` there and `test-usb` is x86-64
  only (log `~/.local/share/ferrix/logs/xhci-driver/usb-7-a64-serial.log`,
  branch `xhci-driver`). If the PC's firmware does the same to a controller, the
  kernel needs a rule for turning decoding on for a BAR it can vouch for
  (inside the host bridge's window, clear of everything `Reserved` names);
  that is a change to the item. Open.

### p3-005

* The `FS`/`GS` skip's `GS` base control on a processor that keeps the base
  over a null load (`docs/OPAQUE-KERNEL.md` §9.8 3c; po10-sel-cert, ledger
  line 445, K2): an AMD part without `NullSelectorClearsBase` (CPUID
  `0x8000_0021` `EAX[6]` clear, Zen 2 and older), on hardware or under KVM
  there. On nazuna's Ryzen 9 9900X and under TCG a null load clears the
  base, so the control (the `GS` base write skipped with the load) cannot
  fire; the `fsgs` line prints the vendor and the bit. Owner: whoever next
  has such a machine.

### p3-006

* The `FS`/`GS` skip's bring-up control `k1-bringup` (A5's null load of `FS`
  and `GS` in `set_cpu_local` removed; §9.8 3c; po10-sel-cert, ledger lines
  445 K1 and 498 L2) did not fire on nazuna under KVM: the compatibility-mode

  null selector there whatever the hidden part, or because earlier stages

  unusable bit, and `INIT` leaves `FS`/`GS` usable), hardware, or this host

### p3-007

* The DK1 run `cacheflush` owes (po10-chrome-a, 2026-10-07; the
  certification consultant's D1.5): QEMU keeps translated code coherent by
  itself, so only the board shows whether `cacheflush` (`0x0f0002`) makes
  code written into a page mapped executable run. `jitflush` (source and a
  static armhf build in `~/.local/share/ferrix/logs/po10-chrome-a/` on
  nazuna) writes and calls `mov r0,#k; bx lr` 200,000 times: `jitflush
  flush` must find no wrong answer; `jitflush noflush` is expected to find
  some on a Cortex-A7, and if it finds none the run does not discriminate
  and is recorded so. Needs a board image with the program in it; scheduled
  by the product owner.

### p3-014

* **NVMe, what the driver leaves (nvme-driver, 2026-10-10; `docs/NVME.md`).**
  (1) *The first run on a real drive*, by §9's checklist, on the WD PC
  SN720 once the PC boots Ferrix at all (H0): nothing in the driver has met
  hardware, and §8 lists what QEMU cannot show. (2) *The shutdown
  notification is unreachable*: the driver writes `CC.SHN` on STOP, and no
  kernel code sends STOP (stage 10's *Still to do*), so a real drive is
  powered off flushed but unnotified and counts an unsafe shutdown each
  time. (3) *Names*: an NVMe disk is `/dev/vdX`; `/dev/nvme0n1` as
  `docs/INSTALLER.md` §5.2 has it needs the block ring's name check and
  major to take it. (4) *The Host Memory Buffer, timeouts and Abort* are
  shown against the driver's own model only; QEMU's controller asks for no
  host memory and cannot be made to lose a command. (5) *One I/O queue
  pair*, until a serve loop runs on more than one processor. (6) *AArch64
  in the shell gate*, once uutils is built for it; `test-nvme --boot up`
  boots the driver there today. (7) *An interrupt 100 ms late, once*: at a
  host load of 50 a restarted driver's watch took completions before any
  interrupt came (`~/.local/share/ferrix/nvme-driver/logs/late-interrupt-load50.log`,
  at 55.08). Taken for the virtual processor the vector is routed to
  standing still on a starved host, which is not proved; the gate says it
  and does not judge it. Worth one look on an idle host with the vector's
  processor pinned.

### p3-015

* **A function below a PCIe root port has its DMA faulted by the SMMUv3
  (nvme-driver, 2026-10-10).** `cargo xtask test-nvme --boot up --arch
  aarch64` with `FERRIX_NVME_BELOW_PORT=1` puts QEMU's `nvme` on a
  `pcie-root-port` of the `virt` machine: the kernel says `pci 0000:01:00.0
  behind the SmmuV3 unit at 0x9050000 as stream 0x100`, the driver's first
  admin command is never read (`nvme 0000:01:00.0 did not come up: Fatal`,
  QEMU's controller setting `CSTS.CFS` when its read of the queue faults),
  and the boot ends `FX-1007`, `16 DMA faults no check provoked`. On the
  root bus the same drive works, and on x86-64 the same drive works three
  bridges down behind VT-d, so it is the SMMUv3's handling of a stream
  above 0xFF or of a bridge, not the driver. Nothing else on that machine
  sits below a bridge, which is why no gate saw it. Log:
  `~/.local/share/ferrix/nvme-driver/logs/aarch64-smmu-bridge-fault.serial.log`
  (branch `nvme-driver`). The certified item's IOMMU code is the place to
  look, so the fix goes through the consultant.

### p3-016

* **N4a: interrupts instead of polling on the N150 are the drivers'
  (vtd-n150, 2026-10-17).** Branch `vtd-n150`'s design (§0,
  `~/.local/share/ferrix/n150-linux/vtd-design.md`) found that remapping
  does not gate MSI minting: with no unit remapping, `msi_allocate`
  mints a compatibility-format message (`arch/x86_64/msi.rs`), and the
  "0 vectors minted" of stage 10's line is printed before any driver binds.
  The YT6801's one MSI is delivered on the box -- once at bring-up and about
  209 times in five minutes -- so delivery works and the chip raises it
  rarely. It is in `ferrix_pci::msix::MSI_PREFERRED` (MSI-X held off),
  while Linux runs it on six MSI-X vectors (rx-0, tx-0, mac); which events
  the glue raises a single MSI for is in `ref/fxgmac`. xHCI (8086:54ed, MSI
  under Linux) raises none under Ferrix: the interrupter's enables are the
  next look. Interrupt remapping gives a diagnostic: a refused message is
  recorded with its source ID and reason.

### p3-017

* **VT-d slice 2: honour RMRRs (vtd-n150, 2026-10-17).** Slice 1 brings a
  unit an RMRR holds up for interrupt remapping only (`L.iommu.67`), so on
  the N150 the iGPU's DMA is unconfined (VULNERABILITY-ANALYSIS V-03).
  Slice 2: before TE, attach a kernel-held domain for each RMRR function
  and identity-map base..=limit read/write; refuse (keep slice 1) an RMRR
  overlapping usable RAM; never detach it, and refuse a driver domain for
  such a function until a GPU driver exists. Needs its own design OK from
  the consultant.
