`blk` (pids 3 to 8) and `ahci` each made 200 voluntary switches a
second. While one program spun, it was switched away from 160 to 660 times
a second, against 2 on Linux in the same guest shape. Wake placement onto
idle processors (design `~/.local/share/ferrix/ef-sys/wake-steal-design.md`
on the gate host) removes the cost where a processor is idle; on a machine
that is all busy, only fewer wakes do.

None of the drivers asked for those wakes: devmgr waits on its port with no
deadline and the block loop sleeps for good while the device is idle. The
kernel's `port_wait` used `wait_until_deadline`, whose 5 ms recheck woke
every port waiter 200 times a second. On branch `driver-polls` (2026-10-22;
consultant ledger 3056) `port_wait` trusts its wakes as `channel_write_read`
does (`WaitQueue::wait_trusting_until`, L.object.247). The same scan after:
no driver above its 2.5/s floor (1,600/s before), one spinner's involuntary
switches 185/s to 81/s, four spinners' 680/s to 406/s each. yt6801's look
without interrupts (the N150 box) backs off from 1 ms to 8 ms while it
moves no frame, and usbhid's service without interrupts from 8 ms to 32 ms
while it finds nothing, each back to the fast poll at once on any traffic
(`next_poll_nanos`, `next_service_poll`, host-tested); neither has run on
the box yet. Left: usbdev's 2 ms ADB tick (Pixel 7) and the virtio-console
vport's 10 ms tick (desktop guests), not seen in the idle scan.

### p2-139

**No `/proc/<pid>/environ`.** On 2026-10-21 the N150 box's launcher froze
under DXVK on anv, and whether `DXVK_CONFIG` had reached `Games.exe`, which
the launcher starts, could not be read from outside the process: Ferrix has
no `/proc/<pid>/environ` (also listed among p2-124's gaps). DXVK's log at
`DXVK_LOG_LEVEL=info` ("Found config env") answered it that time. Linux
serves the environment block the process started with, as the bytes
between `mm->env_start` and `env_end`, readable under the same
`PTRACE_MODE_READ` check as `/proc/<pid>/mem`.

### p2-140

**No call view on the Arm architectures.** `sched::inspect` reads a blocked
thread's call from the entry frame at a fixed place below its kernel stack's
top, which x86-64's `SYSCALL` entry gives (`gs:8`) and its `RSP0` gives a
trap. On AArch64 the vector pushes its frame on `SP_EL1` as the task's last
`eret` left it, and `ferrix_enter_user` and `ferrix_resume_user` leave it
where their caller's stack stood; ARMv7-A's SVC stack pointer is the same.
test-procfs's debug step read `syscall_2735960` and `restart_syscall` there
on 2026-10-21 before the view was turned off on Arm. The fix is in the cold
user-entry paths, not the hot ones: enter and resume user mode from the
stack's top (resume by copying the frame to `top - frame size` first), so
every later exception's frame is at that fixed place; then
`arch::{aarch64,armv7a}::inspect::entry_frame` returns its frame, and the
debug step's x86-64 branch runs there too. A core change: its own design
review.

### p2-141

**Coverage owed for the call view.** The x86-64 call view of
`docs/DEBUG.md` §1 is reached only by `test-procfs`'s debug step, a blocked
user thread read from outside, which no boot check can make. Until a
coverage measurement runs that gate, `call_of`, `read_call`, `field`,
`calls_are_visible` and x86-64's `entry_frame` are measured as not reached
on x86_64 (the consultant's code review, ledger 2909, R3).

### p2-142

**The open-then-render window in `/proc`.** `may_open` asks
`credentials::may_access` when an entry is opened, and the render follows.
A process that runs a set-id program in between, and so becomes one the
reader may not look at, is rendered as that program: its `environ` and the
call its thread waits in, as its `maps` and `fd` already were. Linux closes
it with the target's `exec_update_lock`, held from the check through the
read; the equivalent here is a lock exec's credential change takes and
`/proc`'s private renders hold (ledger 2909, R4). Named, not fixed.

### p2-143

**`fs::read_file` documents 64 MiB and reads 4 MiB.** `READ_FILE_LIMIT`
says 64 MiB, but `read_file` copies the file into a heap `Vec`, and the
kernel heap refuses a single allocation past its largest buddy block
(4 MiB, `src/lib/kernel/heap`, `MAX_ORDER` 10). So its callers other than
devmgr's reader -- `edid`, `btrfs_check`, `driver_check` -- fail with
`ENOMEM` on a file larger than that. initrd-limit moved only
`read_from_root` (devmgr's program and drivers) to the `vmap::Buffer` that
`read_location` already returns; the consultant's OK IF (ledger 3034,
condition 5) asks that `read_file` either do the same or stop claiming in
its doc comment what it does not do. A change to the item's `fs/mod.rs`:
its own review.

### p2-144

**A devmgr that cannot start under `ferrix.devmgr=init` is retried
forever, silently.** On the N150 box on 2026-10-22 the Intel GPU driver
grew past 4 MiB and `devmgr_start` failed with `NoMemory` (fixed by
initrd-limit). In desktop mode (`ferrix.devmgr=init`) pid 1 logged
`devmgr.service: devmgr_start: NoMemory`, restarted `devmgr.service`
forever, and `/` waited for its disk with nothing on the headless box
saying why; the FX-1006 panic happens only with `ferrix.devmgr=kernel`.
Owed: give up after N tries and say so on the console and in pstore. And
`ferrix.panic=reset`'s reset path (`src/kernel/src/arch/x86_64/mod.rs:1688`)
has never been exercised on the N150 or any real x86 machine.

### p2-145

**`process_create`'s image copy is charged to no job.** `image_bytes`
(`src/kernel/src/syscall/native.rs`) copies the image VMO into a
`vmap::Buffer` before `load_native` loads it. Neither the old heap copy nor
these frames are charged to a job, and with the heap's 4 MiB block no longer
the cap, what one in-flight `process_create` can hold rose from at most
4 MiB to at most `MAX_IMAGE_BYTES` (16 MiB), for as long as the load takes.
The consultant's OK IF (ledger 3045, condition 6) asks for this row: charge
the buffer to the caller's job (`object::quota`), or load from the VMO's
pages directly so there is no copy to charge. A change to the item's
`syscall/native.rs`: its own review.

### p2-147

**Wake placement costs about a fifth of the round trip at four
processors.** Measured on 6a919687e against main 1341888e0 on a quiet host
(load 2.27 to 1.64), x86_64 under KVM, `--pin 8-11`, `ferrix.checks=skip`,
five alternating rounds: domain-call p50 1,628 against 1,298 ns (1.245,
spread 1.237 to 1.262), call p50 6,472 against 5,383 ns (about 1.20).
Earlier runs under load 11 to 48 read 1.023 and hid it. One processor shows
no cycle difference, so the cost is the placement itself: a channel's server
woken onto a busy client processor is queued elsewhere, so each trip crosses
processors. What would recover it: do not place a task woken by a channel
call whose caller is about to block (a synchronous wake, as Linux's
`WF_SYNC`), or keep a channel peer on the waker's processor. Measure with
the same command; the target is within noise of main.
