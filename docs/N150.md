# The N150 box: Endfield's anti-cheat on bare metal

Version 1, written 2026-10-15 by the session `n150-endfield`. The
customer's word of 2026-10-14: the SOYO M4 Pro with an Intel N150, 16 GB of
memory and a 512 GB NVMe drive is a weekday bare-metal box, and its first
job is a proof of concept for *Arknights: Endfield*'s anti-cheat (Anti-Cheat
Expert, ACE) with software rendering. The Intel GPU driver is deferred; the
wired NIC, a Motorcomm YT6801, has a driver in progress (branch
`net-yt6801`).

Why bare metal: on 2026-10-13 ACE refused the game in the Linux guest
`linux-3060` (Debian 13 under KVM, the RTX 3060 passed through) with "The
application can not run under a virtual machine. Please do not run game in
virtual environment or system made from virtual environment image.
(13-65544-2)" ([stage 23](roadmap/stage-23-arknights-endfield.md), step 0).
That was a Linux guest, not Ferrix; Ferrix has never shown ACE anything.
Stage 23 decided then that its steps 4 to 6 wait for Ferrix on a machine
rather than in one, and this box is that machine.

This document is the plan for running the launcher and the game on the box,
and the tooling built for it now, with no hardware attached, and proven
under QEMU: `cargo xtask n150-install` and `cargo xtask test-n150` (§9).

**No certification claim.** The configuration here -- an NVMe boot disk,
`/data` on the root volume, the firmware's framebuffer as the display, an
Intel N150 -- is outside the reference configuration of
`docs/certification/ITEM.md` §5. Nothing in this document claims evidence
for the certified item, and nothing here changes it (the consultant's
review, ledger line 1285).

## 2. The road, in four layers

```
the game (Endfield.exe, ACE)          Windows programs, unchanged
GRYPHLINK launcher (Qt WebEngine)
GE-Proton 11-7's Wine                 /data/proton, a glibc program
yserver (X11)                         /data/yserver
hyprix on the firmware framebuffer    H6, `ferrix.efifb`
Ferrix                                kernel, devmgr, nvme, yt6801 (later)
N150 box                              NVMe root, GOP, 16 GB
```

Everything above Ferrix is what `cargo xtask test-endfield-proton` already
runs under KVM: the launcher draws its window on hyprix through yserver, in
software, and Gryphline's server answers it (`docs/WINE.md` §10). The box
changes the bottom two layers: a real processor, firmware and disk instead
of QEMU's, and the firmware's framebuffer instead of a virtio-gpu.

## 3. How Ferrix and the volumes get onto the NVMe

Three ways were weighed.

| Way | What it needs | Verdict |
|---|---|---|
| **The installer** (`ferrix-install --slots`, `docs/INSTALLER.md`) run on the box from a live medium | the medium on a USB stick, which Ferrix reads only through H4 (USB mass storage served to the block core, not built: `docs/XHCI.md` §6); and the 5 to 15 GB program volume, which no live medium carries | Later. It is the product's way; it is not tonight's |
| **Volumes served by `netboot`** | iPXE fetches files into memory through the firmware's network driver; nothing reaches a running Ferrix through it, and Ferrix has no network on the box until the YT6801 driver lands (`docs/NETBOOT.md` §6). A 5 GB volume fetched into a 16 GB machine's memory is a third of it gone | No, for volumes. Yes for the system: see below |
| **A disk image written on nazuna**, carried to the drive | a host tool that writes the disk -- partition table, EFI system partition, and a btrfs volume holding the programs at `/data` -- and one transfer to the drive | **Chosen now**: `cargo xtask n150-install` (§9) |

**The image.** `n150-install` writes a regular file the size of the box's
drive (512,110,190,592 bytes by default, the size every "512 GB" drive has;
`--disk-bytes` gives the real one):

| Partition | Size | Holds |
|---|---|---|
| 1, `ferrix-esp`, EFI system | 512 MiB, from 1 MiB | the image `build` makes, or `--image`: the loader as `EFI/BOOT/BOOTX64.EFI` (the firmware's fallback path, so no boot entry is needed; I9 is not built), `FERRIX/KERNEL.ELF`, `INITRD.IMG`, and `CMDLINE.TXT` when `--kernel-option` gives one |
| 2, `ferrix-root`, Linux file system | the rest, about 476 GiB | a btrfs volume labelled `ferrix-root`, made by btrfs-progs at the partition's whole size, with the program tree at `/data` |

The volume is made on the host by `mkfs.btrfs -L ferrix-root -O
no-holes,free-space-tree -d single -m dup --rootdir <staging>` (btrfs-progs
6.17.1 on nazuna; the log of every run names its version), where the
staging directory's `data` is the program tree in hard links, which cost no
space. The tool checks that the superblock's `total_bytes` is the
partition's and runs `btrfs check` over the volume before laying the disk
out. The tree is by default the Proton launcher volume's
(`~/.local/share/ferrix/endfield-launcher-proton/tree`: GE-Proton 11-7,
GRYPHLINK, yserver, Debian's i386 libraries, the certificate bundle; about
5 GB), or `--tree` names another -- the `--everything` volume's tree, for
the whole desktop (about 15 GB).

**What the box does with it.** The kernel finds its root by the label
`ferrix-root` on any disk or partition (`src/kernel/src/fs/root_disk.rs`),
so the NVMe driver (`docs/NVME.md`) serves the drive, the partition scan
publishes its two partitions, and `/` goes on the second. At the first boot
the kernel installs the system from the initramfs onto the volume, as on
every disk, and stamps it; a later boot with another initramfs installs
again and leaves everything else, so `/data` and what the launcher writes
stay. The root is committed every 30 seconds, at every `sync`, and at the
kernel's own power-off.

**Netboot afterwards.** Once the drive holds `ferrix-root`, a netbooted
kernel (`docs/NETBOOT.md`) finds it too and puts `/` on it: the system
comes from nazuna at every boot, the data stays on the drive. That is the
day-to-day loop once the image is on the box -- no image is rewritten for a
new kernel. It also ends NETBOOT.md's "nothing on the machine's disk is
touched" for this box: a netbooted run installs its initramfs on the root.
`--kernel-option ferrix.root=tmpfs` on `netboot` keeps a run off the drive.

### 3.1 `/data` is a directory of the root

The programs expect their volume at `/data` (`test-endfield-proton`'s
links, `gryphlink` on the `--everything` desktop). On a virtual machine
`/data` is a second whole disk the kernel mounts (`fs/data_disk.rs`); it
looks at whole virtio disks `vdd` to `vdh` only, never a partition, and the
box has one disk. Rather than change the kernel, the image puts the tree in
a directory `/data` of the root volume. So:

* `/data` shares the root volume's space and its 30-second commit. A full
  `/data` -- the game's download filling the drive -- is a full `/`, and
  the failure is `ENOSPC` on the root, for every program, not on `/data`
  alone.
* If a whole disk carrying btrfs is attached as well (a USB disk once H4
  serves one, a second drive), `fs/data_disk.rs` mounts it over the
  directory at `/data` as on a VM, and the tree underneath is hidden while
  it is mounted. `fs/data_disk.rs` is not changed.
* A data volume on a labelled partition of its own -- a later slice, if a
  root that can be started over without the game is wanted -- is a kernel
  change in `fs/` and needs its own design review first.

## 4. Onto the drive: the transfer

`n150-install` writes a file and never opens a device: it refuses any path
under `/dev` and anything that exists and is not a regular file. Writing the
drive is the customer's step, and it **erases the box's whole disk**,
including whatever system it came with (the M4 Pro is sold with Windows 11;
whether that is kept is a question for the customer, in the morning
questions of 2026-10-15). The drive is picked by its model and serial
number, never by a name such as `nvme0n1`, which can change between boots.

The image is sparse -- 512 GB long, a few GB of data -- and must not cross
the network as 512 GB of zeros. GNU tar's sparse mode carries only the
data (checked on nazuna: a 64 MiB sparse file became a 10 KB stream and came
back byte for byte), so, from a Linux live stick on the box (Ubuntu's, for
instance), with the box on the same network as nazuna:

```
box$ lsblk -o NAME,MODEL,SERIAL,SIZE           # find the drive; note its id
box$ sudo blockdev --getsize64 /dev/disk/by-id/nvme-<model>_<serial>
nazuna$ cargo xtask n150-install --disk-bytes <that number>
box$ ssh <you>@<nazuna> 'tar -cSf - -C <checkout>/build/x86_64 n150-disk.img' \
       | tar -xSOf - \
       | sudo dd of=/dev/disk/by-id/nvme-<model>_<serial> bs=4M oflag=direct status=progress
```

`tar -xO` writes the zeros of the holes too, so the whole drive is written
once at the drive's own speed (a few minutes); only the data crosses the
network. A drive bigger than `--disk-bytes` boots too -- the kernel reads the
primary table only -- but its backup table is then not at its end, which a
Linux `gdisk` would offer to repair; giving the real size avoids it. An
NVMe enclosure on nazuna, with the drive out of the box, is the other way,
the same `dd` locally. Both are the customer's.

## 5. The writable btrfs for the game

The game wants about 60 GB installed and about 45 GB more while it unpacks
(Steam's page; stage 23), and the launcher's download was 111.18 GB
announced on 2026-10-14 (`docs/WINE.md` §10). The root's ~476 GiB holds it
with room, beside the 5 to 15 GB of programs.

What the download found on a VM and where it stands:

* **Memory, not disk, ran out** (2026-10-14): a writable btrfs mount's page
  cache was never reclaimed, so an 8 GiB guest answered `ENOSPC` after
  about 5.8 GB. The reclaim of a writable mount's clean pages, a truthful
  `/proc/meminfo`, and writebacks in slices landed on `main` as f0bc9ab2d
  (2026-10-15). The box's root is such a mount, so this was a precondition
  and is met.
* **The network driver's restart** stalled a later download
  (`net-restart-stall`, in progress). On the box the driver is the YT6801's,
  not virtio-net, but it restarts through the same `devmgr` path.
* **A restarted launcher started over**: its Wine prefix was on tmpfs. On
  the box the prefix goes under `/data` (or the home) on the drive, as the
  scratch branch `ef-night` tried with `FERRIX_ENDFIELD_KEEP`; that the
  launcher then resumes is unproven.
* **The download needs the network on the box**, so the YT6801 driver
  first. Without it, the other way is the game's files downloaded on
  nazuna's VM (the 160 GB image on the SN720) and put into the tree before
  `n150-install` -- possible, but it needs the files read out of that btrfs
  image on the host (a mount, which is the customer's to do), and the game
  then updates itself over the network anyway.

## 6. Memory at 16 GB

Endfield asks for 16 GB on Windows (Steam's page). On the box the same
16 GB also holds the kernel, the desktop, Wine, the launcher's web engine,
lavapipe's buffers and the page cache, with no swap. None of it has been
measured together; these are the places it goes, and the measurements the
first boot owes:

| Consumer | Known | To measure on the box |
|---|---|---|
| Kernel, drivers, `devmgr`, init | small beside the rest (the test boots run in 512 MiB) | `/proc/meminfo` at the desktop |
| hyprix, yserver, the firmware framebuffer's copy | a 1920x1080 32-bit frame is 8 MiB; hyprix keeps a few | at the desktop |
| Wine, wineserver, the launcher (Qt WebEngine, Chromium 87) | the download VM ran it in 8 to 24 GiB with the cache unreclaimed; never measured alone | with the launcher idle |
| The game | Windows: 16 GB required | at its first screen, and at ACE's check |
| lavapipe | the game's textures and render targets live in system memory, since there is no GPU | with the game drawing |
| Page cache | reclaimable since f0bc9ab2d | `Cached` and the reclaim counters |

The risk is plain: the game alone may want all 16 GB, and there is no
swap. For the proof of concept that matters less than it seems -- ACE's
verdict comes at the game's start (§8), before a world is loaded -- but an
out-of-memory end before that point would hide the answer. The record keeps
`/proc/meminfo` every few seconds through the run, so a stop says which.

## 7. Software rendering

The display is the firmware's: H6 (`docs/INSTALLER.md` §6, design in
`docs/DISPLAY.md` §8; `test-compositor --boot firmware-screen`) lends the GOP
framebuffer the loader hands over to a ring-3 driver under the kernel
option `ferrix.efifb`, and hyprix draws into it at the mode the firmware
chose, with no mode setting and no GPU. The window is mapped uncached for
now, so each frame copied to it costs more than the rest of the stack needs;
write-combining is H6's follow-up. Above it, as on every VM desktop:
yserver for X11, Wine's X11 driver, and the game's Direct3D 11 through DXVK
on Mesa's lavapipe, which satisfies DXVK at feature level 11.1
(`docs/WINE.md` §6, `cargo xtask test-dxvk`).

What to expect of speed: Unity's *Spaceship Demo* drew about 1.3 frames a
second at 1024 by 768 on 8 KVM processors of nazuna (`test-unity`). The
N150 has 4 smaller cores; Endfield is heavier. Well under one frame a
second is the honest expectation. That is enough for this job, whose
question is ACE's answer at the start, not play; playable frames need the
Intel GPU driver, which is deferred, and are not this plan's goal.

## 8. The anti-cheat: what is known, and what the proof of concept does

**Nothing in this plan is built to evade, hide or disguise anything from
the anti-cheat.** No masking of the processor's hypervisor bit (on bare
metal there is no hypervisor to mask), no `Linux` from `uname` (it says
`Ferrix`, the customer's choice of 2026-09-13; stage 23's E5.4), no altered
firmware strings, no patched or reverse-engineered anti-cheat code, no
instructions to get past it. The goal is that a real bare-metal Ferrix is
seen as what it is, and the proof of concept records what ACE does on it.
It claims no compatibility before a run shows one.

What is public, with its source:

* ACE is Tencent's Anti-Cheat Expert; on Windows it is a kernel-level
  driver, and the game's Steam page says it needs manual removal after the
  game is uninstalled ([Wikipedia](https://en.wikipedia.org/wiki/Anti-Cheat_Expert),
  [Steam app 4732690](https://store.steampowered.com/app/4732690/Arknights_Endfield/)).
* On Linux the game has been played under patched Proton builds, with ACE
  running inside Wine in user space
  ([AreWeAntiCheatYet #1905](https://github.com/AreWeAntiCheatYet/AreWeAntiCheatYet/issues/1905),
  [Dawn PR 516](https://codeberg.org/Krock/dawn/pulls/516)), and that has
  broken and been fixed more than once in 2026
  ([proton-ge-custom #433](https://github.com/GloriousEggroll/proton-ge-custom/issues/433),
  [GamingOnLinux, 2026-02](https://www.gamingonlinux.com/2026/02/ge-proton-10-31-brings-fixes-for-arknights-endfield-duet-night-abyss-and-more/)).
  For other ACE games on Linux, reports are mixed and anecdotal
  ([GamingOnLinux, 2025-04](https://www.gamingonlinux.com/2025/04/wuthering-waves-arrives-on-steam-another-with-anti-cheat-problems-on-steam-deck-and-desktop-linux/page=1/)).
* ACE refuses a virtual machine for this game: seen on `linux-3060` on
  2026-10-13, message 13-65544-2 (above).
* What ACE checks to decide that a system is a virtual machine is not
  published. A search on 2026-10-15 found no public description of it or of
  the error code. This document does not guess at it.

What a Windows program under Wine is shown of the machine is public in
Wine's own source, and it is where a truthful bare-metal Ferrix differs from
the VM: the processor answers its `CPUID` instruction itself, with no
kernel in between, so on the box it is the N150's; and Wine builds Windows'
view of the firmware (the SMBIOS table and the `HARDWARE\DESCRIPTION\System\BIOS`
keys) from Linux's `/sys/class/dmi/id/`, which Ferrix does not have today.
So Windows code on Ferrix sees empty firmware strings where Linux on the
same box would show the box maker's. Whether ACE looks at them is not
known. Showing the real ones is answering truthfully what Linux answers,
not a disguise; it is a later slice (D1 below), and it is not built.

**D1, the firmware's SMBIOS tables to programs (not built; design review
first).** The sysfs files are in the load ring, but the tables reach the
kernel only through two changes in the item: the UEFI loader
(`src/boot/common/uefi`, in the reference configuration) must hand over
the SMBIOS 3 entry point, where today it passes only the ACPI RSDP; and the
kernel must map the firmware's memory holding the tables, which is core
code. That is a new interface into the item, so it waits for a design
review with the certification consultant before any code, and holds these
constraints (the consultant's, ledger line 1285): read-only, copied once at
boot, bounded by the entry point's table length under a stated cap; fail
closed -- no table or a bad checksum means the files are absent, never
empty strings or invented values; the values passed through unaltered;
Linux's file modes, with `product_serial`, `product_uuid`, `board_serial`
and `chassis_serial` readable by root alone (0400); what AArch64 and
ARMv7-A do named; requirement ids reserved at that review; and an entry in
`docs/certification/VULNERABILITY-ANALYSIS.md` for the serial numbers it
exposes.

**What the run records**, each kept with the commit that ran:

1. The launcher's own logs and the download SDK's (`HGDownloadLog.log`),
   as on the VM.
2. Every window ACE opens, and its text: photographed from the screen
   (the box has no serial port), and taken from yserver's screen where the
   desktop's screenshot works.
3. Ferrix's report of the system calls it did not answer
   (`syscall::report_unanswered`), and Wine's own `WINEDEBUG` channels for
   the anti-cheat's process, at the default level -- nothing that changes
   what the program sees.
4. `/proc/meminfo` through the run (§6).
5. The result in words, in stage 23's step 5: accepted, refused (with the
   message and its code), or stopped by something else (a crash, a missing
   call, memory), and on which day and launcher version.

**The account and the terms.** The game requires a Gryphline account and a
third-party EULA (stage 23, "What can stop this", items 3 and 4). Which
account is used, whether the terms permit running the game under Wine on
another operating system, and the risk of that account being flagged are
the customer's, and stated before the first run.

## 9. The tooling built now

| Command | What |
|---|---|
| `cargo xtask n150-install [--image FAT] [--tree DIR] [--disk IMG] [--disk-bytes N] [--kernel-option W]...` | §3's image, at `build/x86_64/n150-disk.img` unless `--disk` says. Prints the transfer of §4 |
| `cargo xtask test-n150 [--accel kvm\|tcg]` | the box under QEMU, below |

Both write their disk through one function (`n150::make_disk`): the same
partition table, the same `mkfs.btrfs` invocation and features, the same
checks.

**`test-n150`** builds a system whose first program is a shell script, and
writes its image into a 4 GiB disk with a fixture tree (`/data/n150/marker`)
in place of the launcher's. Then, under OVMF, the disk is the machine's
one boot disk: an NVMe drive on a PCIe root port, first in the firmware's
boot order, no AHCI disk, and q35's standard VGA as the only display, so
the loader and the kernel see a GOP framebuffer and no virtio-gpu, as on
the box. It requires:

1. the NVMe driver bringing the drive up, `/` on its partition 2 with the
   system installed on it, the marker read from `/data`, nothing kept yet,
   and a file written to `/data` and synced;
2. after a power cycle (a new QEMU), `/` on the same partition as the last
   boot left it, and the file the first boot wrote;
3. `btrfs check --readonly --check-data-csum` of the root partition after
   both boots.

Its negative controls, each run through the gate pool's `control`:

| Control | Change | Must fail with |
|---|---|---|
| (a) the label | the root made with another label | `/ is not on its root partition` |
| (b) the marker | the fixture's marker written elsewhere | `the tree's marker was not read from /data` |
| (c) a fresh disk | the disk written again before the second boot | `the second boot did not find the root the first left` |

What it does not show: a real N150's firmware, ACPI and interrupts (H0);
the firmware framebuffer driven by hyprix (H6's own gate, `test-compositor
--boot firmware-screen`, on its branch; once H6 lands, `n150-install
--kernel-option ferrix.efifb` writes a disk whose desktop uses it); the
YT6801; and the launcher, which `test-endfield-proton` already covers on a
VM.

## 10. Risks

1. **ACE refuses Ferrix too**, as something it does not recognise, or for
   a reason the PoC cannot see. That is a result, recorded as such; the
   customer decides what follows. Stage 23's "What can stop this" holds
   whole: ACE under Wine is a community arrangement that one update can end.
2. **Bring-up (H0).** Ferrix has never booted on an x86 PC. ACPI as a real
   firmware writes it, interrupt routing, the timer, the NVMe drive's own
   quirks (`docs/NVME.md` §8) will each cost something no estimate shows.
   The netboot stick's screen and PCI report are the first look.
3. **No network on the box** until the YT6801 driver lands and works on
   the real chip: no download, no login. The launcher needs Gryphline's
   server before the game starts at all.
4. **Memory** (§6): no swap, 16 GB for everything.
5. **Speed** (§7): software rendering on four small cores may be too slow
   for the launcher's web engine to be usable, never mind the game, or slow
   enough that a timeout in the game or ACE fires first.
6. **Erasing the box's disk** (§4): the customer's decision and step.
7. **A full root** (§3.1): the game fills `/`, not a separate `/data`.
8. **The account** (§8).
