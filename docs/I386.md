# The 32-bit x86 ABI: i386 programs on the x86-64 kernel

Version 1, written on 2026-09-26 when the customer asked for the next step
towards Steam to start. `docs/ROADMAP.md` stage 22 lists what Steam needs
"in the order it can be tested", and the first item is this: the Steam
client is an `i386` program, and so is every 32-bit Wine that Proton runs a
32-bit Windows game in. Sound (`docs/AUDIO.md`) is already under way, and
XWayland is counted in stage 19's remainder, so this is the part of stage 22
that nobody had started.

## 1. What this is, and what it is not

Linux calls it IA32 emulation (`CONFIG_IA32_EMULATION`): a 64-bit kernel
runs 32-bit x86 programs unchanged, in the processor's compatibility mode,
through the `i386` system call table, with every structure laid out as a
32-bit program expects. Ferrix already has a 32-bit Linux ABI, ARMv7-A's,
but that one runs on a 32-bit kernel, where `usize` is the program's word.
Here the kernel is 64-bit and the program is not, so every width the
program sees has to be chosen on purpose.

It is x86-64 only: the Arm architectures have no 32-bit x86 program to run.
It is not Wine's `modify_ldt` segments, `vm86`, 16-bit code, `ptrace`, or a
32-bit vDSO. §5 says which of them Steam may still need.

**The exit**, in the order it can be tested:

1. **I1:** a 32-bit program enters compatibility mode, makes system calls
   through `int $0x80`, and exits. The boot runs one, built at boot from a
   hand-assembled i386 image like `USER_TEST_PROGRAM`.
2. **I3:** Alpine's static musl `busybox` for `x86`, unchanged, passes
   `cargo xtask test-shell` and `test-vfs` on x86-64.
3. **I4:** Debian's i386 `busybox` passes `test-shell` on its own
   `ld-linux.so.2` and `libc.so.6`, and an i686 Rust `std::thread` program
   passes `test-threads`.

After that, what is left is whatever the Steam runtime and client find
missing (§5), found by running them.

## 2. What the programs actually do

Read from musl 1.2.5 (`~/.local/share/ferrix/ferrousli-ref`) and Linux's
`arch/x86/entry/syscalls/syscall_32.tbl` (the UAPI header
`asm-x86/unistd_32.h` in the local QEMU checkout).

* **The way in is `int $0x80`.** musl's `__sysinfo` defaults to a stub of
  `int $128; ret` (`src/internal/i386/defsysinfo.s`), and is replaced only
  when the kernel passes `AT_SYSINFO`. glibc's i386 port has the same
  fallback, `_dl_sysinfo_int80`. A kernel that passes no `AT_SYSINFO` is
  therefore entered by `int $0x80` alone, and the fast `SYSENTER` and
  compatibility-mode `SYSCALL` paths are optional. Ferrix leaves them out
  (§3.3).
* **The thread pointer is a segment.** musl's `__set_thread_area` calls
  `set_thread_area` (243) with `entry_number` −1 and a flat 4 GiB data
  descriptor based at the thread block, then loads `%gs` with the entry the
  kernel chose. If that fails it falls back to `modify_ldt` (123) and
  selector 7. glibc does the same without the fallback. So compatibility
  mode needs three thread-local descriptors in the GDT, per thread, swapped
  on every switch. Linux's are entries 12 to 14.
* **Registers:** the number in `EAX`; the arguments in `EBX`, `ECX`, `EDX`,
  `ESI`, `EDI` and `EBP`; the result in `EAX`. A 64-bit argument is two
  registers, low half first, with **no** alignment to an even register.
  ARMv7-A's EABI aligns such an argument to an even pair, so the arm
  handlers' reassembly cannot be reused as it is.
* **Layouts** differ from ARMv7-A's more often than they agree. `struct
  stat64` is 96 bytes on i386 and 104 on ARM, because i386 aligns a
  `long long` to four bytes. `epoll_event` is packed on both x86 ABIs.
  Anything holding a `long` or a pointer (`iovec`, `msghdr`, `sigaction`,
  `stack_t`, `siginfo`, `rlimit`, `rusage`, `sysinfo`, `statfs`) is 32-bit
  words. And there are the i386-only multiplexers: `socketcall` (102) and
  `ipc` (117), which older glibc builds, the Steam runtime's among them,
  still issue; `mmap` (90) taking a pointer to its six arguments; and the
  pre-`rt` `sigaction` and `sigreturn`.
* **time64:** musl 1.2 on i386 uses the `_time64` calls (403 onward) first,
  as it does on ARMv7-A, so the 32-bit `timespec` calls are a fallback, and
  ARMv7-A already answers most of them.

## 3. The design

### 3.1 The GDT takes Linux's order and Linux's numbers

Ferrix's GDT is Linux's in shape, but one slot shorter at the front, so
every user selector is eight below Linux's: 32-bit user code `0x1b`, user
data `0x23`, 64-bit user code `0x2b`, against Linux's `0x23`, `0x2b` and
`0x33`. Its 32-bit user code descriptor exists only to put the other two
where `SYSRET` computes them. It has no size bit, no granularity and a limit
of zero, so compatibility mode cannot run in it.

Decision: **take Linux's layout exactly**. Entry 1 is an unused 32-bit
kernel code slot, 2 is kernel code (`0x10`), 3 kernel data (`0x18`), 4
32-bit user code (`0x23`), 5 user data (`0x2b`), 6 64-bit user code
(`0x33`), 8–9 the TSS, 10–11 an empty LDT slot, and 12–14 the thread-local
descriptors (`0x63`, `0x6b`, `0x73`). The user code and data descriptors
become flat 4 GiB segments (`G`, `D/B`, limit `0xFFFFF`), which 64-bit mode
ignores and compatibility mode enforces.

The reason for matching numbers rather than only order: programs compare
them. A signal handler reads `uc_mcontext` `cs`; Wine keeps the 32-bit and
64-bit code selectors to switch between modes; debuggers print them. Linux
is the standard (`docs/BACKLOG.md`, decision of 2026-09-13: Linux wins where
it and POSIX differ), and a selector that differs from Linux's is a
difference a program can see.

### 3.2 The ABI of a call is its entry's

Linux decides by the entry, not by the process (`in_compat_syscall()`). A
call through `int $0x80` is an i386 call even from a 64-bit program, and a
`SYSCALL` from 64-bit mode is an x86-64 call even from a process whose image
was 32-bit. Ferrix does the same. `crate::trap::SyscallArgs` gains an `abi`
field, `Abi::Native` or `Abi::Compat`, which the entry that read the
registers fills in. The certified item's dispatcher decodes the number with
the table that field names (`arch::decode_syscall(abi, number)`), behind the
same Spectre clamp against that table's end. So the personality never sees a
raw number, and the item still holds the only decoding
(`docs/certification/FINDINGS.md`, F-09).

Arguments are zero-extended from 32 bits into `SyscallArgs`, as ARMv7-A's
entry already does. Every `int`-typed argument is therefore right as it
is, because the handlers truncate those. A `long` or `off_t` argument that
the handler reads as a native signed word is not, and neither is a structure
the handler reads in native words (`file.rs` reads `iovec` as
`size_of::<usize>()` words). Those are fixed per call in I3, by the handler
asking the call's word width rather than the build's (`signal::word_of`,
`TimeWidth::in_abi`), and a pair of registers joined into one 64-bit
argument before dispatch (`syscall::compat::normalize`). Until a call has been
read for that, its i386 number is **not mapped**: it answers `ENOSYS`, which
`report_unanswered` names, rather than being dispatched to a handler that
would silently misread it. This is `nr.rs`'s rule, "absent rather than
guessed", applied to widths as well as numbers.

### 3.3 The ways in and out of compatibility mode

* **In:** vector `0x80` becomes a DPL-3 interrupt gate. It classifies as
  `Trap::SystemCall` (it already does), and `arch::system_call` reads the
  i386 registers into `SyscallArgs` with `Abi::Compat`. A 64-bit program's
  `int $0x80` takes the same path, as on Linux.
* **Out: always `IRETQ`, never `SYSRETL`.** On AMD, `SYSRET` does not
  reload `SS`'s cached attributes when the kernel's `SS` is null, which an
  interrupt from ring 3 leaves it, and 32-bit code, unlike 64-bit code, uses
  them (Linux's `X86_BUG_SYSRET_SS_ATTRS`, worked around there on every
  switch). `IRETQ` loads `SS` whole. The trap path already leaves by
  `IRETQ`, and so does everything else that enters 32-bit code: the first
  entry of a 32-bit program, and an `execve` of a 32-bit image from a 64-bit
  `SYSCALL`, build a frame and leave through the trap stub's restore path, as
  `rt_sigreturn` already does (`resume_context`). So the hot `SYSCALL` stub
  is not touched, and entering compatibility mode takes no new assembly.
* **`DS` and `ES`:** long mode ignores them. Compatibility mode faults on a
  null one, and `IRETQ` to ring 3 nulls any data selector whose DPL is
  below 3. Every return to 32-bit code therefore loads both with user data
  first. In I1 that is done on the way out. From I2 each task keeps its own
  `DS`, `ES`, `FS` and `GS` selectors, as Linux's `__switch_to` does, and the
  way out restores them.
* **The other two instructions are made harmless, not supported.** Once a
  real 32-bit code segment exists, any 64-bit program can far-jump into it.
  There, `SYSCALL` goes to `IA32_CSTAR` on AMD. That MSR is zero today, and
  zero would be a ring-0 jump to address zero on the program's stack. So
  `CSTAR` gets a stub that answers `-ENOSYS` without switching mode.
  `SYSENTER` faults when `IA32_SYSENTER_CS` is zero, as Linux leaves it
  without IA32 emulation. Ferrix writes that zero at boot rather than
  trusting firmware to have left one. Neither is how musl or glibc enter
  when there is no `AT_SYSINFO` (§2).

### 3.4 A 32-bit process's shape comes from its image

`execve` of an `ELFCLASS32`, `EM_386` image makes a compat process:

* **A 4 GiB address space.** The space's ceiling is `0xFFFFE000`, Linux's
  `IA32_PAGE_OFFSET`, set on `ferrix_vma::AddressSpace` so that `mmap`'s
  free-space search and `MAP_FIXED` both stop there. A reservation above
  4 GiB would have worked too, but `/proc/<pid>/maps` would show it.
* **Placement:** the stack top is just below the ceiling. A PIE's base and
  the dynamic linker's follow Ferrix's rule for native programs, two thirds
  and one third of the way up, but of the 4 GiB window rather than of
  `USER_VIRT_END` (`load::pie_base`, `load::interp_base`). Linux differs: it
  puts an ia32 PIE at `0x400000` (`ELF_ET_DYN_BASE`) and `mmap`s the linker
  below the stack. Ferrix keeps the linker below the program so the heap has
  the space up to the stack. Revisit in I4 if a 32-bit program cares where it
  lands, which a program with a large heap might.
* **The startup stack in 32-bit words:** `src/lib/kernel/ustack` already builds
  `Width::Bits32` for ARMv7-A. There is no `AT_SYSINFO_EHDR`, because the
  vDSO is a 64-bit ELF and is not mapped, and no `AT_SYSINFO` (§2).
  `AT_HWCAP` is `CPUID.1:EDX`, as for x86-64. `AT_PLATFORM` is `i686`,
  Linux's `COMPAT_ELF_PLATFORM`.
* **Entry** at the image's entry point in 32-bit user code (§3.3).
* **Signals:** i386 `sigframe` and `rt_sigframe` from I2. Until then, a
  compat process whose handled signal would need a frame is ended with
  `SIGSEGV`, which is what Linux does when it cannot build one. A signal's
  default action works in I1.

The image's ABI travels in the loader's `Loaded` and the process's
`Startup`, and it is how the program is first entered. Once the program runs,
its mode is its thread's code selector, which the signal code reads
(`UserContext::is_compat`) and `fork` will copy with the rest of the frame
(I2). System call decoding reads neither (§3.2). A native process, which
`devmgr` starts with a 64-bit handle, cannot be 32-bit: `load_native`
refuses an `EM_386` image.

### 3.5 Thread-local descriptors and segment selectors (I2a)

Each thread keeps three `user_desc`-shaped TLS entries and its four data
selectors. A switch to a thread writes its entries into this processor's
GDT slots 12–14 and loads its selectors, `GS` last, around a `swapgs`, since
loading `GS` in ring 0 replaces the kernel's own `GS` base. That is Linux's
`load_gs_index`. `set_thread_area` with −1 picks the first free slot and
writes the number back. `clone` with `CLONE_SETTLS` from a compat call takes
a `user_desc` pointer, not a base. `get_thread_area` reads an entry back.
`modify_ldt` stays `ENOSYS`: musl falls back to it only when
`set_thread_area` fails, and Wine's need for it is §5's.

As built (I2a): the three descriptors live in the processor's GDT while
their thread runs, like registers, and `UserState` carries them, the four
selectors and the program's `GS` base across a switch. `set_thread_area`
writes the live slot with interrupts masked and reloads a register that
names it. A saved selector is checked against the slots before it is
loaded (`gdt::loadable`), so an entry emptied after its selector was
loaded cannot fault the kernel; Linux recovers from that fault instead.
`execve` empties all of it, and a 32-bit program is given user data in
`DS` and `ES` as it is entered, which retired I1's reload of both on every
return to 32-bit code. Saving the `GS` base per task also stops one
program's base surviving into the next, which I1 left possible.

## 5. Open questions, for when they are reached

1. **`modify_ldt`.** 32-bit Wine keeps its TEB in `%fs` through an LDT
   descriptor, and Proton's older 32-bit path needs it. That means a
   per-process LDT, the `LDT` slot of §3.1, and a load on switch. It is I5's,
   and sized when Wine is run.
2. **A 32-bit vDSO.** Not needed by either libc (§2). Linux has one, and a
   program that reads `AT_SYSINFO` unconditionally would need it. Nothing
   found so far does.
3. **The Steam client may not stay 32-bit.** The roadmap already allows for
   a 64-bit client arriving first. If one does, I1–I4 are still Proton's and
   still 32-bit games', and I5 shrinks.

  64-bit user code selector is now `0x33`, not `0x2b`, and the SMP

  out, recorded in `tools/common/data/asm-allowlist.json`. The first entry into 32-bit

  1600 lines.

**2026-09-26, night: I2b is done** (8 estimated, about 13 spent: the
review's forged-frame checks and the word widths it turned out to need), on
branch `i386-i2b`.

* `fork`, `vfork` and `clone` from `int $0x80`: `UserRegs` on x86-64 is a
  `SYSCALL` frame or a trap frame, and a trap-frame child resumes by `IRETQ`
  in its parent's mode, its selectors and flags sanitised. `clone` takes
  i386's `CLONE_BACKWARDS` order, and `CLONE_SETTLS` a `user_desc` read and
  checked before anything is made, put in the child's copy of its parent's
  slots; its `%gs` then reads through it.
* Both frames: `rt_sigframe_ia32` for `SA_SIGINFO`, `sigframe_ia32`
  without, laid out from Linux's `sigframe.h` and `ia32.h`
  (`src/lib/proto/linux-abi::sigframe32`, host-tested), with the `FXSAVE`
  image in `_fpstate_32`. `sigreturn` and `rt_sigreturn` are answered on
  the `int $0x80` path itself. The return reads and checks the whole frame
  before loading any of it: 32-bit user code, user data for the stack, no
  `IOPL`, `VM`, `VIF` or `VIP`, and data segments `gdt::loadable` accepts;
  anything else ends the program with `SIGSEGV` (certification review,
  T.ESCALATE path 8). A plain frame's `sigreturn` leaves the alternate stack
  alone, so `Restored.altstack` is an `Option`.
* The call's word width, not the build's, for `struct sigaction`, `stack_t`
  and `struct rusage` (`signal::word_of`): the 32-bit ones are Linux's
  `compat_` structures. A 32-bit `siginfo` is the 64-bit one with its union
  four bytes lower (`sigframe32::siginfo_from_64`).
* 13 more i386 calls mapped: `fork`, `kill`, `wait4`, `sigreturn`, `clone`,
  `rt_sigreturn`, `rt_sigaction`, `rt_sigprocmask`, `rt_sigsuspend`,
  `sigaltstack`, `vfork`, `tkill`, `tgkill`. The host test caught one error
  of mine on the way: `I386_END` briefly ended below `dup3`.

The boot runs an i386 program whose `SA_SIGINFO` and plain handlers each
change a saved register through their frames, return through
`rt_sigreturn` and `sigreturn`, and must see it -- and an untouched one --
come back; then it forks, and `wait4` reaps the child's status. It runs a
second program eight times with a forged frame -- a kernel or 64-bit code
selector, a kernel stack selector, `IOPL`, virtual-8086 mode, and data
segments naming a kernel slot, the LDT and the TSS -- each of which must
end in `SIGSEGV`, against a control frame changed only in `EAX` that must
return. With the frame check disabled, the boot stops on the first forgery.

**Known limits now:** `execve` from a 32-bit program (its `argv` and
`envp` are arrays of 32-bit pointers), `mmap`, the stat family, `ioctl`,
`fcntl`, `readv`/`writev` and the sockets are unmapped, so no real i386
program runs yet; that is I3.

  `tv_nsec` from an i386 program keeps its low half, as `get_timespec64`
  keeps it for any compat caller; before, only a 32-bit build did.
* **`ioctl`** passes an i386 program's request only if its argument reads
  the same at both widths: the terminal's (`termios`, `termios2`,
  `winsize`) and those taking an `int` or nothing. Anything else is
  `ENOTTY`, as Linux's `compat_ioctl` answers a request it has no
  translation for, rather than reaching a handler that would read it at 64
  bits.
* The boot's i386 program now checks `-ENOSYS` with number 90, the old
  `mmap` taking a block of arguments, since 39 is `mkdir` and mapped.

Two things the first boot found. `su` failed with "can't set groups: Function
not implemented": musl's `initgroups` asks nscd over a socket first, and
`getgrouplist` fails when `socket` answers `ENOSYS`, so the sockets came into
I3. And musl prefers the time32 calls, above.

**Not carried, and why:** `stat`, `lstat`, `fstat`, `stat64` and
`fstatat64` (`sys_fstatat` writes x86-64's `struct stat`; musl and glibc
both try `statx` first); `socketcall` (musl tries the direct calls first;
glibc on i386 does not, so it is I4's); `mmap` (90) and `select` (82), which
take a block of arguments; `rt_sigtimedwait`, `waitid` and
`pidfd_send_signal`, which carry a `siginfo`; `getitimer` and
`setitimer`; `sched_rr_get_interval`; `ugetrlimit` and `setrlimit` (musl
uses `prlimit64`); `set_robust_list` (its head is 12 bytes, not 24);
`clone3` (its `tls` is a `user_desc` there); and every `ioctl` outside the
terminal's. A file whose `read` returns a structure with a `long` in it,
evdev's `input_event` first, is also still at 64 bits.

branch `i386-i4`. Debian 13's dynamic i386 `busybox`, on its own
`ld-linux.so.2`, `libc.so.6` and `libresolv.so.2`
(`tools/common/fetch/fetch-debian-busybox.sh` now fetches them, pinned by hash,
into `$D/i386/`), passes `test-shell` on the x86-64 kernel. `test-threads
--arch x86_64 --i686` builds the Rust `std::thread` program for

What glibc needed that musl had not was found before booting it, by
running the busybox under `qemu-i386 -strace` on the host over about ninety
applets and reading glibc's own entry points with `objdump`:

* **`socketcall`** (102). glibc on i386 sends every socket operation
  through it (`mov $0x66, %eax` in `socket`, `setsockopt` and the rest),
  where musl tries the direct numbers first. `syscall::compat::socketcall`
  reads the sub-call's block of 32-bit words with Linux's `nargs` and its
  order -- `EINVAL` for a sub-call outside 1 to 20 before anything is read,
  `EFAULT` for a block that cannot be -- and the call it names is answered
  as that call. `send` and `recv` are `sendto` and `recvfrom` with no
  address, as Linux answers them; `recvmmsg` and `sendmmsg` are `ENOSYS`.
  A restart puts back `socketcall`'s own registers, not the inner call's.
* **`ugetrlimit`** (191) **and `setrlimit`** (75), which glibc's
  `getrlimit` and `setrlimit` call where musl calls `prlimit64`: a
  `struct rlimit` of two 32-bit words, `RLIM_INFINITY` as `~0` in 32 bits.
* **`set_robust_list`** (311) **and `get_robust_list`** (312), which
  glibc calls in every process and thread: i386's `robust_list_head` is
  12 bytes, and a 24 would be refused.

The boot's compat check runs a fifth i386 program, through `socketcall`:
a Unix socket pair, a byte sent with `SEND` and read back with `RECV`, then
sub-call 0, a missing block and `RECVMMSG`, each refused as Linux refuses
it. With `SOCKETPAIR` unpacked as `socket`, the boot stops on it.

**2026-09-28: System V semaphores.** The Steam client's `threadtools`
makes a one-semaphore set as a mutex between `steam` and its update child
(`semget(key, 1, IPC_CREAT|IPC_EXCL|0600)`, then `SETVAL`, `GETNCNT`,
`GETZCNT`, `GETPID`, `IPC_RMID` with `IPC_64`, and `semtimedop` of -1 and
+1 with `SEM_UNDO` and of -1 with `IPC_NOWAIT`), and without them it
waited on a futex forever. `src/kernel/extensions/personality/linux/src/syscall/sem.rs` answers `semget`,
`semop`, `semtimedop`, `semtimedop_time64` and `semctl` on every
architecture, and on i386 the `ipc` multiplexer's `SEMOP`, `SEMGET`,
`SEMCTL` (whose `ptr` is the address of the `union semun`) and
`SEMTIMEDOP` with an `old_timespec32`, the call masked with `0xffff` first
(its version is in the upper half), and the direct numbers 393, 394 and
420. A 32-bit `semctl` reads and writes the 64-byte `semid64_ds` of
`IPC_64` -- two halves per time, after a 36-byte `ipc64_perm` with a
16-bit mode -- and the pre-`IPC_64` layout, which glibc and musl never
send, is `EINVAL`. `SEM_UNDO` is paid when the process is released. Proven
by the boot's `sem` line and by `cargo xtask test-sem --arch x86_64
--i686`, whose musl goes through `ipc`; the message queue operations of
`ipc` stay `ENOSYS`.

**2026-10-02: System V shared memory.** Built for Steam's web helper,
whose Chromium presents its frames with MIT-SHM (`docs/STEAM.md` §2);
the 32-bit client may reach it too. `src/kernel/extensions/personality/linux/src/syscall/shm.rs`
answers `shmget`, `shmat`, `shmdt` and `shmctl` on every architecture, and
on i386 the direct numbers 395 to 398 and the `ipc` multiplexer's `SHMAT`
(the address stored at `third`, the answer zero, version 1 `EINVAL`),
`SHMDT` (`ptr`), `SHMGET` and `SHMCTL` (`ptr` the buffer). A 32-bit
`shmctl` reads and writes the 84-byte `shmid64_ds` of `IPC_64` -- its
times in two halves after the 36-byte `ipc64_perm`, then `shm_cpid`,
`shm_lpid` and `shm_nattch` at 64, 68 and 72 -- and the pre-`IPC_64`
layout is `EINVAL`, as for the semaphores. `SHMLBA` is a page on x86 and
four on ARMv7-A, as Linux's. Proven by the boot's `shm` line and by
`cargo xtask test-shm --arch x86_64 --i686`, whose musl goes through `ipc`
and which calls 395 to 398 directly as well.

**2026-09-28: I5b, the bootstrapper, as far as Ferrix takes it.** Valve's
`steam.sh` and `ubuntu12_32/steam`, from the `steam-launcher` package's
bootstrap, run on Ferrix from the volume `tools/common/fetch/fetch-steam.sh`
makes, under `cargo xtask test-steam-bootstrap` (KVM, the network, on
demand like `test-steamcmd`). Traced on the gate host first -- the host
runs i386 natively, and `strace -e inject=...:error=ENOSYS` makes it answer
as Ferrix does -- and then booted. What `steam.sh` met, in order:

* **`uname` must say `Linux`**: "Unsupported Operating System" otherwise.
  Ferrix's says `Ferrix` (the customer's choice); the gate's image puts a
  `uname` first in `PATH` that says `Linux` to the bare question and to
  `-s`.
* **`/dev/fd`**: bash's process substitution opens `/dev/fd/63`, and the
  Steam Runtime's `setup.sh` and its logger both use it; `steam.sh` died of
  "log_to_stdin: unbound variable". Fixed in the kernel: devfs carries `fd`,
  `stdin`, `stdout` and `stderr` as links into `/proc/self/fd`, and
  `/proc/<pid>/fd/<n>` is a magic link to the open file, which opens an
  anonymous pipe as a new end of itself. The fs call check reopens one.
* **What a Debian system has and the volume did not**: GNU `tar` (for
  `--checkpoint-action`), `ldconfig` at `/sbin`, `libcap` for scout's
  `srt-bwrap`, and the i386 `libGL.so.1` and `libdrm.so.2` that
  `steamui.so` will not load without. The volume carries them.
* **User namespaces.** Scout's `steam-runtime-check-requirements` runs
  bubblewrap, which Ferrix cannot serve (no `/proc/sys/kernel/overflowuid`,
  and no namespaces for `clone`), prints "Steam now requires user namespaces
  to be enabled" and exits 71, which `steam.sh` makes fatal. The gate prints
  that verdict and sets the check aside (not executable, again after the
  update restores it). It comes back after the display: the client's UI,
  `steamwebhelper`, runs in the `steamrt64` pressure-vessel container, which
  needs bubblewrap too. Whether Ferrix gets namespaces is the customer's.
* **System V semaphores are not optional for the client.** With `ipc` (117)
  `ENOSYS`, `ubuntu12_32/steam` prints "semaphore creation failed" and
  "Thread synchronization object is unuseable" and waits on a futex forever,
  before any network traffic -- on Ferrix and on the host alike. It uses
  them as a cross-process mutex with its update UI child: `semget` with
  `IPC_CREAT|IPC_EXCL`, then without; `semctl` `SETVAL`, `GETNCNT`,
  `GETZCNT`, `GETPID`, `IPC_RMID`; `semtimedop` -1 and +1 under `SEM_UNDO`,
  and -1 with `IPC_NOWAIT`. No shared memory before the display. The
  customer decided to build them, and they are (2026-09-28, the section on
  System V semaphores above); the gate still stops 60 s after that line and
  says so. `FERRIX_STEAM_PRELOAD` can carry an i386 object to preload in
  their place, and a run with one is reported as such and fails.
* **The client drops to the home's owner.** Run as root, as the gate runs
  it, `ubuntu12_32/steam` moves its effective uid to 1000 -- the owner of the
  volume's files -- partway through, keeping a real uid of 0. Semaphore
  sets it made as root with mode 0600 are then refused to it (`EACCES`,
  `EPERM` for `IPC_RMID`), as Linux's `ipcperms` refuses them to an
  effective uid that is neither owner nor creator; the client prints four
  `threadtools.cpp (2526) : Assertion Failed: Permission denied` and goes
  on to ask for its display. A diagnostic run that logged every semaphore
  call (2026-09-28) showed nothing else refused. On the host the client
  runs as uid 1000 throughout and prints none; the gate should do the
  same.
