## 1. Today

There is one callout from the fault path, the page cache's `Filler`
(`user/vmo.rs`, core; implemented by `fs/pages.rs`'s `Fill`, load):

* `AddressSpace::fault` calls `fill_file_page` **before** it takes the
  space's lock: the region is looked up under the lock, the lock is let go,
  and `Vmo::fill_for_fault` runs `Fill::fill`, which allocates and zeroes up
  to `MAX_FILL_RUN` (32) frames, calls `PageSource::fill_range` with no lock
  held (it may wait for the block ring), and keeps each page the VMO still
  lacks (`insert_absent`). Then `resolve` installs the page; a page reclaim
  took in between (`Commit::Unfilled`, `SpaceError::Evicted`) is filled
  again, at most `REFILLS` times, and is then `SIGBUS`
  (`SpaceError::Unreadable`, `trap.rs`'s `BUS_ADRERR`).
* Only `Backing::File` regions are filled. A native `VMO_MAP` maps
  anonymous objects only.
* Dirtiness is the filesystem's: `write` marks pages in the btrfs source,
  and a shared writable mapping marks nothing; `Vmo::mapped_written` makes
  the owner write back **every** page instead (`take_mapped_writes`).
* The fill is synchronous, in the faulting thread, charged to
  `running_group()`: the faulting job pays already. Nothing bounds the wait
  but the block ring's own timeouts.

`NVIDIA.md` §11.4 (OK IF 2026-10-02, not built) planned a second callout,
the fault window: a `FAULT` packet to a server, a killable wait with no
timeout (AoU-17), kernel copies that never wait, `window_insert`,
`window_revoke`, `UNMAPPED`, server death. Its ids are reserved
(`L.user.111-124`, `L.object.121-125`, `H.MEM.20-21`, owner `nvidia`).

## 2. The mechanism

### 2.1 Objects

* A **pager** (`object/pager.rs`, core): a kernel object bound at creation
  to one **port** (the one its requests go to), with a **bound** on how long
  a fault waits for it, and a registry of its outstanding requests. Its
  handle carries `Rights::PAGER` = TRANSFER | WRITE, **no DUPLICATE**: there
  is exactly one handle, so "the pager's death" is defined as that handle's
  close (the NVIDIA review's H7). TRANSFER is kept for K13 (§6).
* A **pager-backed VMO**: an ordinary `Vmo` whose `source` is the pager,
  with a **key** (the packet's key) chosen at creation. Its absent pages are
  the pager's: never committed as zeros. It is created only by
  `PAGER_CREATE_VMO`, at a fixed size, and is never anonymous
  (`is_anonymous()` false, so it is no dmabuf and no `commit_run` target).
  Creation options: `TRAP_DIRTY` (§2.5) and `NO_COPY_WAIT` (§2.4).

The `Vmo`'s `filler: Option<Arc<dyn Filler>>` becomes
`source: Option<Source>`:

```rust
enum Source {
    /// In ring 0: today's page cache. Filled synchronously in the faulting
    /// thread, as now (§7).
    Kernel(Arc<dyn Filler>),
    /// A pager in user space, over its port.
    Pager(Arc<PagerLink>),   // the pager, the key, the options, the dirty state
}
```

so there is **one** place a fault asks for an absent page
(`Vmo::request_page`), whichever side serves it.

### 2.2 The request

A fault on an absent page of a pager-backed VMO, through any region kind
that names the object (a native `VMO_MAP` mapping as well as a file
mapping), and a read of one by a kernel copy, run this, in the
`fill_file_page` position: after the region is looked up, **with no space,
VMO, pager or preemption-disabling lock held**:

1. **Prepare, with no lock held** *(2858 (2))*. Make the request's node
   fallibly: its record (heap, charged to the running task's job by F-37's
   `Charge::bytes`, i.e. the faulting job), the port's room for one packet
   (`port::Promise`, the same promise accounting signal packets use, so a
   flood of faults can never take a pager's port capacity), and **a K7
   ticket issued by the kernel for the faulting process and its job**
   (`Ticket::issue_for`, K7.md §5). Any refusal is the fault's
   `OutOfMemory`, which takes the OOM path a fault takes today.
2. **Coalesce or list, under the pager's request lock, allocating
   nothing.** If an outstanding request on this VMO covers the page **and
   was opened from the same job** *(2858 (1))*, join it (step 4) and drop
   the prepared node after the lock is let go. Otherwise list the prepared
   node for the run of absent pages from the faulting page, at most
   `MAX_FILL_RUN` (the run the page cache asks for today, so a pager sees
   what a filesystem sees). The registry is intrusive: a request's node
   carries its own links (an intrusive list per VMO, ordered by offset), so
   listing it and unlisting it allocate nothing. The lock is held for one
   walk of the VMO's outstanding requests, bounded by the tasks faulting on
   that VMO, and `MEMORY-AND-TIMING.md` states that bound. The common case
   (the page is not yet requested) prepares a node it then uses; a join
   prepared one it drops, which costs an allocation and a ticket on a
   fault that waits anyway.
3. **Send.** Queue one `PACKET_PAGE_REQUEST` on the port, after letting the
   request lock go:

   | Field | Value |
   |---|---|
   | `key` | the VMO's key |
   | `kind` | `PACKET_PAGE_REQUEST` (3) |
   | `signals` | the command in bits 0-7 (`READ` 1, `DIRTY` 2), the run's length in pages in bits 8-31 |
   | `data[0]` | the run's first byte offset in the VMO |
   | `data[1]` | the ticket's id |

4. **Wait**, on the request's wait queue, with a deadline:
   `wait_until_deadline(ready, start + bound)`. The request ends, and its
   ticket with it, in exactly one of five ways (§2.3).

A request is **one per run and job, not one per thread** *(2858 (1))*:
threads of one job that fault the same pages share it, and that job pays
(§2.6). Another job's fault on the same run opens its own request, with its
own packet, ticket and charge, so one job's limit or failure never fails
another job's fault: if the first request ends Failed at its job's limit,
the second is still answered, and its supply skips any page already present
(§2.7), so nothing is paid twice. Requests are bounded by the faulting
tasks, since each task is in at most one, and each request's record and
packet room are charged to the job that opened it. The pager's registry is
the per-VMO intrusive list under one `SpinLock`, taken only by the fault
path's step 2, by
`PAGER_SUPPLY`, `PAGER_OP` and by the pager's close, never by a port's or a
run queue's lock holder.

### 2.3 How a wait ends

| Ending | When | The faulting thread | The request |
|---|---|---|---|
| **Supplied** | `PAGER_SUPPLY` (or `PAGER_OP DIRTY` for a dirty request) covers the whole run | retries the access; a page reclaim took meanwhile is requested again (`REFILLS` as today) | ended, ticket ended |
| **Failed** | `PAGER_OP FAIL` over any page of the run, with a status | a fault: `SIGBUS` `BUS_ADRERR` at the address (`SpaceError::Unreadable`, the path a btrfs read error takes today); a kernel copy: the call fails `EIO` (native `IO`, below) | ended, ticket ended, audited `PAGER` |
| **Timed out** | the pager's bound passes first | as Failed | if no other waiter is left, ended, ticket ended; audited `PAGER` |
| **Killed / signalled** | the process is ending, or (a fault from user mode only) a signal is pending (`trap::must_attend`) | returns to user mode with nothing installed; a signal handler runs and the access faults again, as `NVIDIA.md`'s wait did | as Timed out, unaudited |
| **Pager gone** | the pager's handle closes (or `DETACH`) | as Failed, at once | every request ended, tickets ended, audited once per VMO |

**Never the safe state.** None of the five stops the kernel; a pager can
make a faulting process die (that is the mapping's consent, §5's AoU), never
the machine. The bound is the pager's: set at `PAGER_CREATE`, between
`PAGER_WAIT_MIN` (1 ms) and `PAGER_WAIT_MAX` (30 s, the block layer's own
request timeout on Linux); 0 asks for the maximum. So the longest any
thread waits for any pager is 30 s plus one scheduling latency, and
`MEMORY-AND-TIMING.md` states it.

A native process has no signal handlers: its `SIGBUS` is the unresolved
fault it is today (the process ends, its status says so), and once K4
lands, the fault goes to its exception channel like any other.

The native ABI gains no status: a failed kernel copy in a native call
answers `FAULT`, as a copy from an unmapped address does (Q1, accepted at
2858); the Linux layer's copies choose `EIO` themselves.

### 2.4 Kernel copies

`with_page` (every kernel copy: native calls' user buffers, the Linux
layer's `copy_to_user`, `futex`, `process_vm_*`) faults through
`oom::fault` today, and so it would wait on a pager. Two rules:

* **By default a kernel copy waits, bounded, like a fault** — what Linux
  does for a `read(2)` into an `mmap` of a file, and what the page cache's
  move onto K3 needs (§7: `test-btrfs` and `test-rustc` read files into
  mapped buffers). The bound makes the deadlock `NVIDIA.md`'s RC2 described
  (a pager's own copy faulting into a VMO it serves) a timeout, not a hang.
  A copy is never interrupted by a pending signal, only by its process
  ending.
* **`NO_COPY_WAIT` VMOs never make a kernel copy wait**: an absent page is
  `Refused` at once, the copy fails `FAULT`, and the pager sees no request.
  A present page copies within its mapping's access. This is
  `NVIDIA.md`'s "kernel copies never wait", kept for the windows (the
  customer's D-C1), now a VMO option. The fault path carries the mode in its
  type (`FaultMode::Program` / `Copy` / `CopyNoWait`), so it cannot be
  forgotten at a call site.
* **A copy never waits under a spin lock** *(2858 (3))*. Before
  `FaultMode::Copy` opens or joins a request it asserts that the copy may
  block: preemption enabled and no spin lock held (the same test
  `SleepLock` makes, `sync.rs`, a `debug_assert` and a release-build
  refusal). A copy that cannot block is answered as `CopyNoWait` would be:
  refused at once, `FAULT`, no request. `with_present_page`, the form for
  callers that hold a lock, never faults at all, as today.
* **Copies under a sleeping lock.** Some kernel copies run with a
  sleeping lock held, and those can make the lock's other waiters wait up
  to the pager's bound, as Linux's `mmap_lock` holders do behind a slow
  `filemap_fault`. Found so far: tmpfs's and the page cache's per-inode I/O
  lock across `write(2)`'s copy-in (`ferrix-vfs` `tmpfs.rs`); `Process`'s
  heap lock (`syscall/process.rs`) where a call copies under it; the space's
  `layout` lock, which no copy holds today (checked again at code). The code
  landing lists every site by a search for copies inside `SleepLock`
  guards, and `MEMORY-AND-TIMING.md` states that a pager can hold those
  locks' waiters up to its bound.

### 2.5 Dirty tracking and write-back

A pager-backed VMO keeps a per-page state, under its pages lock, beside the
frame: **Clean**, **Dirty**, **AwaitingClean** (Zircon's three, and the same
transitions). Supplied pages are Clean.

* **A Clean page is never mapped writable.** Every mapping installs it
  read-only (as a copy-on-write page is), so the first write through any
  mapping faults. `resolve`'s present-page early return is below this test,
  as the copy-on-write branch is today (the NVIDIA review's H4: a write to a
  read-only page must not loop).
* **Without `TRAP_DIRTY`** that write fault marks the page Dirty under the
  pages lock, installs it writable, and retries. Kernel writes into the
  object (`VMO_WRITE`, `commit_and_write`) mark Dirty the same way.
* **With `TRAP_DIRTY`** the write fault opens a `DIRTY` request (§2.2, same
  coalescing, wait and five endings) instead. The pager answers
  `PAGER_OP DIRTY` (the page becomes Dirty and the write retries) or
  `PAGER_OP FAIL` (`SIGBUS`; the page stays Clean). This is btrfs's
  `page_mkwrite`: the pager reserves space for a copy-on-write extent
  before it allows the write, and refuses with `ENOSPC` when it cannot.
* **`PAGER_QUERY_DIRTY`** lists the Dirty and AwaitingClean runs of a range.
* **`PAGER_OP WRITEBACK_BEGIN`** turns Dirty pages in a range AwaitingClean
  and **takes their writable translations down** in every mapper (the
  three-phase `forget_pages` and one shootdown, which returns before the
  call does). A write after that faults and makes the page Dirty again.
* **`PAGER_OP WRITEBACK_END`** turns AwaitingClean pages Clean; a page
  written since `BEGIN` is Dirty and stays Dirty. So **no write is lost from
  the dirty set by a write-back that began before it** (H.MEM.23).
* **Reclaim and `PAGER_OP DECOMMIT` take Clean pages only.** Dirty and
  AwaitingClean pages are never taken by either: the kernel's state is
  exact, so `user::cache` needs no `mapped_written` guess for a pager VMO,
  and the pager supplies a reclaimed page again on its next fault.

The pager owns everything else: when to write back, ordering against its
own journal, what to do with dirty pages at its death (they stay in the
VMO, readable and writable, and are lost with it; §2.3's "Pager gone" makes
further absent pages fail).

### 2.6 Who pays: K7's ticket

The kernel issues each request's ticket for the process and job of the
thread that opened it, and puts its id in the packet. The ticket is K7's
as it lands *(2858 (6))*: `issue_for` records the faulting process's K6
`Sender`, read by the kernel from the faulting task's own process, never
from an argument (2525 (1)). The pager thread
`ADOPT`s it (`CHARGE_TICKET ADOPT` naming **the pager handle** instead of a
channel; the ticket is found through the pager's own request registry,
not a channel's `Tickets` list, so a pager can adopt only tickets of its
own outstanding requests, and K7's 64-per-end bound does not apply: the
requests are bounded by the faulting tasks, §2.2; the ticket itself is
one object charged to the faulting job, as every K7 ticket is to its issuer),
commits pages into its aux VMO, and `PAGER_SUPPLY`s them. Under the
adoption the aux commit is charged to the faulting job (K7.md §2.3's first
row) and the frame keeps that charge when it moves (`adopt_pages` moves
frames, never charges). So **the faulting job pays for the page**, against
its own `memory.max` and, once K12 is wired to `charge_target()`, its own
reservation; at its limit the pager's commit answers `NO_MEMORY`, the pager
answers `FAIL`, and the faulting thread gets `SIGBUS`, as a Linux file
fault at a cgroup's limit gets one. The ticket ends with its request (any
of §2.3's endings), so a late `ADOPT` is refused and a pager can charge a
faulting job only while that job waits. The request's record and packet
room are charged to the faulting job directly (§2.2). The in-kernel
`Kernel` source charges `running_group()`, the faulting thread, as today.

### 2.7 `PAGER_SUPPLY`: by move, from the pager's own anonymous memory

`PAGER_SUPPLY(pager, vmo, aux, spec_at)`, spec `{offset, length,
aux_offset, options}` (four `u64`s read through a pointer, so ARMv7-A
carries them whole, as K10's `TIMER_SET` does):

* `pager` (WRITE) must be `vmo`'s pager; `aux` (READ | WRITE) must be an
  **anonymous** VMO; ranges page-aligned and inside both; `options` 0.
* Every page of the aux range must be committed and none held or pinned
  (`adopt_pages`' `Unmoved::Held`): a page a device reaches at its frame
  never moves.
* Under the VMO's pages lock each page the pager VMO lacks takes the aux
  frame; a page it already holds is **skipped** and stays in aux (a pager
  racing a reclaim or another supply loses nothing). Moved frames leave the
  aux VMO by `adopt_pages`' three phases, so no mapper of aux keeps a
  translation of a frame that now belongs to the pager VMO.
* Every request whose run is now present ends Supplied; its waiters are
  woken after every lock is let go.

`DIRTY` requests are answered by `PAGER_OP DIRTY`, not by supply.

### 2.8 `PAGER_OP` and the pager's death

`PAGER_OP(pager, vmo, op, spec_at)`, spec `{offset, length, value}`:

| Op | What |
|---|---|
| `FAIL` (1) | end every request touching the range Failed; `value` is the status the copy sees (`IO` or `NO_SPACE`, anything else `INVALID_ARGS`) |
| `DIRTY` (2) | Clean pages in the range become Dirty and their `DIRTY` requests end Supplied; absent pages are `BAD_STATE` |
| `WRITEBACK_BEGIN` (3), `WRITEBACK_END` (4) | §2.5 |
| `DECOMMIT` (5) | take the range's Clean pages out (three phases); Dirty and AwaitingClean pages stay |
| `DETACH` (6) | as the pager's close, for this one VMO |

**The pager's close** (its handle's last reference, a dying process's
table included) marks every VMO it serves detached, under each VMO's pages
lock, so no new request opens; then, in task context, ends every request
"Pager gone" and their tickets, and lets the port's promises go. It never
runs from a `Drop` that may hold a lock: the close path is task context
(the NVIDIA review's H2). Present pages stay. *(2858 (4))* The close and
`DETACH` `debug_assert` that they may block (preemption enabled, no spin
lock held), as K10's timer close does. A dying process's table is closed by
the reaper's or the last thread's exit path, `object::dispose` of the
table's objects outside the table's lock (`Process`'s handles are taken out
under it and dropped after); the code landing shows that path holds no spin
lock where `Object::Pager`'s drop runs, and if it does, the pager's drop
only marks it detached (which takes the pages locks only) and hands the
rest to the reaper's task-context pass, as K10's parked port references
are.

### 2.9 Lock order

A space's lock, then a VMO's mapper list, then its pages (as today); the
pager's request lock is taken **with none of these held**, except that
`PAGER_SUPPLY` and `PAGER_OP` take the pages lock, let it go, and only then
take the request lock. A port's queue lock and a wait queue's lock are taken
with no pager lock held. No shootdown runs under any of them. Written into
`object/pager.rs`'s module docs and `user/vmo.rs`'s, and the request lock's
sections (bounded by `MAX_FILL_RUN` and the requests on one VMO) into
`MEMORY-AND-TIMING.md`.

## 3. One fault-forwarding mechanism: the windows on K3

The window of `NVIDIA.md` §11.4 is **a pager-backed VMO with options**, and
`nvrm` is its pager. What it planned maps onto K3 one for one:

| §11.4 | On K3 |
|---|---|
| the `FAULT(window, offset, access)` packet, its promised slot charged to the faulting job | `PACKET_PAGE_REQUEST` `READ`, §2.2 |
| a write to a read-only entry forwards (H4) | `TRAP_DIRTY`'s `DIRTY` request, §2.5 |
| the wait: answer, kill, server death | §2.3, **plus the bound** |
| `SIGBUS` on an error answer or death | §2.3 |
| kernel copies never wait (D-C1, RC2) | `NO_COPY_WAIT`, §2.4 |
| the server handle: no duplicate, its close the death (H7) | the pager handle, §2.1 |
| `window_revoke` (take out, `forget_runs`, one shootdown, then release) | `PAGER_OP DECOMMIT`'s three phases (for any state, under a window option) |
| `window_insert` of a pool page **without moving it** (the reason §11.4 rejected a pager VMO: UVM allocates a page before it knows its address) | **an aliasing supply**, `SUPPLY_ALIAS`: the pager VMO references the pool page under a `Vmo::hold` instead of taking the frame, so the frame never moves and the rejection's premise goes |
| memory type from the pool (H6), never executable, whole-mapping only, `UNMAPPED` promised at creation (H1) | window options on the pager VMO |

**What K3 builds** is the forwarding: the request, the packet, the wait and
its endings, the ticket, the close, `FAIL`, `DIRTY`, `DECOMMIT` by move,
and `NO_COPY_WAIT`. **What stays for C3-K**, as its own landing on K3, is
what only windows need: `SUPPLY_ALIAS` and its holds, the memory type, the
whole-mapping refusals and `UNMAPPED`, and the `fork` rule. Its forwarding
and wait ids (among `L.user.111-124` and `H.MEM.21`) are then not written;
whoever re-plans C3-K shrinks the `nvidia` reservation. K3 does not touch
it.

**One change to the reviewed windows design**: their wait gets K3's bound.
§11.4 said "the wait has no timeout" and AoU-17 relied on it being
killable. Under K3 every forwarded wait is bounded; `nvrm` asks for
`PAGER_WAIT_MAX`, which a UVM migration of one region stays far below, and
a stuck `nvrm` costs a client `SIGBUS` after 30 s instead of a hang. AoU-17
loses "there is no timeout". **Question Q2** below.

`NVIDIA.md` §11.7 also said "a later `userfaultfd` reuses this object
rather than adding a second fault callout": it reuses K3. K4 (exception
channels) is not a second mechanism: K3 forwards a fault that a pager can
**resolve**; K4 reports one nothing resolved, which includes a K3 fault that
ended Failed, Timed out or Pager gone.

## 4. The native ABI

From `src/lib/proto/native-abi`, numbers as allotted:

| Call | Arguments | Returns |
|---|---|---|
| `PAGER_CREATE` | `port` (WRITE), `wait_ns_at` (a `u64` through a pointer), `options` (0) | a pager handle, `Rights::PAGER`. Charges one object and its heap to the caller's job |
| `PAGER_CREATE_VMO` | `pager` (WRITE), `spec_at` `{key, pages, options}` (`TRAP_DIRTY` 1, `NO_COPY_WAIT` 2) | a VMO handle with the VMO rights. The object is charged to the caller (the pager's job); its pages to whoever pays for each (§2.6) |
| `PAGER_SUPPLY` | `pager`, `vmo`, `aux`, `spec_at` | 0 |
| `PAGER_OP` | `pager`, `vmo`, `op`, `spec_at` | 0 |
| `PAGER_QUERY_DIRTY` | `pager`, `vmo`, `spec_at` `{offset, length}`, `buf`, `capacity`; writes `{offset, length, state}` records | the number written, `BUFFER_TOO_SMALL` with the first `capacity` when more remain |

Also: `PACKET_PAGE_REQUEST` = 3 and its `signals` layout;
`VMO_MAP`'s protection gains **`MAP_NO_PAGER`** (bit 3), which refuses a
pager-backed VMO (`WRONG_TYPE`) and changes nothing else; `CHARGE_TICKET
ADOPT` accepts a pager handle. Refusals: a handle of the wrong type
`WRONG_TYPE`, a missing right `ACCESS_DENIED`, a VMO not this pager's
`BAD_STATE`, unknown op or option bit, unaligned or out-of-range
`INVALID_ARGS`, an aux page uncommitted or held `BAD_STATE`, a charge
refused `NO_MEMORY`. The ABI crate's host tests cover the numbers, the
specs' layouts and the packet's encoding.

## 5. Rules and requirements

**H.MEM.22**: *an absent page of a pager-backed VMO becomes present only by
its pager's supply. A thread waits on a pager only for a fault on, or a
kernel copy into, a pager-backed VMO its own process maps or names, and the
wait ends on the supply, the pager's failure, the process's kill, the
pager's death, or the pager's bound of at most `PAGER_WAIT_MAX`; every
ending but the supply gives the faulting process `SIGBUS` or its call an
error, and none stops the kernel. The page is charged to the job of the
thread whose fault asked for it.*

**H.MEM.23**: *a write to a page of a pager-backed VMO keeps the page in
the dirty set until a write-back that began after the write ends; a page in
the dirty set is never reclaimed or decommitted.*

| Id | Rule | Check case |
|---|---|---|
| L.user.146 | an absent page of a pager-backed VMO is never committed as zeros; a fault or a waiting copy on it opens one request for the run of absent pages from it (at most `MAX_FILL_RUN`), or joins the outstanding request covering it | a, b |
| L.user.147 | the request is opened with no space, VMO, pager or preemption-disabling lock held; its record, packet room and ticket are had fallibly before it is listed, charged to the faulting job; a refusal is the fault's `OutOfMemory` | a, l |
| L.user.148 | the wait ends Supplied: the access is retried and sees the supplied bytes | a |
| L.user.149 | the wait ends Failed: `SIGBUS` `BUS_ADRERR` at the address, or the copy's error; audited | c |

### The AoU

**AoU-n** (SAFETY-MANUAL, new): *A native safety partition maps no
pager-backed VMO it did not choose. Its description names every VMO it
maps; it maps every VMO it was handed with `MAP_NO_PAGER` unless the
description names that VMO's pager as part of the same or a higher-level
partition; and no pager it relies on is below its own criticality level
(K17 (d) will make the last a kernel refusal).* Rationale: a pager decides
whether and when the partition's faults complete. The bound keeps that from
being a hang, but a `SIGBUS` in a safety function is still a failure the
partition must not accept from a component it did not choose. The kernel's
part is `MAP_NO_PAGER` (L.object.231) and H.MEM.22's bound; FM-12 (a thread
blocked by a server it mapped) gains K3's bound as its mitigation.

## 6. The boot check (`present` in the reference configuration)

`object/pager_check.rs`, `stages_check::check_pager`, run on every boot in
stage 9 right after K7's `ticket` (FX code `STAGE9_PAGER`). As K7's check:
a job tree with a client job C and a pager job P, a process in each, every
call made **through the architecture's own system call entry**
(`arch::drive_native_words`) by threads of those processes. The client maps
the pager VMO with `VMO_MAP` and touches it from user mode (a small
in-kernel user stub, as `write_read_check` runs one), so the fault really
comes from the trap path. The pager is a thread in P serving its port. On
x86-64 (KVM and TCG), AArch64, ARMv7-A at `--smp 2` and four.

| Case | What |
|---|---|
| a | a read fault opens one request; P adopts the ticket, commits into aux, supplies; the client's load returns the bytes; C's memory rose by the run, P's did not |
| b | two client threads of one job fault the same page: one packet, both resumed; **two jobs** fault the same page: two packets, two tickets, one supply each, the second skipping the page already present and moving nothing *(2858 (1))* |
| c | `FAIL`: the client process ends on the fault (`SIGBUS` for a Linux process), one `PAGER` record |
| d | P never answers, bound 5 ms: the client's wait ends **never before the bound** (the exact lower bound, read from the counter at the fault and at the ending) and within 5 s (a generous upper bound that a loaded TCG host does not reach; the measured time is printed) *(2858 (7))*; one `PAGER` record; the request and ticket are gone |
| e | P's handle closed while a fault waits: the waiter ends before the bound would have (bound 5 s, ended in under 1 s, the time printed) *(2858 (7))*; a later fault on an absent page ends without a packet; a present page still reads |
| f | the waiting client is killed: it ends promptly, the request goes |
| g | `VMO_WRITE` from a buffer in a mapping of the pager VMO: waits, then succeeds after supply; the same into a `NO_COPY_WAIT` VMO fails `FAULT` with no packet |
| h | `TRAP_DIRTY`: a write opens `DIRTY`; `PAGER_OP DIRTY` lets it land; the query shows the page Dirty; on a second page `FAIL` ends the writer and the page stays Clean |
| i | `WRITEBACK_BEGIN`; a write after it makes the page Dirty again; `END` leaves that page Dirty and cleans the other; `DECOMMIT` takes the Clean page and not the Dirty one |
| j | supply refusals: aux not anonymous, aux page held, aux uncommitted, missing rights, VMO not this pager's, out of range; each changes nothing |
| k | `MAP_NO_PAGER` refuses the pager VMO and maps an anonymous one; `ADOPT` of a ticket after its request ended is refused |
| l | C at its `memory.max`: the request's record is refused and the fault takes the OOM path; P's commit under adoption answers `NO_MEMORY`, P fails, the client gets `SIGBUS`, P unharmed; **a sibling job's fault on the same page, opened meanwhile, is supplied and resumed** after the first fails *(2858 (1))* |
| m | a supply over a range with one page already present leaves that page and its aux page as they were |
| n | `PAGER_CREATE`/`_CREATE_VMO` decoding: bound clamped, unknown bits refused, `HANDLE_DUPLICATE` of a pager refused |

The boot line:

```
  pager    faults forwarded, coalesced and supplied, paid by the faulting job;
           failed, timed out, killed and detached waits end, audited; copies
           wait or refuse; trap-dirty and write-back keep every write dirty
```

## 7. The page cache onto K3, still in ring 0 (K3b, M2)

M2 moves `fs/pages.rs` onto K3 while it is in ring 0, so that at the lift
(M5) `linuxd` only changes **who serves** the requests. The move is a
landing of its own after K3, with its own ids:

1. **Already one path.** K3 makes `Source::Kernel(Fill)` the page cache's
   source and routes every fault on an absent page, of every region kind,
   through `Vmo::request_page` (§2.1). The kernel source answers in the
   faulting thread, synchronously, exactly as `fill_for_fault` does now:
   same run length, same `allocate_reclaiming`, same `insert_absent`, same
   `REFILLS`, same `SIGBUS` on a failed read. No port, no wait, no ticket,
   no allocation the fill did not already make.
2. **K3b: the kernel's dirty state for the page cache.** File VMOs get §2.5's
   per-page state with the kernel source (`TRAP_DIRTY` off, so the kernel
   marks a mapped write Dirty itself). `take_mapped_writes` then reports
   the pages a mapping actually dirtied instead of every page, btrfs's
   `reclaim_clean` takes its answer from the VMO's Clean set, and its write
   path brackets a write-back with `WRITEBACK_BEGIN`/`END` (in-kernel
   calls, the same functions the native op calls).
3. **M5, the lift.** `linuxd` creates its file VMOs with `PAGER_CREATE_VMO`
   on a pager of its own, and serves `READ` from its btrfs client and
   `DIRTY` with btrfs's space reservation. The kernel's `Source::Kernel`
   then has no user left and goes with the load.

**Why `test-btrfs`, `test-powerfail` and `test-rustc` stay unchanged**
("unchanged" in MICROKERNEL.md §8's sense: PASSED, the same check counts,
on all four boots):

* K3 itself changes no byte any of them reads: step 1 is a refactor of the
  one call site, and the kernel source's fill is today's code. Its gate
  carries the rows to show it *(2858 (9))*.
* K3b changes *which* pages a shared writable mapping reports for
  write-back: exactly the written ones instead of all. Everything those
  rows check is file contents, on-disk consistency after a cut, and a
  compile's output, which a more precise dirty set does not change, except
  if it **misses** a written page. That is the hazard, and it is what
  H.MEM.23 and check i rule out at the kernel level; `test-powerfail`'s
  cut-and-check rounds are the end-to-end row for it, and K3b is gated on
  them on four boots before it lands, with a negative control (a mapped
  write left Clean) that `test-powerfail`'s mmap round must catch. If no
  such round exists, K3b adds one first.
* Timing: the kernel source adds one match per fault on an absent page; no
  row times a single fault, and `test-rustc`'s wall time is reported beside
  `main`'s.
