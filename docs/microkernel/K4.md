# K4: exception channels

**Design for review, 2026-10-21** (agent mk-k4, branch `mk/k4`, on `main`
`a2d87fe62`). It covers `docs/MICROKERNEL.md` §3, row K4: *faults of native
processes delivered to a supervisor* instead of panic or kill. Supervised
servers need this, since K13's restart contract builds on it, and so do
`linuxd`'s own faults after the lift. Stage M2. Ids, allotted by the product
owner on 2026-10-21: **H.TRAP.20, L.trap.9-13, L.object.241-246,
L.x86_64.186, L.aarch64.66, L.armv7a.28**. Native calls **0x1081-0x1083**.
Right **`SUPERVISE` = 1 << 11**. Panic code **FX-0917**. Audit events
**Granted 8, Ended 4, Changed 4**. One `stages_check` slot,
**`check_exceptions`**.

Zircon's exception channels are the reference (`zx_task_create_exception_channel`,
`zx_exception_info_t`, an exception handle that is resolved by closing it).
Ferrix's version differs from Zircon's in three places. The faulting thread's
wait is bounded. A resumed context is checked as sigreturn's is. A Linux
signal is the default action, not a kill.

## 1. What there is today

A trap from user mode that the address space does not resolve (an unmapped
or refused access, an undefined instruction, a breakpoint, any other
architecture fault) goes to `trap::user_fault_as`, which is in the core. That
function opens interrupts and calls the personality's
`ReturnPath::fault_signal`. In `syscall::deliver::fault_signal` that forces
the Linux signal `arch::fault_signal` chose (`SIGSEGV`, `SIGBUS`, `SIGILL`,
`SIGTRAP`, `SIGFPE`) on the running thread. A native process has no handler,
so the default action applies: the process ends, and `PROCESS_STATUS` reports
`PROCESS_KILLED` with the signal. The machine stops only when there is no
personality or no process (`UNEXPECTED_EXCEPTION`).

Nothing else can see a native process's fault, let alone act on it.
`Rights::PROCESS` deliberately reaches nothing inside a process
(`native-abi/rights.rs`), and `ptrace` is not built: `sched::work::TRACE` is
reserved, and nothing posts it.

## 2. The mechanism

### 2.1 Objects

* **An exception channel** is an ordinary channel (`object::channel`). The
  supervisor holds the read end. The kernel keeps the other end, the only
  writing end, in a **slot** on the task the channel is attached to: a new
  `supervisor: SpinLock<Option<Attached>>` field on the core `Process`
  (`object/process.rs`) and on `Job` (`object/job.rs`). `Attached` holds the
  kernel's `Arc<Endpoint>` and the level's timeout. Since only the kernel
  can write the channel, everything in a report is the kernel's, as K6's
  attested sender is: the identity fields are never taken from anyone's
  body.
* **An exception** is a new kernel object, `Object::Exception`, defined in
  `object/exception.rs` (core ring). It stands for one faulting thread
  that is suspended in the kernel. `ExceptionCore` holds, under one lock:
  * `state`: `Pending`, `Resolved(Verdict)` or `Expired`;
  * `context`: a copy of the thread's `arch::UserContext`, which
    `EXCEPTION_STATE` reads and writes;
  * `changed: bool`;
  * a `WaitQueue` the faulting thread sleeps on.

  The handle carries `Rights::EXCEPTION`, which is TRANSFER, READ, WRITE and
  MANAGE. It has **no DUPLICATE**: exactly one handle exists, so "the last
  handle closed" means "the holder let it go".

### 2.2 Who may attach

`EXCEPTION_CHANNEL_CREATE(task, timeout_ms, options)` attaches. It needs
the new right **`SUPERVISE`** on a process handle or a job handle.

* Resuming with a changed context is control of the process's execution. A
  supervisor can then run any code with the process's handles, so
  `SUPERVISE` is as strong as holding everything the process holds. It is a
  right of its own, apart from `MANAGE` (kill, start) and `WAIT`.
* **Who gets it.** `PROCESS_CREATE` answers `Rights::PROCESS_CREATED` =
  `PROCESS | SUPERVISE`, since the creator chose the image and the
  bootstrap. `JOB_CREATE` answers `Rights::JOB_CREATED` = `JOB |
  SUPERVISE`. The constants `Rights::PROCESS` and `Rights::JOB` stay as they
  are, so the handles the kernel gives out with authority of its own carry
  no `SUPERVISE`:
  * `DEVMGR_START`'s process handle (the promise in `Rights::PROCESS`'s
    documentation stands);
  * devmgr's drivers job;
  * `JOB_FOR_CGROUP`'s handles. A cgroup delegation must not grant what
    Linux would give only to `ptrace` under `ptrace_may_access`.

  `HANDLE_DUPLICATE` and `HANDLE_REPLACE` can only drop the right, never add
  it (`Requested::resolve`). `Rights::ALL` gains bit 11. Each comparison
  against `ALL` is updated in the same commit, as K12's bit 8 was.
* **One channel per task.** Attaching to a task that already has a live
  channel is `ALREADY_BOUND`. Attaching to an ended process is `BAD_STATE`.
  An **unstarted** process may be attached, so that a supervisor is in place
  before the first instruction runs: the call reaches it through `Control`,
  as `PROCESS_START` does.
* **Detaching** is closing the read end, or every duplicate of it. The slot
  sees `peer_closed()` at the next fault, or at the next attach, and clears
  itself; after that a new attach succeeds. Messages still queued when the
  read end closes are dropped with it. Each one holds an exception handle,
  whose drop **hands that exception on** (§2.5), so nothing waits on a
  supervisor that has gone.
* The read end carries DUPLICATE, TRANSFER, READ and WAIT, but not WRITE.
* `timeout_ms` must be in `1..=EXCEPTION_TIMEOUT_MAX_MS` (10,000).
  `options` must be 0.
* **Charging.** Attaching charges the caller's job one `Resource::Objects`
  unit and the heap of the channel pair and the slot (`Charge::bytes`), as
  `CHANNEL_CREATE` is charged. At either limit the call is refused with
  `NO_MEMORY` and nothing is attached.
* A successful attach is audited as `EXCEPTION_ATTACHED` (Granted 8). The
  subject is the caller, and the target is the process or job. A supervisor
  is a grant of control, recorded as `DELEGATED` and `CONTROL` are.

### 2.3 The chain, and where it is entered

`trap::user_fault_as` gains one step before `fault_signal`. With interrupts
open, as they already are there, it calls `exception::raise(frame, trap,
signal)`, which walks the **levels**:

1. The faulting process's own slot (level 0).
2. Each job from the process's job upwards to the root (levels 1 to n).

Levels with no attached channel are skipped at the cost of one lock and one
`Option` read each. **A process with no supervisor anywhere costs one walk of
empty slots** and nothing else. The other boot checks then see exactly
today's behaviour, and that walk is the only cost an unsupervised fault pays.

At each level that has a live channel:

1. Clone `Attached` out of the slot and let the slot's lock go.
2. Make the exception: allocate `ExceptionCore` and the 64-byte report.
   Both allocations are fallible, and both are charged to the faulting
   process's job.
3. Write the report and the exception's handle to the channel with
   `Endpoint::write`.

Any failure in steps 2 or 3 **skips the level**. The failures are a refused
charge or allocation, a full queue (`MAX_QUEUED`), and a closed peer, which
also clears the slot. Each skip is counted (`exception::skipped()`) and is
never a panic. The faulting thread then waits (§2.4) and acts on the outcome
(§2.5).

**When the chain ends without a verdict, the fault takes today's path.** That
happens at the last level, or on an expiry. `fault_signal` runs exactly as
before, so the default action is the one a process with no supervisor gets.
A supervisor's failure therefore never makes the outcome worse than having
no supervisor.

The chain is not entered for a process whose end is already recorded
(`Process::is_terminated`): that goes straight to today's path, which leaves.

Which traps are reported: every trap that reaches `user_fault` or
`user_fault_as` today, and only those. That means unresolved page faults
(`SIGSEGV` and the past-end `SIGBUS`), breakpoints, illegal instructions and
architecture faults. A fault the address space resolves (demand paging,
copy-on-write) is never reported. Signals sent by `kill`, seccomp's
`SIGSYS`, and faults taken in kernel mode on user addresses (`EFAULT`) are
not traps a program took, so they never reach the chain.

### 2.4 The bounded wait

The faulting thread sleeps on its exception's `WaitQueue`, holding no lock,
with interrupts open, in the trap dispatch. A fault from user mode already
does this today when it waits for a TLB shootdown (`handle_page_fault`). The
wait ends at the first of three things:

* **a verdict**, set by `EXCEPTION_RESOLVE` or by the handle's drop;
* **the process's end**: a job kill, another thread's `exit_group`, or a
  fatal signal to the process. The wait is woken the way the item's other
  waits are woken by an end (`Process::end_record` posts `END` to its
  tasks). The thread then takes the way out, where it leaves, and the
  exception becomes `Expired`;
* **the deadline**.

There is **one deadline for the whole chain**. It is fixed at the first
level a report reaches, as `now + EXCEPTION_TIMEOUT_MAX_MS`. Each level waits
until `min(now + its timeout, chain deadline)`. So **one fault waits at most
`EXCEPTION_TIMEOUT_MAX_MS` in all**, however deep the job tree, and any one
level waits at most its own timeout.

**Expiry is the default action.** The exception becomes `Expired` under its
lock, so a later `EXCEPTION_RESOLVE` answers `TIMED_OUT` and changes
nothing. The expiry is audited as `EXCEPTION_KILLED` (Ended 4) with detail
`EXPIRED` and the level. The chain then **ends**, without trying the levels
above, and the fault takes today's path (§2.3). An expiry does not hand on,
because a supervisor that does not answer has failed, and the rule for a
failure is "as if unsupervised".

A signal sent to the thread while it waits stays pending. That includes
`SIGSTOP` and a cgroup freeze. It is delivered, or parks the thread, on the
way out after the verdict, through the existing attention path. A wait never
ends early because of a signal, only because of the process's end.

The wait does not touch vector state. The thread blocks as any wait in the
kernel blocks, and the switch saves and restores its registers (the §9.8 3a
contract). K4 neither exposes nor changes vector state (§3.2).

### 2.5 Verdicts

`EXCEPTION_RESOLVE(exception, verdict)` needs MANAGE and works only while
the exception is `Pending`. A second resolve is `BAD_STATE`, and one after
expiry is `TIMED_OUT`.

| Verdict | What the faulting thread does |
|---|---|
| `RESUME` (0) | Stores the exception's context into the trap frame (`UserContext::store_trap`) and returns from the trap. An unchanged context retries the faulting instruction. On x86-64 a breakpoint resumes after the `int3`; on the Arm pair it resumes at the `brk` or `bkpt` itself, so the supervisor moves the pc on: the report says which (§3.1). If `changed` is set, the resume is audited as `EXCEPTION_CONTEXT` (Changed 4), with the old and new pc |
| `KILL` (1) | `Host::kill(job::KILLED_STATUS)`, which is what a job kill does. The thread then leaves on its way out, and `PROCESS_STATUS` reports `PROCESS_KILLED`. Audited as `EXCEPTION_KILLED` with detail `VERDICT` and the level |
| `HAND_ON` (2) | Goes to the next level, or to today's path after the last |

Any other verdict is `INVALID_ARGS`.

**An exception whose handle is closed while it is `Pending` is handed on**:
`Drop` for the handle's object sets `Resolved(HandOn)` and wakes the thread.
This covers three cases: a supervisor that closes without deciding, a
supervisor that ends (its table closes), and a channel closed with the
message still queued.

### 2.6 Nested and recursive faults

* **A supervisor's own fault** goes to the supervisor's own chain, like any
  process's fault. It is never routed specially and never skipped.
* **The kernel never delivers recursively.** A thread waiting on an
  exception is in the kernel, so it cannot take a user fault, and **one
  thread waits on at most one exception at a time**. Delivering touches no
  user memory: the report and the exception live in kernel heap. A fault in
  the supervisor's own `EXCEPTION_STATE` copy is the supervisor's `FAULT`
  status, not a trap.
* **Self-supervision.** A process may hold the read end of a channel on its
  own process, or on a job above itself. The kernel cannot tell who will
  read a channel, since handles move. If the only thread that would answer
  is the one that faulted, nobody answers. The wait expires, and the default
  action runs (case e2 in §5). That is the backstop, and it is bounded.
* **Cycles.** A supervises B and B supervises A; or A's handler faults and
  its report goes to B, whose handler faults, and so on. Every faulting
  thread blocks, there are finitely many threads, and every wait is bounded
  by the chain deadline. So a cycle ends within `EXCEPTION_TIMEOUT_MAX_MS`
  of its last fault, with the default action at each blocked level.
* **A supervisor that dies holding exceptions** hands each of them on
  (§2.5). The faulting thread moves to the next level at once instead of
  waiting for the deadline (case k).
* **Repeated faults.** A supervisor that resumes an unchanged context at a
  faulting instruction gets the same fault again. Every round is its own
  bounded wait and its own decision. The kernel does not cap the number of
  rounds, just as Linux does not cap a `SIGSEGV` handler that returns. It
  does report `repeat`: how many reports in a row this thread has raised at
  the same pc and address. That count is kept in the core `Task` and reset
  by any return to user mode that was not a resume of a report.

### 2.7 Coexistence with Linux signals and `ptrace`

* **Linux signals.** The chain runs **before** the personality's signal. A
  fault that is handed on all the way, or that expires, is forced as the same
  signal `fault_signal` forces today: a handler of the program's own runs, or
  the default action ends it. A `RESUME` delivers no signal: the fault is
  resolved.
  
  A Linux process meets the chain only if someone holds `SUPERVISE` on it or
  on one of its jobs. From §2.2 that means a process made by
  `PROCESS_CREATE`, or one in a job made by `JOB_CREATE`, never one reached
  only through a cgroup. The supervisor sees it first, by its own explicit
  choice. Garbage collectors and JITs that live on `SIGSEGV` keep today's
  behaviour unless supervised, and a supervisor that hands on costs them one
  round trip per fault.
* **`ptrace`** is not built (`work::TRACE` is reserved). When it is built
  in the personality, a fault's signal-delivery stop is the personality's,
  so it comes **after** the K4 chain hands on, and a tracer never sees a
  fault a supervisor resumed. That order is fixed here: the kernel's
  supervisor first, then the personality's view. The kernel cannot ask the
  personality's trace state from the core without an upcall (F-09), and
  after the lift a Linux program's faults leave restricted mode to `linuxd`
  (K1) and never reach K4. A native debugger uses K4 itself: breakpoints
  arrive as `BREAKPOINT` reports.
* **After the lift (M5).** K1's restricted-mode exit decides first. A
  Linux program's fault in restricted mode goes to `linuxd` by K1. A fault
  of `linuxd`'s own code, in normal mode, takes the K4 chain. The partition
  manager supervises `linuxd`'s job, and with K13's rule ("a `linuxd` that
  dies takes its partition's programs with it") its verdict is `KILL` or a
  restart decision. K1's design states where its branch sits relative to
  `exception::raise`.
* **K3.** A pager timeout returns `SIGBUS`/`EIO` to the faulting process
  (K3's row). If that comes through `user_fault_as`, it is reported like any
  other `SIGBUS`. K3's design decides whether it does.
* **K13** builds on `KILL` and `HAND_ON`, and on the `EXCEPTION_KILLED`
  record, to restart a server. K4 adds no restart semantics.

### 2.8 Locks and allocation

The slot locks (one per process and per job) are plain `SpinLock`s taken in
task context only, and nothing is taken under them. `ExceptionCore`'s lock
is the same. The channel write takes the peer's queue lock, as any write
does. No K4 lock is held across a wait, a channel write or a kill. Every
allocation is fallible and happens before the write, and none happens with
interrupts masked.

## 3. The native ABI

From `src/lib/proto/native-abi/src/nr.rs`, as allotted:

| Number | Call | Arguments | Returns |
|---|---|---|---|
| 0x1081 | `EXCEPTION_CHANNEL_CREATE` | `task` (process or job, `SUPERVISE`), `timeout_ms` (1..=10,000), `options` (0) | the read end: DUPLICATE, TRANSFER, READ, WAIT |
| 0x1082 | `EXCEPTION_STATE` | `exception` (READ to read, WRITE to write), `op` (`READ` 0, `WRITE` 1), `buffer`, `length` (exactly `size_of::<ExceptionRegisters>()`) | 0 |
| 0x1083 | `EXCEPTION_RESOLVE` | `exception` (MANAGE), `verdict` | 0 |

Refusals: a handle of the wrong kind is `WRONG_TYPE`; a missing right is
`ACCESS_DENIED`; an unknown option, op or verdict, a wrong length, or a
timeout out of range is `INVALID_ARGS`; a second attach is `ALREADY_BOUND`;
an ended process, or a resolved exception, is `BAD_STATE`; an expired
exception is `TIMED_OUT`; a refused charge is `NO_MEMORY`; a bad pointer is
`FAULT`. A refusal changes nothing.

### 3.1 The report

The report is 64 bytes, native-endian, `#[repr(C)]` in the ABI crate as
`ExceptionReport`:

| Field | Type | |
|---|---|---|
| `kind` | u32 | `PAGE_FAULT` 1, `BUS` 2 (past-end), `BREAKPOINT` 3, `ILLEGAL` 4, `OTHER` 5 |
| `level` | u32 | 0 for the process, then 1, 2, ... per job upwards |
| `pid` | u32 | the faulting process |
| `repeat` | u32 | §2.6 |
| `tid` | u64 | the faulting task's id |
| `job` | u64 | the faulting process's job id |
| `address` | u64 | the fault address (0 when there is none) |
| `code` | u64 | the architecture's own code: a vector, ESR or FSR |
| `pc` | u64 | the saved pc |
| `flags` | u32 | `WRITE` 1, `EXECUTE` 2, `PRESENT` 4, `PC_AT_TRAP` 8 (the pc is the trapping instruction's own) |
| `reserved` | u32 | 0 |

The message carries exactly one handle: the exception. The host tests in
`native-abi` cover the layout, the numbers' decoding, `Rights::SUPERVISE`,
`Rights::EXCEPTION` and the two `*_CREATED` constants.

### 3.2 Registers, and the check on a write

`ExceptionRegisters` is laid out per architecture in the ABI crate:

* x86-64: the 16 general registers, `rip`, `rflags`, `cs` and `ss`.
* AArch64: `x0` to `x30`, `sp`, `pc` and `pstate`.
* ARMv7-A: `r0` to `r15` and `cpsr`.

A read copies the exception's context. A write is **checked before
anything is stored**, by `arch::UserContext::from_supervisor(&self,
&ExceptionRegisters) -> Result<UserContext, BadFrame>`, the rules of each
architecture's `restore_signal_frame` (`docs/I386.md` I2a/I2b, ledger 7, 15
and 23):

* **x86-64 (L.x86_64.186).** `cs` goes through
  `restored_code_selector(cs, rip, rsp)`: 64-bit user code, or the 32-bit
  user code selector only with `rip` below 4 GiB, and `rip` and `rsp` in
  the user half. A frame outside those is refused, not quietly corrected.
  `ss` is pinned to `USER_SS`. `rflags` is `& FLAGS_RESTORABLE |
  FLAGS_ALWAYS`, so IOPL, VM, VIF, VIP, TF and IF-off can never be loaded.
  A write that asks for any of them is **refused**, unlike sigreturn's mask:
  a supervisor that asks for IOPL is told so. The data segment selectors and
  the FS and GS bases are not in the context, so K4 cannot write them.
* **AArch64 (L.aarch64.66).** `pstate` must be `& PSTATE_NZCV | USER_SPSR`
  exactly: EL0t, with DAIF clear. Any other bit is refused. `pc` and `sp`
  must be user addresses. That is stricter than sigreturn, which an `ERET`
  to EL0 makes harmless; it is kept the same for all three architectures.
* **ARMv7-A (L.armv7a.28).** `cpsr` must be within `CPSR_RESTORABLE |
  USER_CPSR`: USR mode, with A, I and F clear. Any other bit, or mode, is
  refused. `pc` and `sp` must be user addresses.

A refused write is `INVALID_ARGS`, and the context is left as it was. An
accepted write replaces the context and sets `changed`. TLS registers,
vector state and the i386 descriptors are neither read nor written by K4:
K1 owns them for `linuxd`.

## 5. The boot check (`present` in the reference configuration)

`stages_check::check_exceptions` runs in stage 9's native-objects step on
every boot of the reference configuration: x86-64 under KVM and TCG,
AArch64, and ARMv7-A at `--smp 2` and at four. It prints `stage 9
exceptions ...` with its counts, and stops the boot with FX-0917 on any
failure.

The supervisor side is the check process, driving the three calls through
the native dispatch, as the other stage 9 checks do. The faulting side is
**real programs**, because only an instruction executed in user mode takes
the path under test. They are hand-encoded per architecture, as
`arch/*/trap/check.rs` does, made with `PROCESS_CREATE` from a VMO and
started with `PROCESS_START`. Each one ends with `exit_group(97)` if it gets
past its fault, and with `exit_group(rX)` where the case needs a register
to show through.

| Case | What it requires | Ids |
|---|---|---|
| a. resume, changed | A program loads from address 0, then exits with a register. The supervisor reads the state, finds `kind` PAGE_FAULT and `address` 0, writes pc past the load and the register as 42, and resumes. The exit status is 42, one `EXCEPTION_CONTEXT` record shows the old and new pc, and nothing has been signalled | 12, 244, 243 |
| b. forged contexts | One fault, then one write per forgery, each `INVALID_ARGS` with the state read back unchanged. x86-64: a kernel `cs`, 32-bit `cs` with `rip` 4 GiB, IOPL, VM, TF, a kernel `rip`, a non-canonical `rsp`. AArch64: `pstate` EL1h, DAIF set, a kernel `pc`. ARMv7-A: `cpsr` SVC mode, I set, a kernel `pc`. A control write that changes only one general register is accepted | 244, x86_64.186, aarch64.66, armv7a.28 |
| c. kill | Verdict KILL. `PROCESS_STATUS` is KILLED, one `EXCEPTION_KILLED` record has detail VERDICT, and the program did not exit 97 | 12 |
| d. hand on | Channels on the process and on its job, from a `JOB_CREATE`d job. The process level answers HAND_ON, and the job level gets the same fault with `level` 1, resumes it past the fault, and the program exits 97 | 9, 12 |
| e. expiry | A 5 ms channel nobody reads. The program ends KILLED with `SIGSEGV`, today's path, between 5 ms and 5 ms plus a stated slack after the fault. One `EXPIRED` record. A resolve afterwards is `TIMED_OUT` | 10, 11, 245 |
| e2. self-supervision | A program attached by its own job, whose only reader is itself: expiry, then the default action, within the bound | 10, 13 |
| f. closed unresolved | The supervisor closes the exception handle. It is handed on with no level left, so the program is KILLED by `SIGSEGV` well before the timeout | 12 |

## 10. Questions put to the review (answered in §11)

1. **Expiry ends the chain** instead of handing on. Is "as if unsupervised"
   the right default, or should an expiry kill the process? A kill is
   stricter for a safety partition, but it is worse than today for a Linux
   program with its own handler.
2. Is the **10 s chain bound** acceptable as `EXCEPTION_TIMEOUT_MAX_MS`?
3. Is the **supervisor-before-personality order** right (§2.7), given that
   ptrace will come after it?
4. Should **`RESUME` with a changed context** be audited every time? A
   native debugger stepping a program makes one record per step, which the
   job's audit budget bounds.

## 11. The review's conditions (OK IF, ledger 2871)

The consultant's review of 2026-10-21 accepted §10's answers as the design
proposed them: expiry as unsupervised (Q1), the 10 s chain bound, stated in
`MEMORY-AND-TIMING.md` (Q2), the supervisor before `ptrace` (Q3), and every
changed resume audited, bounded by the job's audit budget and the overflow
rule, said in `AUDIT.md` (Q4). Its conditions, and how each is met:

1. **No privilege is raised under a supervisor.** A supervisor could
   rewrite a privileged process's registers if a supervised process could
   `execve` a set-id program and gain its ids. Linux closes this for a
   traced process (`LSM_UNSAFE_PTRACE`). `exec` asks a core predicate,
   `Process::supervised()`: true while a live channel is attached to the
   process or to any job above it. When it is true, `set_ids` becomes
   `SetIds::NONE`, beside `no_new_privs` (`syscall/exec.rs`). Ferrix has
   no file capabilities (no `security.capability`), so set-id is the only
   raise. Case n and control N14.
2. **Every way a process comes under a supervisor:**
   * `PROCESS_CREATE` into a supervised job (needs MANAGE on the job);
   * `JOB_CREATE` under a supervised job, then a process made in it;
   * `fork`/`clone` of a supervised process: the child stays in its job,
     and (1) holds for it;
   * a `cgroup.procs` move;
   * `mkdir` in cgroupfs.

   The last two reach only cgroup jobs. A cgroup job is reached only
   through `JOB_FOR_CGROUP`'s handles and the root job's, and neither
   carries `SUPERVISE` (stated in L.object.246). So no cgroup job can hold
   a channel, and no move or `mkdir` can put a process under one.
   The move refuses anyway, as defence in depth: a `cgroup.procs` move
   into a job whose chain holds a live channel is `EBUSY`. Case o forges a
   `SUPERVISE` handle to a cgroup job inside the check's own table, which
   only a kernel check can do, attaches, and requires the refusal. It also
   requires that the root job's handles carry no `SUPERVISE`. Control N15.
3. **Hand-on drops and locks.** A closing read end empties its queue
   under the inbox lock today (`Endpoint` close). K4 takes the queued
   messages out under that lock and drops them **after it is released**.
   That drop runs the exceptions' `Drop`, which takes the exception's
   lock and wakes its queue. A dying supervisor's table is closed by the
   process's release, in task context with interrupts open
   (`object::dispose`), so every hand-on runs in task context and never
   under a queue, slot or table lock. The diff check is shown the call
   path.
4. **A changed context returns through the full return.** A fault always
   arrives through the exception entry, never through a system call, so
   the context is stored into a `TrapFrame` and leaves by that entry's own
   exit on every architecture:
   * x86-64: the trap stub's `iretq`, never `sysretq`;
   * AArch64: the exception vector's `eret`, with SPSR and ELR from the
     frame;
   * ARMv7-A: the abort or undefined stub's full restore, ending in
     `rfeia`.

   Nothing in K4 enters the fast path or the `SYSCALL` exit.
5. **`from_supervisor` shares sigreturn's checks.** It calls the same
   functions as `restore_signal_frame` (`restored_code_selector`, the
   `FLAGS_RESTORABLE`, `PSTATE_NZCV` and `CPSR_RESTORABLE` masks, from one
   definition) and differs only in refusing where sigreturn masks. Case b
   adds these forgeries, each refused:
   * x86-64: AC (bit 18 is restorable, so AC is *accepted*, as sigreturn
     accepts it, and the case requires that); NT; RF; and every other bit
     outside `FLAGS_RESTORABLE`, one at a time.
   * AArch64: SS and IL.
   * ARMv7-A: J, E, and T. Since `CPSR_RESTORABLE` includes T, T is
     accepted only as Thumb state, as sigreturn accepts it. **The pc's low
     bit is never read as an interworking switch**: the pc is stored as
     given, the state comes from CPSR.T alone, and a pc whose alignment
     does not fit the state (bit 0 set, or bit 1 set in ARM state) is
     refused.

   N1 runs on all three architectures, N12 on AArch64, N13 on ARMv7-A.
6. **Right bits.** Bits 8 (K12, `RESERVE`), 9 (K3), 10 (K2) and 11 (K4,
   `SUPERVISE`). `Rights::ALL` and the undefined-right probe (the lowest
   bit above `ALL`) move with whichever of them lands, as ledger 2845 (6)
   requires.

   These callers of `PROCESS_CREATE` and `JOB_CREATE` now receive
   `SUPERVISE`:
   * init's `Type=native` services (`directory.rs`), made in a cgroup's
     job;
   * devmgr's drivers (devmgr's `process_create`);
   * the `native` library's `Job::create` users;
   * the kernel's boot checks.

   Each caller chose the image the process runs and the bootstrap it
   starts with, and holds MANAGE on the job it is made in. With those it
   could already have chosen to run any code with any handle it gave the
   process. `SUPERVISE` adds control over handles the process receives
   later from others, which is the same authority a parent holds over a
   child under `ptrace` (same uid, dumpable). That is stated in
   `Rights::SUPERVISE`'s documentation and in the VA, path 8b.
7. **Timing cases that do not flake.**
   * Case e keeps its exact lower bound (no default before the level's
     timeout) and an upper bound of the timeout plus `PATIENCE_NANOS`, the
     boot checks' slack on a loaded TCG host.
   * Case k's "well before" is the job level hearing the fault before the
     process level's timeout. That level's timeout is set to the maximum,
     10 s, so the margin is seconds.
   * Case f's is the same.
8. **Evidence before code review:**
   * `test-boot` on x86-64 (KVM and TCG), AArch64, ARMv7-A, and ARMv7-A
     at `--smp 2`, each with the `exceptions` line and the existing
     user-fault checks unchanged;
   * check and release PASSED;
   * N1 to N15 FIRED (panic);
   * `carry-coverage.py`, then `gen-coverage-justification.py --check`,
     after the final rebase.
