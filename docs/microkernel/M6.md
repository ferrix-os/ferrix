# M6: the shrink, what a `personality=user` kernel leaves out

`docs/MICROKERNEL.md` §8's M6 and §2.1's *What leaves ring 0*. The customer, 2026-11-03: the goal is an
actually tiny kernel in `fast` and `max`, chosen only by compile flags from one source; `desktop` stays
hybrid, `present` stays as it is; code the hybrid uses stays and is **compiled out** of `personality=user`
builds; code no building profile needs may be deleted, through the consultant. Ids: L.device.81-85 and
H.DEV.13's neighbour are not needed; M6 writes **withdrawals** and one gate. Panic code: none. K16 is its
own design (`K16.md`).

**Where it stands:** design for review, 2026-11-04. No code.

## 1. The rule

Everything here is `#[cfg(not(ferrix_personality = "user"))]`, or a `#[cfg(ferrix_personality = "user")]`
stub of the same interface with nothing behind it, so `present` and `desktop` compile the same text: the
same symbols with the same sizes (M5-LIFT §8's evidence, re-run). No boot option, no run-time test chooses
any of it.

of text today with checks on. A row's *guess* is what that row removes.

**Not cut**, §2.1's list holds: trap and system call entry; spaces, VMOs; threads, jobs, quotas, the scheduler;
handles, channels, ports, events, timers; interrupts, the IOMMU, I/O mappings, pins and quarantine; the device
registry; SMP and the speculation defences; restricted mode; audit; power-off and reset; clocks and the time
page; entropy; the first-image loader; the debug log and panic path.

**Discovery, cut to §2.1's list.** `discovery/{acpi,firmware,board,tree,pci}.rs` stay: memory, processors,
interrupt controllers, timers, IOMMUs, PCI host bridges. `firmware.rs`'s framebuffer lending stays while the
display server has no other way to it. Whatever a `Finder` no longer finds is a board row, not a silent loss: a
line per finder in the boot line `devices`.

## 3. The gate: `check-item-boundary.py` on `fast` and `max`

Today it validates those profiles statically and says "once buildable". M6 makes it hold **now**, for the shape:

1. **No load file reaches ring 0.** It walks the module tree from `kernel_core.rs`, `kernel_item.rs` and `main.rs`,
   evaluating `cfg` under each profile's flags (`ferrix_personality`, `ferrix_load_built`, `ferrix_fs`,
   `ferrix_linux_abi`, the rest the file declares), and **fails if any reached file is in the `load` ring** or is on
   §2's list. An unevaluable `cfg` fails closed.
2. **The crate.** `ferrix-kernel-load`, `ferrix-kernel-settings`, `ferrix-fbtext`, `ferrix-qr`, `ferrix-smbios` are in
   no `cfg` arm a `personality=user` build takes, read from `Cargo.toml` and `main.rs`.
3. **The image.** mk-lift's symbol check (`nm` finds no `ferrix_kernel_load`) with the listed crates added, over the
   built kernel, in `xtask check`'s `personality=user` build.
4. **Size, a ratchet.** The ring-0 product lines under each profile, by the same walk, printed by `--report` and
   held by a baseline that only falls for `fast` and `max`. This is what mk-base's comparison reads.

**Control**, `gate.sh control --expect-host`: a planted load file, `mod planted;` in `kernel_core.rs` with the
file listed in the load ring, fails it under `fast` and `max`. A second: a `#[cfg(ferrix_personality = "user")]` on
`pub mod screen` that keeps it built. A third: `use ferrix_kernel_load as _;` in `main.rs` under no `cfg`.

## 4. Coverage and the moves

Nothing moves in `present`: it builds the same text. So §6.2's *Moves* owes no carry for the cut itself; the
stubs are new files under `personality=user` only and count there. The stub of `console::screen` is one file
replacing another by `#[path]`, so that no `cfg` litters the callers. Boot lines on `present` and `desktop`
are identical, by the four boots. `check-load-ring.py` unchanged.

A `personality=user` kernel's coverage is M7's, measured afresh at the flip.

## 5. Questions

* **Q1.** `console/input.rs` staying until M8: acceptable, against M6's gate naming "the console's screen and input"?
  My view: yes, with the gate's list naming it from M8.
* **Q2.** Deleting anything from the source: I propose **nothing yet**. `ferrix.devmgr=init`'s path and `DEVMGR_START`
  are used by `present`.
* **Q3.** §3.1's walk evaluates `cfg` in Python. Is a tool that reads `cfg`s itself acceptable as T2, given §3.3 checks
  the real image? My view: yes, the image check is the evidence and the walk the fast early answer.
