## 2. `netd`: the switch

MICROKERNEL §2.3 says the network stack cannot live in a partition's personality, because it serves every partition. I propose narrowing what has to be shared: **the wire, not the stack.**

**One machine outside (customer, 2026-11-04, docs/backlog/DECISIONS.md; it replaces the consultant's default).** `netd` speaks the net ring on both sides. To the real driver it is what the kernel's core is, with `ferrix_netring::kernel` (the same crate, as `ferrix-blkclient` is for blocks). The first partition's `eth0` goes to the wire and nowhere else, with the wire's own MAC: one address, one DHCP client, its own. With more than one partition there is also an internal link that has no way to the wire: `int0` in the first partition, `int0` as the only interface of each further one, each a derived, locally administered MAC, frames moved by destination MAC, broadcast and multicast to the link's others. The first partition's ARP for an internal address cannot reach the wire, since `int0` is a different interface (W.3). A further partition reaches nothing outside; whether it may ever get out through the first partition is a morning question, and failing closed is the default (W.2). `linuxd`'s `interfaces/net_ring` core, the IP stack, sockets, netlink and netns **do not change**: each partition has a stack of its own over what looks like a NIC.

Why not a socket server: a stack shared by partitions means a socket protocol carrying every semantic of `net/socket.rs` (readiness, ancillary data, netlink, packet sockets, netns), and a QM partition's load inside a stack another partition depends on. A switch has one data path, no per-socket state, a bounded table, and is small enough to certify. What it gives up is what the customer chose: a further partition has no way out, and if it ever gets one it is through the first (morning question, W.2).

**Wiring.** Under `personality=user` with `netd` present, devmgr's `NET_RING_CREATE` goes to `netd`'s core channel, by the same flag as CO.4's block one. `netd` then opens one ring per partition with `CORE_OPEN`-shaped requests on each partition's cores channel, as devmgr does, naming a virtual location. `linuxd` is not told the difference. Started and restarted by devmgr, in the drivers' job, with its driver of the wire (N.5); the manager speaks no protocol to it. With a further partition, `netd` opens two rings on the first's channel, `eth0` and `int0`.

**Interference.** One thread. Each partition has its own ring, its slots and a frame budget per scheduling turn, so a partition flooding the switch cannot starve another's queue beyond its share; what it does cost is `netd`'s and the wire's time, stated, with K9 not built. A safety partition does not use `netd`: §2.3's rule (native drivers devmgr assigns directly) stands.

**Copies.** A frame is copied once more each way, driver slot to partition slot. Measured against today in `bench-rows`' network row; a cost the comparison must show. Slots are volatile on both sides and copied before use, as the rings require.

**Restart.** `netd` killed: the driver's ring closes, the driver is restarted by devmgr, and each partition's core sees its ring close: the parked-interface rule (*an interface outlives its driver*) already says what a dead driver's interface does. So a `netd` restart looks to a stack like a cable pulled, and the kill row is that. Who restarts `netd`: devmgr, at most three times (N.5), each new one given duplicates of the further partitions' channels.

**Evidence.** `test-net` unchanged with `netd` in the image. A kill-and-restart row: pings stop and come back, sockets survive. A two-partition row: the second partition reaches the first on `int0` by address, has no `eth0`, and gets nothing from outside by ping or DHCP. Host tests of the forwarding table and a fuzz target on a frame's header hold what a row cannot see: a wire frame to a further MAC reaches nobody, a further partition's frame never reaches the wire (W.4, controls on the landing's ref).

## 3. A second Linux partition

The kernel's `linuxd_start` makes one region and one `linux` job. Generalised: the description gets a row per Linux partition (role `linux`, memory share, whether it holds the devices' cores and the file server's client channel). **One partition holds the device cores and btrfsd's channel**, as now; the others hold a tmpfs root from the initramfs and, with §2, a network interface. That is less than "several partitions", and the row says so.

The row: two partitions; the second's `linuxd` is killed; the first's programs carry on and its job is unaffected; the second's job ends. Then the reverse, with what the first's death costs stated (the cores go with it, §5). `BootPage` is already per region; memory is split by the description instead of the fixed `free / 8 * 5`. The panic and console: each `linuxd` holds a debug log handle, rate budget per holder (BA.6), and only one reads the console.

K12's reservation is what makes one's memory safe from the other's; until K12b is on the branch the row shows the kill and not memory isolation, and says so.

## 4. The console server

**The console's input stays in ring 0 under `personality=user`, for now (N.12, ledger 6238).** The serial line is the kernel's own console under D3, kernel-owned: its registers and its line are never minted, so `devmgr` has nothing to give a server. A server could only have input by the kernel taking those from itself, for a panic's output too, or by forwarding each byte to it over a channel, which moves no code out of ring 0: the ISR and its ring stay, and a queue is added. So no server is drawn. `linuxd` reads the bytes with its `READ` handle on `Object::Console` (`first_rows.rs`). What this leaves in the shape is `console/input.rs`, the ring and its interrupt, which M6's list and `check-kernel-shape.py`'s report count; a keyboard from a USB driver is not this file. MICROKERNEL's M8 row keeps it as named, and a server is a later design if a board's console is not the kernel's.

## 5. The device servers: not tried

Display, render, input, audio and chardev cores touch program memory, dma-bufs, `mmap` of device memory and `poll`, through `devfs` (46 call sites), `syscall/fd.rs` (16) and `syscall/memory.rs` (8). Each is a protocol like §3 of `BTRFSD.md` with mapping semantics in it. That is days of work for each, with compositor rows as the judge. M8's row stays open for them, and until they move the partition holding them is the only one with a screen. A partition's death then costs the desktop.
