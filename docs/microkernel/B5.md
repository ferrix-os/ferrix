`docs/MICROKERNEL.md` §6.2, B5, and stages M2 and M3: *each id verified only from
load-ring checks is re-homed to a check in a core or item file with its negative
control fired again; a new `xtask check` step fails when a core or item id is

## 2. The step

`tools/common/check/check-evidence-homes.py`, in `cargo xtask check` as "evidence
homes", in CI, `TOOLS.md` entry (F-19, T2). It uses `check-item-boundary.py`'s
classifier. It fails when an id's every `Verifies:` tag in `src/kernel/src` is in a
load-ring file and the id is not on `tools/common/data/evidence-orphans.json`;
when a listed id has a home (stale); and when a listed id has no tag left (lost
its check, ledger 5782 (2)). So the list only shrinks, and only by a check that
exists. A second list, `raised_only`, holds the §1 ids the same way, so a tag moved
into a raised file leaves no id unaccounted for (5782 (1)). M3's gate is an empty
first list, or class C's marked entries until `personality=user` builds.

Scope, stated in its head and in `TOOLS.md`: kernel source tags only; an id whose
only check is a host test or an xtask row is outside it and argued apart.

**Controls.** (1) `--self-test`, run by `xtask check` with the step: a tag moved
into a load check makes an orphan, a stale entry fails, a deleted tag fails, a tag
moved into a raised file fails off the ratchet. (2) Through `gate.sh control
--expect-host`, on the step itself: a `Verifies:` tag for a core requirement with no
kernel tag planted in a load-ring check, and a listed id taken off the list (a move
of a tag out of a core file is two edits, which `gate.sh control` does not make: the
self-test holds that case). (3) A `Verifies:` tag for an id with no kernel tag planted in a raised file
(`object/check.rs`) fails off the ratchet (ledger 5866 (a)). FIRED logs cited at
the landing. `--report` also says how many core and item requirements have no kernel
tag, so "argued apart" has a number (373 today, counting units in kernel files only: an item crate's units, `ferrix_btrfs_write`'s among them, are not in it).

## 3. What re-homing is

An id leaves the list when, in one landing: a check in a file of the core or item
ring (not raised into the load's crate) verifies the id; its whole statement is
proved at that check (SP-3's rule, CONVENTIONS); the requirement's `criterion` is
restated to name the new check; a negative control sabotaging the **product** code
the statement is about fires it through `gate.sh control --expect` (x86-64 KVM, the
arch's own boot for an `L.aarch64`/`L.armv7a` id); and the old tag stays where it is
for `present` and `desktop`, since the load's check still runs there. A control
may be shared by the ids one sabotage breaks, and is cited for each.

Commits follow SP-3: per-commit check-list, no product change. Where re-homing shows
a statement names Linux-only behaviour while its unit is kernel code, the statement
is restated for the kernel's half under review, not stretched.

The checks: `user/rehome_check.rs` (space and VMO), `object/rehome_check.rs` (quota,
job, process core), `trap/rehome_check.rs`, `sched/rehome_check.rs`, each run by a new
stage function in the check's own stage, one boot line each. Names are final at code.
They build in core's crate, so the crate boundary itself proves they name no load.

## 4. Three classes

**A, the unit in kernel terms.** The statement is about a core or item function, and
the check can call it with kernel objects alone: `AddressSpace`, `Vmo` over a check
`PageSource`, `Job`, `Quota`, the trap filter with frames of its own.

**B, needs ring 3 without Linux.** The statement is about what a store or a trap does
from user mode. Needs a **check host**: `object/check_host.rs`, a core `Host` with
no Linux `Process`, a small stub mapped by `first_image`/K2, entered through the
architecture's way in. It is what the raised files need too (§1), and `linuxd`'s
tiny boot needs a native process type anyway (K11, mk-restricted). Lands after K15.

**C, leaves with the personality.** Every unit is compiled out of `personality=user`,
or its statement is the Linux ABI's. Under BUILD-FLAGS.md rule 7 ("a requirement that
holds only under some flags says so, and its check runs in those profiles") its load
check stays its evidence in `present` and `desktop`, and in `fast`/`max` the id does
not apply; `linuxd` and `btrfsd` carry the behaviour at M5, by their own rows.
Proposed mechanism: the requirement gains `attribute profiles = ("present",
"desktop")`, the step treats such an id as no kernel orphan, and the step checks
the attribute's claim: **each unit must sit under `cfg(not(ferrix_personality =
"user"))`** once `personality=user` builds (mk-lift), reported until then. Q1.

Totals on 2026-11-03: **A 83, B 26, C 26**. Now: **66 done, B 43, C 26**: seventeen of
class A's statements turned out to need ring 3 or the personality, each row saying why
(§6); a tag is not stretched over a statement its check does not prove. Some of those rows
do not wait on the check host, and each says what it does wait on (ledger 6142 (10)).
