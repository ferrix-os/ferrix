## 1. What it is

A thread of a shared process (K11) has two modes. In **normal mode** it runs
`linuxd`'s code, on a root that maps the shared region and the process's
restricted space, and calls the kernel through the shared handle table. In
**restricted mode** it runs a Linux program's code on a root that maps the
restricted space alone. `RESTRICTED_ENTER` goes from the first to the second
with a context the kernel has checked. A system call, a fault the kernel cannot
resolve, or a kick comes back: the same kernel thread, with no switch of thread,
no scheduler decision and no channel message, resumes `linuxd`'s code at the
instruction after its `RESTRICTED_ENTER`, with the reason in its registers. To
`linuxd` the whole thing looks like one system call that takes a long time.

Zircon's restricted mode is the shape; the differences are that the context
lives in the kernel rather than in a bound VMO (§2.3 says why) and that an exit
returns as the call's own return rather than through a vector table.

Not in this mechanism: what a Linux call means, signals, `fork`, `exec` and
`ptrace` (all `linuxd`'s, on K2 and on §2's calls); the two handle tables and the
two roots (K11).

## 2. The interface

This section is the contract `linuxd` is written against, and `rt`
(`ferrix_native::restricted`) wraps it. All eight calls are in the native range
and answer on the native ABI's usual terms unless a call says otherwise. **All
but `RESTRICTED_KICK` act on the calling thread alone**: there is no call by
which one thread reads or writes another's context; a thread that wants to know
another's (`ptrace`, a core dump) asks it, by a kick.

### 2.1 The calls

| Number | Call | Arguments -> result | Mode | Refused |
|---|---|---|---|---|
| 0x1090 | `RESTRICTED_ENTER` | `(context: *const RestrictedContext, options)` -> the exit, §2.2; options 0, `ENTER_ALL_CALLS_EXIT` or `ENTER_COPY_MISS_EXITS`, either or both, sticky until the next entry; an unknown bit is `INVALID_ARGS`, before anything is taken | normal | `BAD_STATE` not a thread of a shared process, or from restricted mode; `INVALID_ARGS` the context fails §4, and nothing has changed; `INVALID_ARGS` unreadable pointer; `NO_MEMORY` the first entry's record |
| 0x1091 | `RESTRICTED_RESUME` | `(value)` -> the exit, §2.2 | normal | `BAD_STATE` no context is held, or the last exit was neither `SYSCALL` nor `SYSCALL_COMPAT` |
| 0x109D | `RESTRICTED_CONTINUE` | `()` -> the exit, §2.2 | normal | `BAD_STATE` no context is held, the last exit was neither `KICK` nor `FAULT`, or the saved `rip` is not a user address (a program's own jump past the user half: `IRETQ` would fault on it in ring 0). Re-enters the held context exactly as it stands, otherwise unchecked, because nothing has changed since the processor saved it. The way back after a `KICK` or `FAULT` exit where `linuxd` changes nothing |
| 0x1092 | `RESTRICTED_KICK` | `(thread: handle)` -> 0 | either | `ACCESS_DENIED` the handle lacks `SIGNAL` (`Rights::SIGNAL`, bit 12, new); `WRONG_TYPE` not a thread; `BAD_STATE` the thread has ended, or is not a thread of a process with a region |
| 0x1093 | `RESTRICTED_CONTEXT_READ` | `(out: *mut RestrictedContext)` -> 0 | normal | `BAD_STATE` no context is held |
| 0x1094 | `RESTRICTED_VECTORS_READ` | `(out: *mut u8, length)` -> bytes | normal | `BAD_STATE` no context; `INVALID_ARGS` length under `restricted::VECTORS_BYTES` |
| 0x1095 | `RESTRICTED_VECTORS_WRITE` | `(in: *const u8, length)` -> 0 | normal | `INVALID_ARGS` as §5.2; `NO_MEMORY` the record, before the first entry; `BAD_STATE` from restricted mode |
| 0x1096 | `RESTRICTED_COPY_WINDOW` | `(start, end, landing)` -> 0 | normal | `INVALID_ARGS` the range is not in the shared region, or the landing is not inside it and below `USER_VIRT_END` |

A call in the table marked *normal* made from restricted mode is answered
`BAD_STATE`; the program learns nothing and the thread stays in restricted mode.
`RESTRICTED_RESUME` writes `value` to the program's result register (`rax`, `x0`)
and goes back in: it never reads the context from memory, which is what makes it
the fastpath's call (§7). `RESTRICTED_ENTER` is the one for every other case: the
first entry, and any change of register (a signal, `sigreturn`, `exec`, a `fork`
child's first run, `ptrace`, the restart of a call).

A thread holds no context until its first successful `RESTRICTED_ENTER`.
`RESTRICTED_VECTORS_WRITE` before that sets what the first entry starts with
(for a `fork` child); otherwise a first entry starts from the vector registers'
initial state (`FNINIT`-equivalent `MXCSR`/FCW, every register zero; on AArch64
`FPCR`/`FPSR` zero), never from `linuxd`'s.

`RESTRICTED_CONTEXT_READ` writes the context **normalised**: `rflags` as K4's
`supervised()` gives it (only `FLAGS_RESTORABLE`, `IF` and bit 1), on AArch64
`pstate` as NZCV alone. The held context itself stays raw, which is what
`RESTRICTED_CONTINUE` re-enters. So a program that set `TF`, `NT` or `ID` by `popf`,
or took a fault that pushed `RF`, gives `linuxd` a read that `RESTRICTED_ENTER`
accepts unchanged, unless `rip` or `rsp` lies outside the window or a selector is
not pinned. **`INVALID_ARGS` on a value the program chose is that program's
`SIGSEGV`, never the partition's death**: `linuxd` handles the refusal as Linux
handles a bad frame.

`RESTRICTED_COPY_WINDOW` names the code that may fault on a program's memory: §2.5.

### 2.2 The exit

`RESTRICTED_ENTER` and `RESTRICTED_RESUME` return only by an exit or a refusal.
On return, `rsp`/`sp` and `linuxd`'s callee-saved registers are as they were at
the call (`r12` on x86-64 and `x9` on AArch64 excepted, the reason's), its FS and GS
bases and selectors (`TPIDR_EL0`) are its own, and the following hold the exit. **A refusal is told from an exit by the reason
register**: `rt` zeroes it before the call, a refused call leaves it zero and the
status in the usual return register, as any native call. The other registers the table does not name are
not preserved.

| | x86-64 | AArch64 |
|---|---|---|
| **reason** (`restricted::Reason`; 0 means the call was refused) | `r12` | `x9` |
| number / vector | `rax` | `x8` |
| word 0 to 5 | `rdi`, `rsi`, `rdx`, `r10`, `r8`, `r9` | `x0` to `x5` |
| clobbered as well | `rcx`, `r11` | none (`x10` to `x18` as across a function call) |

So a system call's number and six arguments arrive in the registers the program
put them in, and nothing has to be moved. What a refused call leaves in the
return register is the same `rax`/`x0` a native call answers in.

| Reason | Value | number / vector | word 0 | word 1 | word 2 | word 3 | word 4 | word 5 |
|---|---|---|---|---|---|---|---|---|
| `SYSCALL` | 1 | the program's number, whole | argument 1 | 2 | 3 | 4 | 5 | 6 |
| `SYSCALL_COMPAT` (x86-64 only: `int $0x80`) | 2 | `eax`, zero extended | `ebx` | `ecx` | `edx` | `esi` | `edi` | `ebp` (each zero extended) |
| `FAULT` | 3 | the architecture's vector (x86-64) or `ESR_EL1.EC` | error code, or the whole `ESR_EL1` | fault address (`CR2`, `FAR_EL1`), zero where none | `FaultKind` | program's `rip`/`pc` | program's `rsp`/`sp` | 0 |
| `KICK` | 4 | 0 | 0 | 0 | 0 | program's `rip`/`pc` | program's `rsp`/`sp` | 0 |

`FaultKind`: 0 not a memory fault; 1 no mapping (`SEGV_MAPERR`); 2 protection
(`SEGV_ACCERR`); 3 past the end of an object or a pager failure (`SIGBUS`,
`BUS_ADRERR`); 4 memory poison (`SIGBUS`, `BUS_MCEERR_AR`, with word 1 the
address). A page fault the kernel *can* resolve never exits (a resident page, a
demand-zero page, a copy-on-write copy, a pager's supply: K3): an exit is a
fault the program would die of, or be sent a signal for, under Linux. A
`FAULT` exit leaves the program's context as the fault left it, at the faulting
instruction; `linuxd` chooses what happens next and says so with
`RESTRICTED_ENTER`, or `RESTRICTED_CONTINUE` to retry the instruction, since a
`RESTRICTED_RESUME` after a fault is refused. A program's `popf` with `TF` set is its
own: the `#DB` exits `FAULT` with vector 1, though `TF` stays refused in a context
handed in (§4), so `ptrace`'s single step waits for a review of its own.

A native number from restricted mode (0x1000 to 0x1FFF) is **not** an exit: the
kernel answers it against the private handle table and returns to the program
(`MICROKERNEL.md` §2.4), with one exception, `PORT_FD` (0x101B), which exits as
`SYSCALL` with that number. Every other number exits as `SYSCALL`, a value with high
bits set included: only 0x1000 to 0x1FFF is native. `int $0x80` always exits, a native
number in it too.

**Which native numbers.** `nr::from_restricted`, an exhaustive match, gives every native
call one row (*answered from restricted mode*, *exits*, or *refused, normal only*); a call
with no row fails the build. Refused: the restricted-mode and region calls, `PROCESS_BOOTSTRAP`
and `DEVMGR_START`. The calls that need no handle, so that rights do not bound them, are
answered as for any native process, each bounded as it is there: `CHANNEL_CREATE`,
`PORT_CREATE`, `VMO_CREATE`, `TIMER_CREATE`, `SPACE_CREATE`, `PAGER_CREATE` (objects charged to
the job), `ADDRESS_WAIT`, `_WAKE`, `_REQUEUE`, `_WAIT_ANY` (its own memory) and `CHARGE_TICKET`
(a ticket it adopted). Rights on handles still govern what an answered call
may do, and §2.4's rule of `MICROKERNEL.md` is what the table holds. A K-row's rule
about restricted code (K14's, for one) cites this table.

**`ENTER_ALL_CALLS_EXIT`** (ledger 6268 Q2 (a), 6483). With the option, a system call of this context
exits whatever its number, a native one with its number in the exit's register: nothing is answered by the
table of §2.2. It is what `linuxd` asks for a thread under Syscall User Dispatch, whose program asked that
every call be taken away. It holds until the next `RESTRICTED_ENTER`, across `RESUME` and `CONTINUE`, and it
is read only on a native number's branch, so a Linux number's path does not read it.

**`ENTER_COPY_MISS_EXITS`** (ledger 6326, 6529). `linuxd`'s restricted space is only a cache of its shadow, so a
native call's copy can miss memory the program holds. With the option, an answered call that answers `FAULT`
because its copy missed this thread's own restricted space, and whose row in `nr::copy_miss` is `Rerun` or
`Restores`, exits instead: `Reason::Fault`, the page-fault vector (x86-64) or a data abort's class (AArch64), word
1 the address, word 2 `FaultKind::CallCopy`, which the kernel sets and `linuxd` never infers. The context is the
program's registers as at the call, the number included, `rcx` and `r11` as `SYSCALL` leaves them and on AArch64
`pc - 4` and `x8`; the exit is decided at the dispatcher's end, before anything of the answer is written, with no
lock held and nothing done from inside the copy. `CONTINUE` runs the call again under `may_continue`, attention
looked at on the way as on any return, so a kill ends a thread that repeats, and the repeat costs that thread
only. A miss in a space the call names by handle is that space's `FAULT` and never exits, and a failure the call
goes on past (`channel_read`'s best-effort fault-in) is forgotten. If the shadow refuses the page, `linuxd` answers
the status: the context past the instruction, `FAULT` in the return register, by `RESTRICTED_ENTER`; never a
signal. The option holds until the next `RESTRICTED_ENTER`, and with it down the answer is `FAULT` as ever. The
rows are `nr::copy_miss`: `Rerun` no effect before its last copy, or the same effect again; `Restores` gives back
what it took (`Endpoint::unread`, `Port::put_back`); `AnswersFault` everything not shown to be one of those. A
match with no default, so a number with no row does not build. A thread with `ENTER_ALL_CALLS_EXIT` up never
reaches this, since a native number exits first. The IPC fast path's words are registers: it has no copy to miss.
Its row on `personality=user` and real init's negative control are owed by M5's landing (6529 Q5).

The `Rerun` rows, one line each (6529 P2, 6667). `VmoRead`, `VmoGetSize`, `VmoDigest`, `ObjectId`, `ProcessStatus`,
`JobGetQuota`: they read, and their one copy out is last. `VmoWrite`: the same bytes again, the same effect.
`ChannelCreate`: its out copy fails after the ends are made and it gives them back, so a rerun makes a new pair.
`ChannelWrite`: bytes and handle values are copied in before anything is taken or pushed. `ObjectWaitOne`: the
deadline is read before the wait, and the observed copy after it changes nothing; run again it waits again.
`ObjectWaitAsync`, `PortQueue`: the key or packet is read before anything is registered or queued. `ProcessCreate`:
the name is copied in before the process is made. `SpaceRead`: the target goes through a bounce page, whatever it
commits being the same commit again. `HandleDuplicate`, `HandleReplace`, `HandleClose`, `PortCreate`, `VmoCreate`,
`ProcessStart`: no user copy, so they do not miss. `ChannelWriteRead` is `AnswersFault`: it sends first and does
not unsend.

The note's guard, the thread's own restricted space alone: no path reaches it with another space today, since a
by-handle call reads through `_present` copies and `space.fault`, which never reach `resolve`'s faulting arm. It
is shown with a plant, not a case (ledger 6677): `L.user.191`'s criterion names the tags.

### 2.3 The context

The kernel holds the program's context, in the thread's own kernel memory, from
the first entry on. That is deliberate, against Zircon's mapped state page: a
page `linuxd` can write is one that every exit and entry has to treat as hostile
and copy twice, and the fastpath's validity rule (`MICROKERNEL.md` §3: "the
context the kernel holds is unchanged apart from the result registers") only
means something if the kernel holds it. `linuxd` sees it through
`RESTRICTED_CONTEXT_READ`, one more native call on the slow paths that need it
(a signal, a `fork`), and never needs it on a `getppid`.

`RestrictedContext`, `repr(C)`, every field a `u64`, in `ferrix_native_abi::restricted`:

```text
x86-64 (232 bytes)                         AArch64 (288 bytes)
  r15 r14 r13 r12 rbp rbx                    x: [u64; 31]    x0 to x30
  r11 r10 r9 r8                              sp              SP_EL0
  rax rcx rdx rsi rdi                        pc              ELR_EL1
  rip rsp rflags                             pstate          SPSR_EL1, flags only
  cs ss ds es fs gs                          tpidr           TPIDR_EL0
  fs_base gs_base                            tpidrro         TPIDRRO_EL0
  tls: [u64; 3]   GDT slots 12 to 14 
```

Which fields a program can change by itself and which the kernel owns is §4. The
vector state is not in the context: it is larger, `linuxd` rarely wants it, and
§5's lazy rules need it apart.

`restricted::VECTORS_BYTES` is the size of §5.2's image: 832 on x86-64 (the
standard-form `XSAVE` area for x87, SSE and AVX that `UserState` already keeps),
528 on AArch64 (`V0` to `V31`, `FPCR`, `FPSR`).

### 2.4 The kick

`RESTRICTED_KICK` raises the target thread's kick mark and, if it is running on
another processor, interrupts it. The rule, on every path:

* In restricted mode, running: an exit with `KICK` before it runs another
  instruction once the interrupt is taken.
* In restricted mode, in a native call of its own that blocks (`channel_write_read`'s
  receive half too): the wait ends with `INTERRUPTED`, that goes in the context's result register, then the same
  exit. A call that does not block completes, then the same exit.
* In normal mode: nothing now. Its **next** `RESTRICTED_ENTER` or
  `RESTRICTED_RESUME` exits at once with `KICK` and runs no instruction of the
  program; a `RESTRICTED_RESUME`'s value and an `ENTER`'s context are taken first
  and are in the held context, so a kick loses no result. `linuxd` goes back
  with `RESTRICTED_CONTINUE` after it has looked at its signals. A normal-mode wait is
  not interrupted: `linuxd` wakes its own threads by its own means.
* The mark is raised through `sched::work`'s post, so a kick has that path's
  ordering, its interrupt and its look on the way out, on a `--smp 2` check beside
  the one-processor one, with a board row owed for real multi-core Arm.
* A mark is one bit. Any number of kicks before the exit are one exit, and the
  exit lowers it. So a thread that takes a `KICK` exit looks at its signal queue
  after, and a kick made after that look gives another exit.

A kick to a thread of another process is allowed by the handle: `linuxd` holds
every thread's handle in the shared table. A program gets none unless `linuxd`
gives it one, and K17's refusals apply to a thread handle as to a process's.

### 2.5 `linuxd`'s copies, and what a normal-mode fault does

`linuxd`'s normal root maps the restricted space, so a copy to or from a program
is a load or store in `linuxd`'s own code, with no call at all (`MICROKERNEL.md`
§2.2's cached `read`). The program chooses those addresses, so that copy can fault
on a hole. `RESTRICTED_COPY_WINDOW(start, end, landing)` declares, for the whole
partition and replacing the last declaration, the code range that does such
copies:

* A page fault in **normal mode**, at an address in the restricted half, that the
  kernel cannot resolve after K11's `sync_top`, ahead of K4's supervisors, with `rip`/`pc` in `[start, end)`, resumes at `landing`
  with the fault's `FaultKind` in `rax`/`x0`. Nothing else is written. `rt` gives
  the routine (`copy_from_program`, `copy_to_program`), a loop in a linker
  section, and `linuxd` calls it. A window is a pair of addresses in the shared
  region, the landing checked inside it, only `rax`/`x0` written, and its only power
  is over a fault on the restricted half.
* Any other fault in normal mode, a fault in the shared region and a fault
  outside the window alike, is a fault of `linuxd` and goes as any native
  process's: K4's supervisor, and past it **the region's job is killed, not one
  process**, failing closed: `linuxd`'s state is the partition's, so one process of
  it faulting has left it in doubt. It is never an exit: `linuxd`'s own fault cannot
  be turned into the program's (K13).

K2's `SPACE_READ` and `SPACE_WRITE` still work and need no window, at the price
of a call.

## 3. How the kernel does it, on x86-64

**The mode** is one per-task field, written with interrupts masked, mirrored in
one per-processor byte (`PerCpu::restricted`, set by `restore_user_state`'s
caller at every switch and by every flip), which is what the entries read. Only
a task of a shared process can ever have it set.

**What the thread holds** (`RestrictedState`, allocated by the first entry,
charged to the process's job, freed with the task): the held context; the normal
mode's `SyscallFrame` as its `RESTRICTED_ENTER` or `RESTRICTED_RESUME` saved it;
the other mode's `UserState`; the kick mark; and the last exit's reason.

**Enter** (the general path, in `answer_here`'s place on `SYSCALL`'s entry, so it
owns the frame). Interrupts open: copy the context in and check it (§4), or the
held one plus `value`. Interrupts masked: refuse if the kick mark is up (taking
the exit instead, below); save the frame as the normal mode's; swap the user
state (`save_user_state`, `restore_user_state`: bases, selectors, descriptors,
vector state); set the mode; install the restricted root (K11 §3), which is the
flip's root write; then write the context into the frame and leave. It leaves by
`SYSRET` when it can: 64-bit `cs`, `rcx == rip`, `r11 == rflags`, which is every
context that a `SYSCALL` exit saved and nothing changed. Otherwise by `IRETQ`
through `ferrix_resume_trap_frame`, which restores all sixteen, and which a
32-bit context always takes (`docs/I386.md`'s reason).

**Exit** is rewriting a frame, on every path: the entry saved the program's
registers on the kernel stack as it always does; the exit copies them to the held
context, then replaces the frame with the normal mode's, with the exit's registers
written over it, and goes on down the entry's ordinary way out to `SYSRET` or
`IRETQ`. Its steps with interrupts masked: copy the registers out, lower the mode,
swap the user state, barrier (§6), install the normal root, write the frame.

| Way out of restricted mode | Where it is taken |
|---|---|
| `SYSCALL`, a Linux number or `PORT_FD` | first thing in `ferrix_syscall_entry`, on the per-processor byte, before the fast path and the filter: a restricted thread's Linux number never reaches `filter_system_call` or the personality |
| `SYSCALL`, a native number | the same test: not an exit; dispatched with the mode still up, so K11's table and K11's route pick the private ones, then `leave` as any call. `vectors_die_in`'s contract (AoU-25/27) is **not** applied: the program made a real call and keeps its registers under Linux's rules as under the native rule; §5 |
| `int $0x80` | the vector's own test in `x86_64/mod.rs`, ahead of the Linux compat decode. A 64-bit program's `int $0x80` is `SYSCALL_COMPAT` as well, as Linux treats it |
| `SYSCALL` from compatibility mode (AMD, `CSTAR`) | no exit: `ferrix_syscall32_stub` answers `ENOSYS` with nothing touched, as today |
| `SYSENTER` | no exit: `IA32_SYSENTER_CS` zero makes it `#GP`, which is the `FAULT` below |
| A resolvable page fault | no exit: `handle_page_fault`'s ordinary resolve, in the restricted space, as for any program |
| Any other fault, exception, `int3` or a program's own `#DB` from ring 3 | `trap::user_fault_as`'s first test, ahead of `exception::raise`: the frame is rewritten instead of a signal being raised. K4's supervisors are not asked: a restricted program's supervisor is `linuxd` |
| A machine check from ring 3 | the existing `machine_check_marked` branch, then the same test, `FaultKind` 4 |
| An interrupt | no exit, unless the kick mark is up on the way back: a preemption is an ordinary preemption in restricted mode, and the root it finds at the switch back is the restricted one, K11 §3 |
| A kick | the look in `leave` and the trap path's way back, ahead of `return_to_user`'s, with interrupts masked; so a kick IPI that arrives after the look finds a thread back in ring 3 and exits from the interrupt |

**The way back from anything** still runs `attention_due`, going in included: after
the context's copy, with interrupts masked again, and before the flip, so that a kill
posted while they were open takes effect here and not at the next tick: a process ended from
outside ends here, as every process does, with the thread's held context simply
freed. No signal is ever delivered by the kernel to a restricted thread: the
Linux personality's `return_to_user` is not called with a restricted context
(`attention_due` is answered for a shared process by a kill alone).

**Not on any existing path's cost, and measured so.** `ferrix_syscall_entry` gains
one byte test and an untaken branch at its top; `trap::user_fault_as` and the
`int $0x80` path, where no hot row runs, one test each; the claim is held by
`null-getppid` on `present`, before and after. `present`'s and `desktop`'s behaviour
and boot lines are otherwise unchanged, but for §10's new boot line, which carries §6's
rule within it. The byte says what one thread is doing, never what shape the kernel
is: **no boot option and no run-time test chooses a shape** (BRIEF, the customer,
2026-11-03). The mechanism is built in every profile with a boot check; `linuxd`
using it is `personality=user`, a compile-time flag, and so are §6's and §7's choices.

## 4. What the kernel checks in a context

`RESTRICTED_ENTER` copies the context once into kernel memory and checks the copy
(no second fetch), through the same functions `rt_sigreturn` uses and with the
same rules (the I2a/I2b rules, ledger 7, 15, 23), with one difference: sigreturn
masks and forces, and **this refuses**. A program's own forged frame gets what it
asked for or a `SIGSEGV`; a `linuxd` handing in a wrong context has a bug, and a
wrong context silently corrected would hide it. Any failure answers
`INVALID_ARGS` and nothing has changed: the thread stays in normal mode with its
held context as it was.

x86-64 (`L.x86_64.260-268`):

* `rip`, `rsp`: user addresses of the restricted window, below the space's
  ceiling (`is_user_address` narrowed to K11's `SHARED_BASE`). In 32-bit code,
  `rip` under 4 GiB: `IRETQ` faults otherwise in ring 0 (`restored_code_selector`).
* `cs`: exactly `USER_CS` or `USER_CS32`. `ss`: exactly `USER_SS`. RPL included;
  a kernel selector is never masked into a user one here.
* `rflags`: bit 1 set; only `FLAGS_RESTORABLE` and `IF` beside. `IF` must be set,
  and **`IOPL`, `VM`, `VIF`, `VIP`, `NT`, `RF`, `TF`, `ID`** are refused. (`TF`:
  the single step is `linuxd`'s to emulate with a breakpoint or to ask for by a
  later review; `AC` is restorable as Linux's `FIX_EFLAGS` has it.)
* `tls[0..3]`: each zero or `gdt::ring_3_segment` (present, S=1, DPL 3, L=0, data
  or readable non-conforming code). The kernel sets them; they are never read back
  from the program, which can only name them.
* `ds`, `es`, `fs`, `gs`: each with `gdt::loadable(selector, &tls) == selector | 3`
  or null. A value `loadable` would turn into null is refused, not nulled.
* `fs_base`, `gs_base`: canonical and user addresses of the restricted window, or
  zero. Non-canonical is `#GP` at `WRMSR` in ring 0.
* A 16-bit `rflags` or a selector field with bits above its width is refused
  (fields are `u64` so nothing is truncated into validity).

AArch64 (`L.aarch64.70-72`): `pc`, `sp` user addresses of the restricted window
(with the architecture's checks of alignment left to the program's own fault);
`pstate` **exactly** NZCV bits and nothing else, so EL0t, AArch64, no `D`, `A`,
`I`, `F`, `SS`, `IL`, `PAN`, `UAO`, `DIT`, `TCO`, `BTYPE`, `SSBS` from the caller;
`SSBS` the kernel keeps as the speculation plan has it. `tpidr` any value, since a
program can set it itself; `tpidrro` zero (§8).

Each rule is a check on a forged context with a negative control (§10).

**After the check nothing is re-read from `linuxd`.** On the fastpath nothing is
read at all. `SYSRET` to a non-canonical `rcx` is excluded by the `rip` check,
and flags and selectors by the rest.

## 5. Vector state

### 5.1 The contract

The program's whole vector state survives every exit: it is the program's
registers, and §9.8 3a's contract and AoU-25/27 bind `linuxd`'s own native calls,
never a Linux program that made none. `RESTRICTED_ENTER` and `RESTRICTED_RESUME`
are declared to `linuxd` as function calls on its vector registers: caller-saved
ones are lost (`MXCSR` and the x87 control word kept, on AArch64 `V8`-`V15`'s low
halves and `FPCR`, `FPSR` kept, as the AAPCS has it). The native-number rule from
restricted mode (a program's own `object_wait_one`, its `port_wait`) keeps the
whole of the program's state too: `vectors_die_in` is by the entry, and not raised
in restricted mode, so a program that made no bargain loses nothing.

### 5.2 The image

`RESTRICTED_VECTORS_WRITE` is held to `restore_fpu`'s rules: `MXCSR` masked by the
processor's mask **refused rather than masked** here; `XSTATE_BV` only bits the
kernel enabled, and at least x87 and SSE's; the reserved bytes of the header zero
(`XRSTOR` faults otherwise, in ring 0). `RESTRICTED_VECTORS_READ` gives the
standard form, written by the kernel, whatever §5.3 has left in the registers.

### 5.3 Eager first, lazy after

The first landing is **eager**: every flip saves and restores with `XSAVE` and
`XRSTOR` through `UserState`. Lazy is a later landing, the fastpath's (§7), under
`MICROKERNEL.md` §3's four rules, each with a check:

(a) the program never sees `linuxd`'s values: on re-entry, if `linuxd` touched
vector state, the program's is restored at once, or the registers are cleared and
the first use traps and restores; (b) AoU-25/27 never applies while the program's
state is still in the registers: a per-thread *unsaved* mark forces the save
before any switch away (a blocking native call by `linuxd`, preemption, migration),
with a check and a negative control that another thread never reads the program's
values; (c) `SPECULATION.md` gains an entry for LazyFP (CVE-2018-3665), argued,
not assumed; (d) "`linuxd`'s call path uses no vector registers" is a compiler
setting with a check over the binary.

The trap used is `CR0.TS` on x86-64 (`#NM`) and `CPACR_EL1.FPEN` on AArch64, set
at exit and only when the mark says the registers are the program's. On LazyFP's
face: with `TS` set a speculated vector read gives the program's own data to
`linuxd`, which already holds every program's memory; the entry's real question
is between two programs, and the switch forces the save (rule b) so nothing
crosses a switch.

## 6. The barrier

`partition_speculation` (`BUILD-FLAGS.md`):

* **`exit`** (`max`; and every build where the flag is `not_applicable`, so today's
  `present` and `desktop` run the boot check with the strong rule). One `IBPB`
  with `IBPB_BRTYPE`'s semantics on **every exit, none on entry**, before any
  instruction of `linuxd` runs; the return-stack refill or ERAPS on the root write;
  `MICROKERNEL.md` §7, ledger 941. `speculation::restricted_exit` issues it and
  counts it per processor. **A check counts exactly one per exit, with a control
  that removes it and fires.** On a processor that reports SRSO_NO, BTC_NO, BHI
  unaffected (`speculation::bhi`, never `BHI_NO` alone), no ITS, and with the
  return predictor cleared at the root switch, the barrier may be skipped: decided
  at boot, printed, failing closed, and nazuna does not qualify. That skip also
  needs the stable toolchain's retpolines over `linuxd`, which do not exist: **it is
  not built in this landing and the IBPB always runs.**
* **`partition`** (`fast`). None at a flip; the barrier at a switch between
  partitions only. The job is marked a speculation domain by its MANAGE holder at
  creation, with its audit record (2026-10-01's rules).

**Between the threads of one process.** T1 preempted in restricted mode and T2 of
the same process resumed in normal mode is an exit by another name: the program's
training reaches `linuxd`'s code and `entered_space` sees one key. So a per-processor
mark says the last thing this processor ran in ring 3 was restricted, set at each flip
and each switch-in to restricted; a switch that brings a normal-mode thread in with the
mark up, under `exit`, issues the barrier and lowers the mark. It has a count check and
a control.

**ERAPS.** The tree says ERAPS empties the return predictor at a `CR3` write that
flushes. With PCID a flip keeps translations, so a kept flip gets the software refill
unless `IBPB_RET` is read as covering it, failing closed. nazuna has no PCID, so its
flips flush; §7's pricing states which case it measured.

**Counted at the issue.** The count is of barriers issued, not of decisions; under TCG,
where a model has no `IBPB`, the check reads decisions and says so on its line.

**`partition` lands only with a boot that runs it.** Until a `fast` boot runs the check,
`exit` is the only rule built into a check that counts.

**Between two programs**, whichever rule: `speculation::entered_space` is keyed on
the *restricted* root of the process being entered, not on whichever root the
processor installs (K11 §3): the flip does not call it at all, so a flip is never
mistaken for a switch of program, and two roots of one process count as one key
(the consultant's note, *Where it stands*, Q5). A switch from one process to
another decides exactly as today's switch decides, on domains. So under `exit` the
full barrier between programs is the existing one; under `partition` the job is a
domain, and only the refill stays.

**AArch64**: the architecture's Spectre-BHB sequence on every exit (`CLRBHB`, or
Arm's loop with its count for the core) unless the core reports history isolation
(`ECBHB`), as §7's rule; CSV2 with distinct ASIDs covers the targets, so restricted
root and normal root have **different ASIDs** (§8). `SSBS` provides SSBD.

The kernel's boot line says which rule and whether the skip applied.

`SPECULATION.md` §3 and the ST's FDP_IFC gain §7's argument, and an assumption of
use says what no barrier does: Spectre v1 gadgets in `linuxd` are `linuxd`'s, which
holds every program's data anyway, and are not claimed.

## 7. The fastpath

`restricted_fastpath` (`BUILD-FLAGS.md`): `on` for `fast`; `off` in `max` until the
fastpath's coverage run, its vulnerability-analysis entry and its own code review
exist, and then `on`. §7's row is measured on an `on` build with the barrier in it,
labelled so. **Not in the first landing; lazy vectors and this section come back to
review before their code: §7.1.** Its shape, so
that the first landing is built to take it:

**The exit** (`SYSCALL` with a Linux number): the entry stub, at its byte test,
branches to a hand-written path. Registers already in the kernel frame are copied
to the held context, or (seL4's trick, a *later* refinement if the measurement asks)
`gs:8` points into the held context in restricted mode so the stub's own pushes
write it. Then `IBPB` under `exit`; a root write; `linuxd`'s frame's callee-saved
registers and `rsp`, the reason, and `SYSRET`. **No scheduler decision, no lock, no
allocation, no dispatch.** It falls back to the general exit, in Rust, on anything
unusual: pending work on the processor, the kick mark, a job over its quota, a
compat context, and the vector mark not saying what the path expects.

**The re-entry** (`RESTRICTED_RESUME`): the same at the other end. Its validity
rule is the plan's: **"the context the kernel holds is unchanged apart from the
result register"**. The kernel knows that, because the only way to change the held
context is `RESTRICTED_ENTER`, which takes the checked path by construction: the
fastpath's call has no pointer to read and no register it copies but one. The check
with a negative control ("a forged context offered through the fastpath is
refused") is two: `RESTRICTED_RESUME` after `RESTRICTED_ENTER`'s own refusal, and
after a `FAULT` or `KICK` exit, each refused `BAD_STATE`, with a control that drops
the last-exit test and fires, and a sweep with hostile `value` (it goes to `rax`
only, and `RESUME`'s flags, `rcx`, `r11` are the saved ones).

**`linuxd`'s dispatch** is a direct call from the point of return in `rt`'s wrapper.
**Nothing global**: no global pages, no TLB tricks (R1), the root switch paid as
seL4 pays it; ERAPS in place of the refill on nazuna. **Rejected and recorded**:
tagging restricted mode with SVM ASIDs (ledger 886), and any call answered in ring 0.

### 7.1 The design for its review (2026-11-04)

**Reviewed: OK IF (1)-(12), ledger 6093, no code until K1's general path has passed.**
The twelve are folded in below where marked, and a dated list closes the section.
Read so far, not a row: the general path, eager, 3,500 to 4,410 ns on a dev kernel and
1,750 ns on one release boot, at load 30 (the `regions` line's `restricted-getppid`,
which `bench-rows` reads). Where that goes is unmeasured; four `XSAVE`-class operations,
two copies of a 1 KiB `UserState` each way, the descriptors and selectors and a Rust frame
copy are reasoning, to be profiled before any lazy code (6093 (10)).

**Exit, on `SYSCALL` with a Linux number or `PORT_FD`.** `restricted::fast_exit` in
`ferrix_syscall_entry`, ahead of anything else, interrupts masked throughout. It takes
the path only if **all** hold, and otherwise falls to the general exit with nothing
changed: the task's work word is clear (no kick, no end, no signal, no `PLACE`);
`sched::nothing_due_here()`; the program's `cs` is 64-bit; the program's four data
selectors and three descriptors are unchanged since the last entry, or both modes' are
all null, read as `clean`, set by the slow path, with the four selectors read from the
processor at each crossing and never from a record (6093 (4)); the vector mark says the
registers are in the expected state. Then, in this order: sixteen words copied to the
held context; `last` set; the bases written by `WRMSR` only where they differ, from
the record; `speculation::restricted_left`'s barrier; `CR0.TS` set; the root write;
normal mode's words copied back with the exit's registers over them; the mode byte
lowered. No lock, no allocation, no scheduler decision, no dispatch.

**Re-entry, on `RESTRICTED_RESUME`.** `restricted::fast_resume`, at the same place, by
number: the validity rule is `MICROKERNEL.md` §3's and needs no check of the context,
since the only write to it is `enter_prepared`'s, from a checked copy, or the
processor's own, and this call has no pointer: `held`, `last` a system call's, the
same conditions as the exit, and the vector mark still *program's*. It writes `value`
to `rax`, saves normal mode's frame, clears `CR0.TS`, writes the root, restores
sixteen words and leaves by `SYSRET`, since `rcx` and `r11` are `SYSCALL`'s own. Every
other re-entry takes the general path.

**Lazy vector state, the mark.** `RestrictedState::vectors`: `Program` means the
registers hold the program's while normal mode runs, `CR0.TS` set. It holds §5.3's
rules so:

* (a) Normal mode's first vector instruction takes `#NM`: `XSAVE` to the program's
  area, `XRSTOR` of normal mode's, `CR0.TS` clear, the mark `Normal`, and retried; so
  it never reads the program's values and the program, on the general re-entry that
  mark forces, never reads its.
* (b) **A switch away with the mark `Program`** (`save_user_state`, every way a task
  stops running: a block, a preemption, a migration) clears `CR0.TS` first, saves the
  registers into the *program's* area, loads nothing, and sets the mark `Normal`; so
  the switch back restores normal mode's as ever and the program's state is in memory.
  AoU-25/27's `vectors_dead` is never applied to it: the check that another thread never
  reads the program's values, with a control that skips this save, is `L.trap.31`-class
  (a free id is taken from the hold). `CR0.TS` is a processor's, not a task's: the switch
  leaves it clear for whoever comes next.
* (c) `SPECULATION.md` gains LazyFP's entry: speculation past `#NM` in normal mode can
  read the *same program's* registers, in a thread whose `linuxd` holds that program's
  memory by design, and nothing crosses a switch by (b). Between two programs the
  registers are never left: the mark does not survive a switch, so no other program's
  state can be in them. On a processor LazyFP does not reach, the same holds.
* (d) `linuxd`'s call path uses no vector registers: its crates are built for the
  soft-float target, as this kernel's and `rt`'s are, and `tools/common/check` greps the
  linked `linuxd` for vector opcodes outside the routines that declare they use them
  (they trap, and cost, but are correct). That check is `mk-lift`'s image's; until
  `linuxd` exists the check program's normal mode holds it.

**The kernel's own use.** `XSAVE` and friends with `CR0.TS` set would fault in ring 0, so
every kernel path that touches vector state (`save_user_state`, `capture`, `reset`,
`VECTORS_READ`, a signal frame's) goes through `materialise`, which takes the mark down
first. The native-call and trap entries do not look at it.

**The exit barrier and the refill.** `exit`: the `IBPB`, in this path, counted as the
general one is. On a kept flip (PCID) the refill is explicit. `partition`: none at a flip, (11) below. Neither is left to a decision that can be mistaken: the
const is compile-time.

**The twelve, as this design reads them (6093).**

* (1) **A dead task.** `CR0.TS` is cleared on every switch, a dead previous included, ahead of

  Case and control.
* (2) **The barrier cannot stop.** `fast_resume` raises `RESTRICTED_RAN`, as `fast_exit`'s

* (4) **Selectors and bases.** All four selectors read on each exit; the condition is that the

* (7) **The work word** means the whole word, and `KICK` is tested by name. No kernel-time stamp at a fast exit or re-entry: a fast crossing's time and the look on the way out read as user time, as the native fast path's (ledger 6464 Z1). `vtime`: a fast trip charges

* (9) **LazyFP.** (c) holds for one process, and it rests on restore's overwrite, its reset path included,

## 8. AArch64

The same interface; the same rule for each path. `svc` is an exception there, so
every way out of EL0 arrives in `trap::dispatch`, and the test goes first in the
architecture's `system_call`; there is one kind of frame and every way back is
`eret`, so going in is writing the context into it. **TTBR0 holds the restricted
space alone in restricted mode and the normal root in normal mode** (K11 §3); the
kernel stays in TTBR1, `TPIDR_EL0` goes with the user state, and `TPIDRRO_EL0` is
refused non-zero in a context: no A32 code runs on this kernel, each core zeroes the
register as it starts and nothing writes it after, so that no value crosses a switch.

**No AArch64 row, §7 figure or isolation claim is made** (ledger 6198 A1, correcting
6064 (1)). A restricted root and a normal root have their own ASIDs since §8.1, so a flip
need not invalidate. What an exit does about the predictor is unchanged and is not yet a
claim: `machine::switch_barrier` calls firmware's workaround 1 only where the core's plan
has it, so on a core with CSV2 (Pixel 7's X1, A78) an exit has the branch-history loop alone
and no target barrier, and whether two ASIDs are two hardware contexts when an ASID is reused
is the open question of §8.1. Vector state: `V0` to `V31`, `FPCR`, `FPSR`, saved eagerly, as
§5; the lazy trap is `CPACR_EL1.FPEN`.

### 8.1 ASIDs (2026-11-04, ledger 6198)

As `docs/PCID.md`'s rule, smaller. `arch/aarch64/asid.rs`: a table per processor of
**sixteen slots**, each holding the id of the root it tags (`AddressSpace::id`, or the
normal root's own id, K11 §3), so a shared process's two roots have two ASIDs; ASIDs 1 to
16; ASID 0 for no user root at all, as `uninstall_user_root` leaves it. Ids are never
reused. Eight-bit `TCR_EL1.AS` is enough, and `A1` stays 0, so one `msr ttbr0_el1` writes
the root and its ASID at once.

* **A hit keeps the slot's translations**: the root write with its ASID, an `isb`, and no
  invalidation. It is safe because every shootdown on AArch64 is broadcast and names no
  ASID (`tlbi vaae1is`, `vmalle1is`, `TLB_FLUSH_IS_BROADCAST`), so it has reached this TLB
  under every tag whether or not the space was loaded. The `begun` count PCIDs need is not
  needed. A space's id going means its slot is never hit again.
* **A miss takes the next slot round robin and invalidates it**: `TTBR0` regime off
  (`EPD0`), `isb`, `tlbi aside1, slot`, `dsb nsh`, then the root with its ASID, `EPD0` off,
  `isb`. So no walk under that ASID can use the evicted owner's entries or tables,
  including ones already freed, whose frames are reused. An `isb` on each side is the
  order `disable_ttbr0`'s comment argues.
* **`uninstall`** turns the regime off (`EPD0`), as today, writes `TTBR0_EL1` zero, and no
  longer invalidates. That is safe because the zero puts ASID 0 in force, and no user
  translation is ever tagged 0 (L.aarch64.78): a TLB hit for a stray read has nothing to find.
  `user::check` asks `AT S1E1R` after each uninstall; TCG walks for that rather than reading
  a TLB, so a real core's answer is the board row's.
* **Every tag site** (A4): `asid::tagged_root` into `TTBR0_EL1`, `cpu::write_ttbr0_invalidating`
  into `TLBI`'s operand, both in bits 63:48, since a wrong shift would silently invalidate
  ASID 0; `disable_ttbr0`'s zero. `flush_user_tlb`, whose hard-coded 0 was the last, is gone.
  `TCR_EL1.AS` and `A1` are 0 on both loaders and secondaries copy the boot core's.
* **What the tag cases read** (A5). `TTBR0_EL1` has no keep bit, so `asid::last_write` is a
  record of the decision: the root, the ASID in its low bits, and bit 63 when kept. Only
  `root_tag_now` reads the register, and the cases hold the record's ASID to it. After a
  shootdown of a space on no processor a hit keeps here where a PCID flushes
  (`arch::SHOOTDOWN_REACHES_EVERY_TAG`), and the read of the new frame still has to hold.
* **Walk caches and freed tables.** A table freed under `unmap_in` goes after its broadcast
  shootdown; at a space's end, no root write names it again, and a walker only walks the
  active root, so a dead ASID's cached walks are never consulted, and they go with the
  invalidation at the slot's next taker.
* **Speculation.** `entered_space` decides as today, on the restricted root, and
  `restricted_left` is unchanged. **Narrowing the exit's barrier on CSV2 is refused for this
  landing** (ledger 6198 A2): ASIDs are reused even though ids are not, and `tlbi aside1` clears
  the TLB and not the predictor, so a program's training under ASID 3 can run as linuxd's context
  once the normal root takes slot 3. It comes back as a design of its own that answers reuse.
* **Requirements.** L.aarch64.75 the tag per root; L.aarch64.76 a hit does not invalidate;
  L.aarch64.77 a miss invalidates before the walk; L.aarch64.78 uninstall leaves the regime
  off; L.aarch64.79 ids are never reused and a dead id's slot goes at its eviction;
  L.aarch64.80 a shootdown reaches a space under another tag; L.aarch64.81 the slot rule
  (`check_root_tags`, on a table of its own, as `pcid::check`, so it runs on every boot).
* **Checks.** `user::check`'s tag cases, on the record above; `check_root_tags`, on a table of
  its own, every boot; the stray read. `restricted-check` case 138: a restricted page read here,
  so held under the restricted root's tag, unmapped from another processor while this one is in
  normal mode under the other tag, and read again; case 89 is the normal root's. From K1's
  landing (92a4f29dc) until cf774db5b, a passing boot did not judge this read: the other thread
  ended the process with status 0 first; ledger 6829. QEMU flushes
  everything when an ASID changes and invalidates a page under every ASID whichever `tlbi` it is
  told, so **no stale read can show under TCG**, and these cases cannot see a wrong tag: the
  decision is what they hold. Controls, each on its own text: a miss recorded as a hit (the
  table); a hit that invalidates (the tag cases); a tag shifted wrongly (`check_slot_rule`); `AT`
  answering after an uninstall with the regime left on; a narrowed shootdown, by
  `tools/common/check/check-asid-tlbi.py` and its self-test, since QEMU cannot show it.
* **Gates.** AArch64 runs under TCG here, which models neither the tags nor their timing, nor
  any real core's caching. `docs/BACKLOG.md` has the board or Pixel run with the core's errata
  to read (A7), which is the PO's to allot. **Nothing about an ASID is claimed from TCG alone.**

**ARMv7-A has no restricted mode** (`MICROKERNEL.md` §11 Q7): the eight calls answer
`NOT_SUPPORTED` there, and it runs native programs only.

## 10. Checks and controls

**`CONTINUE`'s guard** (ledger 6282 R7). A jump to `0x8000_0000_0000` on the Ryzen 9 9900X under KVM
reports the jump's own address, so the program cannot reach x86-64's refusal on this part, by a local
probe; other parts are unverified. So the guard stays, the decision is the pure
`restricted::may_continue`, host-tested with the non-canonical address and with a control there, and
case 56 takes either answer short of a stopped kernel.


A stage 9 check (`check_restricted`, the panic code `FX-0920`, one boot line,
`restricted`) starts a native test program, `src/user/system/native/restricted-check`,
as a shared process (K11), on all three boots that have K1 (x86-64 under KVM and
TCG, AArch64). ARMv7-A checks that the calls answer `NOT_SUPPORTED`. It runs in
every configuration; it is not deactivated code in the reference configuration.
The program, in normal mode, maps a small hand-encoded image into its restricted
space by K2 and enters it:

| Case | What the restricted image does, what normal mode checks |
|---|---|
| Round trip | `getppid`'s number and six marked arguments; every word and `reason` read, program's `rcx`, `r11` and every other register unchanged after `RESTRICTED_RESUME(value)` and `value` in `rax` |
| Registers | every general register set, `int3`: `FAULT`; `RESTRICTED_CONTEXT_READ` gives them all |
| Own `#DB` | `popf` with `TF` set: `FAULT` vector 1; the read goes back through `ENTER`, and `RESTRICTED_CONTINUE` too; `TF` in a handed-in context, refused |
| Fault | a load at a hole, a write to a read-only page, a fetch from NX, `ud2`, `div 0`: each `FAULT` with its kind and address; a touch of demand-zero memory no exit |
| Shared region | load, store and fetch at a shared address and at `linuxd`'s own code: `FAULT` kind 1, each; **the sweep**, new code in `mm::check`: a walk of the restricted root finds no entry in any root slot at or above `SHARED_BASE`, and no leaf below it whose frame is a frame the region's tables map at that moment, unless it is a VMO the restricted space itself mapped by K2 |
| Forged contexts | each §4 field wrong, one case a field: `INVALID_ARGS`, mode still normal, held context unchanged, and then a good entry still works |
| Native from restricted | a `handle_duplicate` of a private handle succeeds; of a shared handle's number, `BAD_HANDLE`; `RESTRICTED_ENTER` from restricted, `BAD_STATE`, still restricted |
| Kick | from a second thread: looping in restricted, exits `KICK`; a thread in normal mode, next entry exits and no instruction ran (a memory mark); many kicks, one exit; in a blocking native wait, `INTERRUPTED` then `KICK` |

| Vectors | `XMM`, `YMM` (`V`) set in the program, `linuxd` sets its own otherwise: after a call, each its own; a second process's thread never reads them; `RESTRICTED_VECTORS_WRITE` with a wrong `MXCSR` refused, and `XSTATE_BV` too |
