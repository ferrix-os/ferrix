## 1. Today

F-35 and F-37 charge **the job of the task that does the work**:

* frames, from `mm::allocate_user_frame`/`allocate_user_run`, to
  `sched::running_group()` (a VMO's commit, a fault, a copy-on-write copy,
  the page cache's fill in `fs/pages.rs`);
* native objects, from `quota::Charge::running` (VMOs, channel ends, ports,
  jobs);
* kernel heap, from `ferrix_kmem::Charge::bytes`, whose
  `Account::current` is `KernelHeap::current`, which is also
  `running_group()`.

So when a server makes a VMO or fills its pages *for* a client, the server's
job pays. Once servers hold the page cache and the sockets
(`MICROKERNEL.md` §4), one client could fill a shared server up to the
server's limit, and then the server would refuse everyone: T.EXHAUST by
another door. Letting the server say "charge job J" would be worse, because
a compromised server could then charge any victim. K7 is the third way, the
one point 5 and ledger 36 ask for.

## 2. The mechanism

### 2.1 The ticket

A **ticket** is a kernel object (`object/ticket.rs`, core ring):

| Field | What |
|---|---|
| `id: u64` | from one counter for the whole machine, starting at 1, **never reused**. At one a nanosecond it would take 584 years to wrap, and it refuses rather than wrap |
| `issuer: Sender` | **K6's attested sender** of the issuing call: the issuer's process id and its job id at the issue, made by `Sender::of(process)` from the caller's own core record, never from an argument *(2525 1)* |
| `slot: u32` | the issuer's job's quota slot at the issue, **held** (`quota::hold_group`) while the ticket lives, so the index stays valid after the job goes, as a frame's does |
| `state: AtomicU8` | `Live`, then `Ended`, once and for good |
| `charge: quota::Charge` | the ticket itself, one native object charged to its issuer |

**The kernel issues a ticket, never a program.** No argument names a job, a
process or a slot anywhere in the surface. **A client end shared by several
processes** issues each ticket for the job of the process that issues it,
so two processes sharing one end can each be charged only for their own
requests *(2525 1)*.

Tickets are kept on the **channel** they were issued on, in a registry
behind **its own lock** (`Channel::tickets`, a `SpinLock` taken only by
`CHARGE_TICKET` and by an end's close). It is never the inbox lock, so the
IPC paths neither take it nor wait on it *(2525 6)*. The registry holds at
most `MAX_TICKETS = 64` live tickets per issuing end. A ticket belongs to the
channel and to the side that issued it, and it can be adopted only from
**the other side**.

### 2.2 The call: `CHARGE_TICKET` (0x1070)

One native call with an operation word, `charge_ticket(op, channel, id, out)`:

| Op | Who | What |
|---|---|---|
| `ISSUE` (1) | the client, on its end (`WRITE` right) | issues a ticket for the caller's own job on this channel and writes its id to `out`. The client puts the id in its request, as bytes or as one of `channel_write_read`'s three words. Refused `SHOULD_WAIT` when its end already has `MAX_TICKETS` live, and `NO_MEMORY` when its job cannot pay for the ticket |
| `ADOPT` (2) | the server, on its end (`READ` right) | the calling **thread**'s native calls charge the ticket's job from now on (§2.3). Writes the ticket's issuer, K6's `{process, job}`, to `out` *(2525 1)*. Refused `BAD_STATE` for an id this channel never issued on the peer end, one that has ended, or one issued on this end (a ticket is never adopted from the side that issued it). A refusal changes nothing and is audited (`TICKET`) |
| `LEAVE` (3) | the server | the calling thread charges its own job again. `channel`, `id` and `out` are ignored. Always succeeds |
| `END` (4) | either side, on its end | the ticket ends. Ending one that has already ended, or one this channel never issued, is `BAD_STATE`, audited |

A ticket also ends when **either end of its channel closes**. Ending never
moves a charge already made (§2.5).

**What the kernel enforces is "until `END` or a close", not "until the
reply".** The kernel cannot see which message is the reply. The client
library (`ferrix-native`'s `charge_ticket::Request`) ends the ticket when
the reply arrives or when it gives up, and the server's library ends it as
it sends the reply. Either side's `END` is enough, and the requirements say
exactly that *(2525 2)*.

**The register path's identity** *(2525 1, K6's condition (3) at ledger
2485)*. K6 leaves `channel_write_read` (0x1013) without identity, and a
server that decides by sender reads with 0x1014. K7 is how a server learns
its client on the register path: the client sends the ticket id as one of
the three words, and the server's `ADOPT` answers the issuer's attested
`{process, job}`. That costs the fast path nothing, because nothing on it
changes, and a server can match a ticket against a 0x1014 sender as well. A
K7 note in K6.md says so; it is agreed with mk-k6 through the product owner.

**The adoption's life** *(2525 5)*. A thread adopts at most one ticket. Its
adoption is dropped when it `LEAVE`s, adopts again, exits, or execs. It is
**inert once its ticket has ended**: the thread's next native call charges
its own job, with no `LEAVE` needed. A forked or `process_create`d child,
and a new thread, start with none.

**Why ids in the message, not handles.** The 3-word `channel_write_read`
cannot carry handles, and a handle in every request would cost a table
insert per call. An id on its own is useless: it is honoured only through
the server's own end of the very channel it was issued on. So guessing a
sequential id gains nothing that being sent it would not.

### 2.3 What an adopted call charges to the client, and what it does not

The target is set **at the entry of a native call** (`syscall/native.rs`'s
`dispatch`) when the calling task has an adoption whose ticket is live, and
cleared when the call returns. `channel_write_read`'s own entry
(`dispatch_write_read`) and the fast path never set it: a round trip makes
nothing to charge. *(2525 3)* lists each site:

| Site | Charged to, under a live adoption | Why |
|---|---|---|
| `mm::allocate_user_frame`/`allocate_user_run` reached from a VMO call: `vmo_write`'s commit, `vmo_pin`'s commit, a VMO call's copy-on-write copy | **the client** (`quota::charge_target()`) | memory made for the client's request |
| `quota::Charge::running`: a new VMO, channel, port or job | **the client** (`charge_target()`) | objects made for the request |
| page faults on the server's own space, the user copies a call makes to and from the server's own buffers (`oom::fault`, `oom::user_fault`) | the server | the server's memory; both suspend the target for their work, so `throttle` and `out_of_memory` see the server's own job (Q2) |
| page-table frames `VMO_MAP` builds in the server's space (`PageTables::allocate_table`, the space's `owner`) | the server | already charged to the space's owner, not to the running task; unchanged |
| the server's handle-table growth, its region records (`ferrix_kmem`, `KernelHeap::current`) | the server | `KernelHeap::current` stays `running_group()`: structures of the server's own process that a call grows are the server's for as long as it lives |
| the page cache's fill (`fs/pages.rs`), `blkio`, the OOM and throttle paths | the server (unchanged) | not native calls; `running_group()` as today |
| processor time | the server (unchanged) | the scheduling group is not touched; K9's half (§5) |

`charge_target()` answers the ticket's slot when the running task's
per-call target word is set, and `running_group()` otherwise. It is one
load of a word the task carries, through `sched::with_current`, which is
safe with interrupts masked, as `running_group` is. **`charging_nobody`
wins** *(2525 8)*: it clears the target word as well as the group for its
work and restores both, so the kernel's own allocations made for a process
inside an adopted call are charged to nobody, as today.

**A refusal at the client's limit is the server's call answering
`NO_MEMORY`, and nothing more.** No `memory.high` throttle sleeps the server
on the client's account. No OOM kill is started from the server's call, and
the server's job is not charged instead. The VMO calls already answer a
refused frame with `VmoError::OutOfMemory`, never through
`oom::out_of_memory`, and the fault paths that do reach the OOM path run
with the target suspended. The client's job meets its own OOM reaction at
its own next charge, as before. So a client at its limit can never make a
server sleep, die or pay.

### 2.4 The slack after an end

A call checks the ticket at its entry, and the target holds until the call
returns. A ticket ended while an adopted call runs (the client's `END` or
close, or another server thread's `END`) still pays for **the rest of that
one call**. **At most the rest of one call per adopted thread is charged to
the client after the end, and always within the client's own limits**
*(2525 4; the consultant accepted per-call slack, Q1)*. Every call that
starts after the end charges the server's own job.

### 2.5 What was charged stays, and comes back

A charge made through a ticket is an ordinary F-35/F-37 charge to the
client's slot: kept by the frame record or by the object's `quota::Charge`.
It stays charged to the client's job **after** the ticket ends, for as long
as the object lives, whether the server holds it or not, and it is taken
back from exactly the levels it charged when the object goes
(`H.QUOTA.4`'s mechanism, unchanged). The ticket's end changes no counter.

### 2.6 Against a limit, and K12's reservation

A ticket charge is a charge to the **client's** slot against the client's
limits (`memory.max`, the object limit): the same counters F-35 and F-37
use. When K12 lands, a ticket charge is a charge to the client's slot like
any other. It draws on **the client's** reservation and never on the
server's. K7 adds no counter and no pool of its own, so K12 has nothing to
special-case. **K12's reservation lookup uses `quota::charge_target()` as its
"whose job" function** (the K12 review, ledger 2550 (3)), so an adopted
server thread's client-charged frames and objects (§2.3's table) draw on the
client's reservation. What §2.3 leaves on the server, its own heap and
tables, draws on the server's. Whichever of K7 and K12 lands second wires
this in, with a case in its check.

## 3. Rules and requirements

**H.QUOTA.14** (high level, parent of the six): *memory and objects a
server's native calls make while it holds a live ticket are charged to the
job the kernel recorded when it issued the ticket, and to no job a server
names. A ticket stays live until `END` from either side or the close of
either end of its channel. The client's library ends it when the reply
arrives or when it gives up.*

| Id | Rule | Check (stage 9, `ticket`) | Negative control |
|---|---|---|---|
| L.object.207 | A ticket is issued only by `CHARGE_TICKET ISSUE`, for the job and process of the calling task (K6's `Sender::of`), read by the kernel. No operation takes a job, process or slot. On a shared end each issuer's ticket names its own job | client in job C issues; server's `ADOPT` answers C's process and job ids (equal to `OBJECT_ID`/0x1014's for C); a second process in job D issues on the same end and its ticket names D | C1: `ISSUE` takes the slot from its `id` argument: the slot comparison fails |
| L.object.208 | `ADOPT` honours a ticket only through the peer of the end it was issued on, while it is live. Any other id (never issued, ended, issued on this end, issued on another channel) is refused `BAD_STATE`, audited `TICKET`, and changes nothing | five refused cases; after each, a VMO made charges S; one `TICKET` record each | C2: the channel comparison skipped: the other-channel case is honoured and the check fails |
| L.object.209 | While a thread holds an adoption whose ticket is live, the VMO commits and pins and the new objects its native calls make are charged to the ticket's job and every job above it, against their limits. Faults on its own space, its page tables, its handle table and its region records stay its own job's. Refused at the client's limit, the call answers `NO_MEMORY` with no throttle, no kill and no charge to the server's job | S, adopted, makes a VMO and commits N pages, a channel and a port: C's memory and objects rise by exactly those and S's do not; S's own handle-table growth and the page tables of a `VMO_MAP` land on S; with C's `memory.max` just above, the next commit is `NO_MEMORY`, S unchanged, no task killed, C's `high` count unchanged with its `memory.high` set low; after `LEAVE`, S's own commit succeeds | C3: `charge_target` always answers `running_group()`: C's counters do not move. C7: a throttle planted on the adopted refusal path: C's `high` count moves and the check fails |
| L.object.210 | A ticket ends at `END` from either side and when either end of its channel closes. It never becomes live again, and its id is never issued again. A native call that starts after the end charges the calling thread's own job, with or without a `LEAVE`. At most the rest of one call per adopted thread is charged to the client after the end, within the client's limits | the server's `END`, then a commit with no `LEAVE`: S charged, C not; the client's `END`, then the server's next commit: S charged; a third ticket ended by the client's close, same; ids strictly increase | C4: the server's `END` leaves the state `Live`. | L.object.211 | What a ticket charged stays charged to the client's job after the ticket ends, until the object goes, and is then taken back from exactly the levels it charged | after `END`, C's use is unchanged; S closes the VMO and the objects (not adopted); C, its parent and S return to their starting counts and every slot is given back | C8: the object's release takes back from `running_group()` instead of its recorded slot: the counters-back-to-zero case fires |

Every control goes through `fleet/gate.sh control ... --expect` on its
`ticket self-check failed: ...` sentence, reading `control: FIRED (panic)`,
on x86-64 under KVM at least *(2525 7)*.

## 4. The boot check, in the reference configuration

`src/kernel/src/object/ticket_check.rs`, run on stage 9 right after `quota`
(`stages_check::check_tickets`, `FX-0912`). It is built as
`write_read_check` and K6's `sender_check` are. A job tree is made for the
check, with a client job C and a server job S under one parent, a process
in each, and a channel between them. Every `CHARGE_TICKET` and every VMO,
channel and port call is made **through the architecture's own system call
entry** (`arch::drive_native_words`) by a thread of the check's process
(`syscall::check::spawn_in`). So it runs as a program's call does, on every
architecture (2458 M6). It runs on every boot, so the mechanism is not
deactivated code in the reference configuration (`ITEM.md` §5). The boot
line:

```
  ticket   issued to the caller's job and process; 6 refused, audited; N pages
           and 3 objects charged to the client, none to the server; S's own
           tables on S; refused at the client's limit, no wait, no kill; ended by
           either side and by close; 64 live at the bound; counters back to zero
```

`ferrix-native` gets the call's wrapper (`charge_ticket::{issue, adopt,
leave, end}`, and a `Request` guard that ends on drop), with host tests of
the registers it sends. No program uses it yet. The first servers that will
are btrfsd and `linuxd` (`MICROKERNEL.md` §4). A server's `NO_MEMORY` at a
client's limit should map to the client's own error in the server's
protocol; that is a note for their designs (2525 C2).

## 5. What it leaves room for

* **K6 (sender identity).** K7 lands on K6. A ticket's issuer is K6's
  `Sender`, and `ADOPT` answers it, which is K7's answer to K6's register-path
  question (§2.2).
* **K3 (pager-backed VMOs).** When the kernel forwards a fault to a pager,
  the kernel is the issuer: `Ticket::issue_for(sender, slot, channel)`,
  kernel-internal, for the faulting process and job, with the id in the
  fault message. It is ended by the pager's supply or by the bounded wait's
  timeout. The pager `ADOPT`s while it supplies, so the faulting job pays for
  the page (`MICROKERNEL.md` §3's K3 row). The chardev core's REQUEST can
  take a ticket the same way, so that `nvrm`'s allocations for a program are
  charged to that program. That is a load-ring change with its own review,
  K7b (2525 C1), and is not in this landing.
* **K9 (time budgets).** The adoption binds a thread to a client's job for
  the length of a request, which is the shape of seL4 MCS's scheduling-context
  donation. K9 will charge an adopted thread's processor time to the ticket
  job's budget by reading the same binding. K7 leaves the scheduling group
  where it is, and a note in `quota.rs` says so.
* **K13 (rebind).** Parked state is objects whose charges already name the
  client's slot (§2.5), so parking moves no charge and makes no uncharged
  pool, as ledger 36 asks. A ticket does **not** survive its server's death:
  the server's end closes and every ticket on the channel ends. A rebound
  server gets **new** tickets for the requeued requests.

and sets no target, the fast path reads nothing new, and the registry's
lock is not the inbox lock. The one cost on existing paths is a load in
`charge_target()` at each charge, and one test at `dispatch`'s entry.
