# K2: address space by handle

**Design for the certification consultant, 2026-10-21 (mk-k2, branch `mk/k2`).**
`docs/MICROKERNEL.md` §3, row K2, stage M2. No code is written before the
consultant's OK or OK IF.

Ids, allotted by the product owner on 2026-10-21 (the reservation lands
batched with K3's and K4's):
**H.MEM.24-25**, **L.object.232-240**, **L.user.158-162**; native calls
**0x1079-0x1080** (the space object), **0x1035 `PROCESS_SPACE`**,
**0x1027 `VMO_EXECUTABLE`**; **`Rights::EXECUTE` = bit 10**; panic code
**FX-0916** (`STAGE9_SPACES`); one stage 9 line, **`space`**. No new audit
kind: every refusal for a missing right is `ACCESS_DENIED`, which `RIGHTS`
(`Refused 2`) already records. Estimate: **20 points**, in two landings (§9).

## 1. Today

* `VMO_MAP` (0x1024, `syscall/native.rs::vmo_map`) maps a VMO into **the
  caller's own space** only, through `AddressSpace::map_object`. It is always
  shared, read or read-write, needs `MAP|READ` (and `WRITE` for a writable
  mapping), and **refuses every executable mapping** (`SpaceError::Refused`,
  answered `ACCESS_DENIED`). The region's id goes into `Inner::native`, and the
  Linux calls that reshape a region (`mprotect`, `mremap`) refuse it: "the
  protection stands for rights the handle carried".
* Nothing in the native ABI names another process's memory. `Rights::PROCESS`
  says so in as many words: no call reads or writes a process's memory, so a
  handle to devmgr (kernel-started) hands its holder none of devmgr's
  authority.
* `AddressSpace::fork` (`user/space.rs`) is Linux `fork`'s copy-on-write
  clone: private anonymous objects and private file shadows are forked
  (`Vmo::fork` shares every frame and the regions are marked copy-on-write),
  shared objects, `vmo_map`'s among them, are shared. The parent's writable
  translations of the shared pages come down, with a shootdown, **before** the
  lock goes (`unmap_copied_on_write`, `begin_shootdown`, `shoot`). F-41's fix
  is that `protect` making a private region writable marks it copy-on-write
  (`ferrix_vma::protect`), and stage 6 holds it.
* `execve` empties the existing space (`exec.rs::empty_user_half`) and loads
  into it. `PROCESS_CREATE` loads the image in ring 0 (K15 takes that out).
* The executable mappings a program gets are made by the kernel's loader, and
  the vDSO and the ARMv7-A sigpage by `map_shared_code`/`map_code_page`.

## 2. The mechanism

### 2.1 The space object

A new kernel object kind, `Object::Space(Arc<AddressSpace>)`: a handle to an
address space. It keeps the space (its tables, its regions, the objects they
name) alive as a process does, and nothing else: a space handle holds no
process, no thread and no handle table. It has no signal (`object_wait_async`
refuses it, as it refuses a VMO).

Rights on a space handle (`Rights::SPACE`):

| Right | Lets the holder |
|---|---|
| `MAP` | `SPACE_MAP`, `SPACE_ALLOCATE`, `SPACE_UNMAP`, `SPACE_PROTECT` |
| `EXECUTE` (new, bit 10) | make or protect a mapping executable in this space (with `MAP`) |
| `READ` | `SPACE_READ`, and `SPACE_CLONE` (a clone reveals every byte) |
| `WRITE` | `SPACE_WRITE` |
| `DUPLICATE`, `TRANSFER` | as for every object |

Each is reduced by `handle_duplicate`/`handle_replace` as every right is
(`Requested::resolve`, unchanged). So a debugger can be handed `READ` alone,
a loader `MAP|EXECUTE` without `READ`/`WRITE`, a core dumper `READ`.

**`Rights::EXECUTE` on a VMO handle** means the VMO's pages may be mapped
executable. `VMO_CREATE` gives no `EXECUTE` (`Rights::VMO` is unchanged).
**An executable mapping by handle needs `EXECUTE` on the space handle and on
the VMO handle**, as Zircon asks both `ZX_VM_CAN_MAP_EXECUTE` and
`ZX_RIGHT_EXECUTE`. An executable private anonymous mapping
(`SPACE_ALLOCATE`, §2.3) needs it on the space handle. This is the row's
"an executable mapping only through a handle with the EXECUTE right".

### 2.2 Where a space handle comes from

Two ways, and no other:

* **`SPACE_CREATE`** makes a **fresh, empty space** (`AddressSpace::new`)
  and answers a handle with `Rights::SPACE`. That is the row's "fresh
  restricted space for `exec`": `linuxd` builds the new image's space while
  the old program still runs, and swaps it in at the point of no return. The
  swap, which binds a space to a process as its restricted space, is **K11's**
  (and K1's for entering it). Until K11 nothing runs in a created space. It is
  a full space all the same: mapped, read, written, cloned and swept by the
  boot check, so it is not deactivated code. An in-place exec (unmap the whole
  window, as `empty_user_half` does) is also open to a holder of `MAP`.
* **`PROCESS_SPACE(process, rights)`** answers a handle to the space of a
  process **made by `process_create` and not yet started**, through a process
  handle with `MANAGE` that carries the process's `Control`. It is refused
  `BAD_STATE` once the process has started (and for good after it ends), and
  `ACCESS_DENIED` for a handle with no `Control` (a
  process the kernel started: init, devmgr) or without `MANAGE`. The new
  handle has `rights`, a subset of `Rights::SPACE` (`INVALID_ARGS`
  otherwise). That is how K15's creator maps an image's segments itself.

So `Rights::PROCESS`'s sentence stays true in the form that matters: a handle
to a process the kernel started with authority of its own reaches nothing
inside it, and a handle to a running process reaches nothing inside it
either. **Only the creator of a process, before it runs, gets its space**, and
whoever it hands that space handle to keeps what the handle's rights say for
as long as the space lives. K11's "the creating `linuxd` gets no handle into
the new process's restricted space beyond K2's rights on it" is this rule.
`Rights::PROCESS`'s comment is amended to say so.

### 2.3 The calls

All on `syscall/native.rs` (item), over `AddressSpace` (core). Every call
that changes which ranges are mapped holds the target's `layout()` sleep lock
first, as `mmap` does, so a by-handle change and the program's own `mmap` or
`munmap` cannot interleave. Every address range must lie in
`[MMAP_MIN_ADDR, ceiling)` of the target and be whole pages.

| Number | Call | Arguments → result | Needs |
|---|---|---|---|
| 0x1079 | `SPACE_CREATE` | `()` → space handle | nothing; one native object charged to the caller's job |
| 0x107A | `SPACE_MAP` | `(space, vmo, address, length, protection, *offset)` → address | `MAP` on the space; `MAP|READ` on the VMO, `+WRITE` for `MAP_WRITE`, `EXECUTE` on both for `MAP_EXECUTE` |
| 0x107B | `SPACE_UNMAP` | `(space, address, length)` | `MAP` |
| 0x107C | `SPACE_PROTECT` | `(space, address, length, protection)` | `MAP`; `EXECUTE` for `MAP_EXECUTE` |
| 0x107D | `SPACE_ALLOCATE` | `(space, address, length, protection)` → address | `MAP`; `EXECUTE` for `MAP_EXECUTE` |
| 0x107E | `SPACE_READ` | `(space, address, buffer, length)` → bytes | `READ` |
| 0x107F | `SPACE_WRITE` | `(space, address, buffer, length)` → bytes | `WRITE` |
| 0x1080 | `SPACE_CLONE` | `(space)` → space handle | `READ` |
| 0x1035 | `PROCESS_SPACE` | `(process, rights)` → space handle | `MANAGE`, `Control`, not started |
| 0x1027 | `VMO_EXECUTABLE` | `(vmo)` → VMO handle | `MAP|READ`; consumes the handle |

`address` zero means "wherever it fits" for `SPACE_MAP` and `SPACE_ALLOCATE`,
as for `vmo_map`; otherwise the range must be free (`INVALID_ARGS` for an
overlap, as `vmo_map` answers it today). `protection` is
`MAP_READ`, `MAP_READ|MAP_WRITE` or `MAP_READ|MAP_EXECUTE`, with the new
`MAP_EXECUTE = 1 << 2` in `types.rs`. **`MAP_WRITE|MAP_EXECUTE` together is
`INVALID_ARGS` on every call, whatever the rights** (§3).

* **`SPACE_MAP`** is `vmo_map` into the named space: shared, the region keeps
  the object alive, `fork` and `SPACE_CLONE` share it (§2.5). The region
  records its **ceiling**, the protections its VMO handle allowed: `READ`
  always, `WRITE` if the handle had it, `EXECUTE` if it had it. `vmo_map`'s
  own regions get the same record (read, and write per the handle; never
  execute). The ceiling replaces `Inner::native`'s plain set by a map from id
  to ceiling; the Linux reshaping calls refuse such a region exactly as they
  do now.
* **`SPACE_ALLOCATE`** maps fresh **private anonymous** zero-fill memory
  (`map_anywhere`/`map_anonymous`), the shape of `MAP_PRIVATE|MAP_ANONYMOUS`:
  no handle names it, a clone copies it on write. Its ceiling is
  read-write-execute (it is nobody else's memory), and §3 still holds every
  protection to W^X. It is how a loader or `linuxd` gets a program's stack,
  heap and writable segments without a VMO per region, and what makes
  `SPACE_CLONE` a `fork` (§2.5).
* **`SPACE_UNMAP`** is `AddressSpace::unmap`: whatever lies in the range goes,
  with the four-step order and the shootdown `user/space.rs` documents. A hole
  is not an error (`munmap`'s rule).
* **`SPACE_PROTECT`** sets the protection of a range wholly mapped **by
  handle** (regions with a ceiling). The new protection must be within each
  region's ceiling (`ACCESS_DENIED` otherwise, audited `RIGHTS`); a range that
  reaches a region the program made with Linux `mmap` is `BAD_STATE`. Making
  a private region writable marks it copy-on-write, through the same
  `ferrix_vma::protect` F-41 fixed. All or nothing: the ranges are checked
  before anything changes.
* **`SPACE_READ` / `SPACE_WRITE`** copy between the caller's buffer and the
  target space, at most `SPACE_COPY_MAX` = 64 KiB per call (the answer is the
  bytes copied, short at the first unmapped or refused page, `FAULT` if none).
  They go **through a kernel bounce buffer of one page**, page by page:
  `with_page` on the target under the target's lock, then `copy_to_user` /
  `copy_from_user` on the caller's space under the caller's lock, **never
  both locks at once** (the lock order in `user/space.rs`: no two spaces'
  locks together). They **honour the region's protection**: a read needs a
  readable region, a write a writable one (so a write into a private
  copy-on-write page copies it first, as the program's own write would).
  A write never reaches a region that is not writable, and never makes one so.
  Device regions are refused, as `with_page` refuses them (F-55). The caller
  may name its own space; the target may be running, since `with_page` is what
  every user copy already uses on a live space.
* **`SPACE_CLONE`** is `AddressSpace::fork` of the named space into a new,
  unbound space, answered as a handle with the **same rights** as the source
  handle (never more). §2.5 says what is copied and what is shared.
* **`VMO_EXECUTABLE`** replaces a VMO handle with one that carries `EXECUTE`
  and **no `WRITE`**, keeping its other rights; the old handle is closed, as
  `handle_replace` closes it. So no one handle can both write a VMO and map it
  executable. K14 builds its sealing on this call (§6).

### 2.4 W^X on every space mapped by handle (ASR-2)

* **At map and protect time.** `SPACE_MAP`, `SPACE_ALLOCATE` and
  `SPACE_PROTECT` refuse `MAP_WRITE|MAP_EXECUTE` before any lock is taken, and
  `AddressSpace` refuses a by-handle region whose flags are both write and
  execute again under its lock (`map_object`, `map_anonymous` and `protect`
  given the region's ceiling). Two layers, so a decoder bug alone does not
  make a W+X region.
* **Across a clone.** A clone copies the source's flags; a source with no W+X
  by-handle region makes a clone with none.
* **The sweep.** `mm/check.rs::sweep_w_xor_x` walks the kernel's root and the
  identity root today. K2 adds `sweep_user_root(root)`, the same walk over a
  user root's leaves, and the boot check runs it over **every space it made
  or reached by handle**, after its last map and protect: N leaves, E > 0 of
  them executable, 0 both writable and executable. That is ASR-2's detection
  (FM-2) extended to the spaces K2 maps.

**What W^X here does not cover, stated:** (a) **F-43** is unchanged: a
program's own Linux `mmap`/`mprotect` may still make an RWX region in its own
space, and a space reached through `PROCESS_SPACE` may hold one its program
made. K2 refuses W+X on every operation **by handle**; `SPACE_PROTECT` cannot
touch a region the program made itself. Once `linuxd` maps every Linux
program's memory through K2 (M5), the PO's 2026-09-13 rule ("ASR-2 holds on
every space mapped by handle") means F-43 is closed by option 1 for Linux
programs. **That is a consequence the customer should see before M5** (a JIT
needing RWX pages must flip them); this document names it and does not decide
it. (b) **Aliases.** A VMO mapped writable in one place and executable in
another (two handles, one with `WRITE`, one with `EXECUTE`) gives no single
W+X mapping but the same effect. K2 makes it awkward (the `EXECUTE` handle has
no `WRITE`) and does not forbid it; **K14's sealing** (an image VMO immutable
from its seal on) closes it for certified items. Question Q1.

### 2.5 The copy-on-write clone, and the F-41 lesson

The clone is `AddressSpace::fork`, unchanged, reached by handle:

| Region | In the clone |
|---|---|
| `SPACE_ALLOCATE`'s and Linux's private anonymous memory | the object forked (`Vmo::fork`), both sides' regions copy-on-write |
| a private file mapping's shadow | forked, copy-on-write |
| `SPACE_MAP`'s and `vmo_map`'s regions, shared file mappings, the vDSO | the same object, shared (as `fork` shares `MAP_SHARED`) |
| device regions | shared, owning no frames |

**Why a space clone and not copy-on-write child VMOs.** The row allows
either. A space clone is the operation Linux `fork` already runs, and its
order (the parent's writable translations down and shot down before the lock
goes) is the one F-41 and stage 6 hold. A copy-on-write child of a VMO that
other spaces map **shared and writable** would also have to take down the
writable translations of **every other mapper of the parent object** at the
clone, or a third space's write through its old translation would reach a
frame the child shares: F-41's bug one level up. K2 does not need it:
`linuxd` gives a Linux program's private memory with `SPACE_ALLOCATE`, and
K15's loader copies a writable segment into an anonymous region or a fresh VMO
(a start-time copy, as Zircon's process builder makes a child VMO). If K3's
private file mappings want child VMOs, that is K3's design, with this hazard
named.

**The check of the row's sentence** (L.user.160), each case on
a source space S and its clone C, with a word W in a private page:

1. W written in S **before** the clone, and S's translation of the page left
   writable and **touched** (so it is in the TLB) by a thread of the check's
   process running in S on another processor, if there is one;
2. the clone; then S writes W' **through that old translation** (the thread's
   store, not a kernel copy): C reads W, S reads W';
3. S writes W'' with `SPACE_WRITE`: C still reads W;
4. **F-41's own case**: a page written, made read-only with `SPACE_PROTECT`,
   cloned, then made writable again in S with `SPACE_PROTECT` and written:
   C reads the old value; and the same with C writing: S reads the old value;
5. C writes: S never sees it;
6. a `SPACE_MAP`'d VMO page written in S after the clone **is** seen in C
   (shared stays shared), so the check proves the difference, not just
   "nothing is shared";
7. no frame leaks: the frame counts return to where they were once S, C and
   the VMO are closed.

Case 1 needs a thread running in S. Until K11 binds a created space to a
process, S is the space of a process the check makes with `process_create`
and holds by `PROCESS_SPACE` **before** starting it; the check then starts it
(its program stores W' when told, over a channel). That is the stage 9
`spawn` check's machinery, reused.

### 2.6 Charging

As today (F-35, F-37), with nothing new: a space object is one native object
charged to the job of the call that made it (`SPACE_CREATE`, `SPACE_CLONE`,
`PROCESS_SPACE`'s handle names an existing space and charges none); a frame
committed by a fault is charged to the faulting task's job, and one committed
by `SPACE_WRITE` (or a copy-on-write copy it makes) to the **caller's** job
(`allocate_user_frame`'s `running_group()`, which K7's ticket can move to a
client). Page tables are charged to the space's owner as now. A space a
handle keeps alive after its process ended keeps its frames charged where
they were. Question Q2 asks whether `SPACE_WRITE`'s commits should go to the
target space's job instead.

## 3. Rules and requirements

**H.MEM.24** (parent of L.object.232-240 and L.user.158, 159, 161, 162):
*An address space reached by handle is mapped, unmapped, protected, read and
written only as that handle's rights allow; no mapping made by handle is ever
both writable and executable; and an executable mapping by handle needs the
EXECUTE right on the space handle and, for a VMO, on the VMO handle.*
Under O.ISOLATE, O.WXN, ASR-2.

**H.MEM.25** (parent of L.user.160): *A copy-on-write clone of a space never
sees a write its source makes after the clone, by any path, and the source
never sees one the clone makes; memory both map shared stays shared.*
Under O.ISOLATE.

| Id | Rule | Check (stage 9, `space`) | Negative control |
|---|---|---|---|

Every control goes through `fleet/gate.sh control ... --expect` on its
`space self-check failed: ...` sentence, reading `control: FIRED (panic)`, on
x86-64 under KVM at least; K2-C6 and K2-C6b on AArch64 as well, where TLB
behaviour differs (F-41 was found on AArch64).

## 4. The boot check, in the reference configuration

`src/kernel/src/user/space_check.rs` (core), run on stage 9 after `native`
(`stages_check::check_spaces`, `FX-0916`). Every call goes
**through the architecture's system call entry** from a thread of the check's
process (`syscall::check::spawn_in`, as K6's and K7's checks do), so it runs on
every architecture as a program's call does. It runs on every boot, so K2 is
not deactivated code (`ITEM.md` §5). The boot line:

```
  space    N maps, protects and unmaps by handle in 3 spaces; R refusals as
           specified, audited; W^X: 0 of L leaves writable and executable
           (E executable); clone: 7 cases, no write crossed; F frames back
```

`ferrix-native` gets the wrappers (`space::{create, map, unmap, protect,
allocate, read, write, clone}`, `process::space`, `vmo::executable`) with
host tests of the registers they send. No program uses them yet; K15's loader
library and `linuxd` (M5) are the first.

## 5. What K2 does not do

* Bind a space to a process or a thread (K11, K1). `SPACE_CREATE`'s space runs
  nothing until then.
* Private (copy-on-write) mappings of a VMO, or child VMOs (§2.5; K3 if
  needed).
* Forced writes into a read-only region (ptrace's `FOLL_FORCE` breakpoints in
  text). A debugger protects the page writable, writes, and protects it back
  within its ceiling; text mapped from a VMO handle without `WRITE` is
  breakpointed through a private copy, which waits on K3. Named so K11's and
  `linuxd`'s ptrace design meets it.
* Change the Linux personality's `mmap` (F-43 stays as it is, §2.4).

## 6. What builds on it

* **K15** (loader out): `process_create` (changed by K15) → `PROCESS_SPACE` →
  `SPACE_MAP` the text from the image VMO through `VMO_EXECUTABLE`'s handle,
  RX; `SPACE_ALLOCATE` the data, bss and stack, written with `SPACE_WRITE`;
  `PROCESS_START(entry, stack, bootstrap)`. **K15 depends on K2's slice A**
  (§9) for map and EXECUTE, and on slice B for `SPACE_ALLOCATE`/`SPACE_WRITE`.
* **K14** (image integrity): its seal is a mode of `VMO_EXECUTABLE`
  (`VMO_EXECUTABLE(vmo, SEAL)`, its own design): the VMO becomes immutable
  (refused while writably mapped; every `VMO_WRITE` and writable map refused
  after) and the kernel computes its digest there. In a certified job, K14
  makes plain `VMO_EXECUTABLE` refuse and `SPACE_MAP` with `MAP_EXECUTE`
  accept only sealed, measured VMOs. That closes §2.4's alias (b) for them.
  **K14 depends on K2's EXECUTE right.** Bit 10 and the call's operation word
  leave room (K2's call takes `(vmo)` with the second register reserved, must
  be zero).
* **K11** (shared processes): a Linux process's restricted space is a K2
  space; `PROCESS_SPACE` (or K11's own create) answers the **restricted** space
  only, never the shared region; K11's binding call takes a space handle.
  **K11 depends on K2's space object.**
* **K1** (restricted mode) enters a context on that space; its "nothing of the
  shared region reachable" sweep reuses `sweep_user_root`.
* **`linuxd`'s `fork`, `exec`, `ptrace`** (M5): `SPACE_CLONE`; `SPACE_CREATE`
  then K11's swap; `SPACE_READ`/`SPACE_WRITE` for `PTRACE_PEEK*`/`POKE*`,
  `process_vm_readv`/`writev` and core dumps.

## 8. Questions for the consultant

* **Q1** Is §2.4(b), the two-handle alias, acceptable as a residual stated in
  K2 and closed by K14 for certified items, or should K2 already refuse an
  executable mapping of a VMO that is writably mapped anywhere (and the
  reverse), with an executable-mapping count beside `shared_may_write`?
  Recommendation: the residual, since K14's seal is the stronger rule and a
  count without immutability still lets `VMO_WRITE` change code.
* **Q2** `SPACE_WRITE`'s commits charged to the caller (as every copy is
  today) or to the target space's job? Recommendation: the caller, with K7's
  ticket as the way a server charges a client; a space has no job of its own
  until K11 gives a restricted space one.
* **Q3** Is free minting of `EXECUTE` through `VMO_EXECUTABLE` acceptable
  until K14 restricts it per job? It gives nothing beyond what a creator
  already has today, since `process_create` runs any image VMO it is given.
* **Q4** The F-43 consequence at M5 (§2.4(a)): recorded in `FINDINGS.md` as
  a note under F-43 by this landing, or left to M5's design?
