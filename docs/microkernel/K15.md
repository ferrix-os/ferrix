# K15: the native ELF loader leaves the kernel

**Design for the certification consultant, 2026-11-03 (mk-m2).**
`docs/MICROKERNEL.md` §3, row K15, and stage M2: *`PROCESS_START` takes an
entry point, a stack and a bootstrap channel; the creator maps the image's
segments itself through K2, with a user-space loader library (Zircon's process
builder is the reference). The native ABI changes, and every native starter
(devmgr, `linuxd`, the test programs) moves to the library. The kernel keeps
one loader only: for the two first images of §5, read from the initramfs, which
K14 vouches for, held to the item's rules with its own requirements.*

The customer's rule of 2026-11-03 (`docs/backlog/DECISIONS.md`): one source, compile
flags only. So `PROCESS_CREATE`, `PROCESS_START`, `load_native`'s loader and the Linux
loader stay for `present` and `desktop` and are compiled out of `personality=user`;
every ring-3 starter moves to the library on every profile, and `first_image` serves
`devmgr`'s start on every profile, so both run on every boot.

## 1. Today

* `PROCESS_CREATE` (0x1030, `syscall/native.rs`, item) checks the job, reads the
  image VMO whole into kernel memory (`image_bytes`, 16 MiB at most) and calls
  the personality's `Processes::load` (`syscall/launch.rs`, load), which makes a
  Linux-personality `Process` with its credentials, namespaces, seccomp mode and
  fs context, and runs the Linux loader (`syscall/load.rs` on `ferrix-elf`) in
  ring 0 over bytes a user process chose. `PROCESS_START` (0x1031) then claims
  the start and moves the bootstrap.
* The stack is the loader's: 8 MiB reserved below `stack_top(Native)`, a guard
  above up to the user half's end and 1 MiB below it (`exec.rs::load_into`).
* Starters: devmgr (`main.rs` 4 sites, `usb.rs`), init (`directory.rs`),
  the Intel GPU keeper (`keeper/link.rs`), `ipc-bench`, `ipc-equiv`,
  `pipe-bench`. All go through `ferrix_native::pending::create_process`.
* The kernel's own start of devmgr (`discovery/devmgr.rs`, item), and under
  `ferrix.devmgr=init` `DEVMGR_START`, go through the same `Processes::load`.
* The in-kernel checks that need a native child (`launch::load_native` in
  `seccomp_filters_check`, `pidns_check`, `namespace_check`,
  `user_dispatch_check`, `syscall/check.rs`) too; `native_check.rs` and
  `devmgr.rs`'s check drive `PROCESS_CREATE`/`PROCESS_START` by number.
* `ferrix-elf` (`src/lib/platform/elf`) is unclassified: F-76's open debt in
  the manifest. It is fuzzed and has host tests.

K2 (on `mk-resolve`, stage M2) gives `PROCESS_SPACE` on an unstarted process,
`SPACE_MAP`, `SPACE_ALLOCATE`, `SPACE_PROTECT`, `SPACE_WRITE`, `VMO_EXECUTABLE`,
EXECUTE on both handles, W^X under the space's lock, and the owner slot: **every
frame a by-handle call commits is charged to the job the process was in at the
grant, a refusal answers `NO_MEMORY` to the caller** (K2.md §2.6).

## 2. The mechanism

### 2.1 Two calls

| Number | Call | Arguments → result | Needs |
|---|---|---|---|
| 0x10A0 | `PROCESS_MAKE` | `(job, name_ptr, name_len)` → process handle | `MANAGE` on `job`, `may_start_in`; exactly `process_create`'s job rules, charge, audit (`PROCESS_MADE`) and handle (`Rights::PROCESS`, `Control`) |
| 0x10A1 | `PROCESS_RUN` | `(process, entry, stack, bootstrap)` → 0 | `MANAGE`, `Control`; `TRANSFER` on the bootstrap as `process_start` |

`PROCESS_MAKE` is `process_create` with the image taken out: an unstarted
process with a **fresh, empty space**, in `job`, with the creator's ids,
fs context, namespaces, seccomp mode and attributes as today (the personality's
half of `Processes::load`, renamed `Processes::make`, stays in `launch.rs`, load:
these are `Process` fields and go with the Linux personality at M5, when K11's
native process replaces them). It parses nothing. Its space is reached by K2's
`PROCESS_SPACE`, whose rule (K2.md §2.2, ledger 2845 (1)) is unchanged.

`PROCESS_RUN` is `process_start` plus an entry point and a stack pointer, in
`process_start`'s order: claim, make the task, move the bootstrap, run; a failure
moves nothing and gives the start back. **`entry` and `stack` are checked as the
loader's `entry_point` checks an image's**: `entry` must be a user address below
the space's ceiling, because `sysretq` raises `#GP` *in ring 0* on a non-canonical
`RCX` (x86-64), and bit 0 is Thumb on ARMv7-A, with the bound even so it cannot
cross; `stack` must be at most the ceiling. Refused `INVALID_ARGS` before the
claim. What the addresses hold is the creator's business: an empty space or a bad
entry is a fault in the child, a process that ends, never the kernel's.

The start values are recorded on the claim (`StartClaim::prepare_at(entry, stack)`)
so a concurrent second start cannot change what the first enters: `claim_start`
today refuses a process with no `startup`; `PROCESS_MAKE` leaves `startup` empty
and only the claim's holder sets it, after the claim and before the task exists.

**A process `PROCESS_MAKE` made is `Abi::Native`, always.** A 32-bit image on a
64-bit kernel cannot be one (`load_native_in`'s test today). The library refuses
such an image; a creator that bypasses the library has a process that runs 64-bit
code at `entry`, or faults, in its own job.

### 2.2 `PROCESS_CREATE` and `PROCESS_START`, compiled out

0x1030 and 0x1031 are compiled out of `personality=user` (`cfg`), where the numbers
answer `ENOSYS` as every unknown native call does (L.object.295, a BACKLOG row until
that build boots), and stay in `present` and `desktop`, with their requirements scoped
to those. No starter uses them on any profile; whether to delete them is the
morning question (ledger 5782): this run's default keeps them, since `present` stays as
it is. The checks that used them only to get a child (`object/check.rs`, `native_check`,
`driver_check`, `creator_check`, `exception_check`, `space_check`) moved to
`PROCESS_MAKE` and `PROCESS_RUN` on all profiles (`Side::built`, `Side::run`);
`process_create`'s own cases stay under the flag (`sealed_check`).

### 2.3 The library: `ferrix-process-builder`

`src/lib/proto/process-builder`, `no_std`, `forbid(unsafe_code)`, on `ferrix-native`
and `ferrix-elf`, generic over `Syscall`, so a recorder tests every call on the host
and under Miri, as `ferrix-native`'s tests do. A fuzz target drives it with
arbitrary images against the recorder. It is in no ring (a user-space library,
`ITEM.md`'s "outside"), until `btrfsd` or the partition manager, which link it,
make it part of a certified user-space item (§6.3, K14's review).

```rust
let image = image(vmo)?;                   // VMO_EXECUTABLE, then narrowed: IMAGE_RIGHTS
let built = build(&job, &image, "name")?;  // PROCESS_MAKE .. SPACE_* .. handle closed
built.process().notify_on_exit(&port, key)?;
let process = built.run(bootstrap)?;       // PROCESS_RUN(entry, stack, bootstrap)
```

`build`, in order:

1. Read the ELF header and program headers out of the VMO (`VMO_READ`); parse with
   `ferrix-elf`, the same validator the kernel's loader uses. Refuse: another
   machine or class than the program's own, no `PT_LOAD`, a `PT_INTERP`, an entry
   outside the user half, any segment outside it.
2. `PROCESS_MAKE`; `PROCESS_SPACE` with exactly `MAP|EXECUTE|WRITE` (never `READ`).
3. Per page, as `load.rs` already decides it ("mapped from the file where a page is
   the file's, copied where it is not", module docs, and the union of permissions
   for a page two segments share): every page of one **non-writable** segment's file
   contents, congruent, in no other segment, its first and last pages mapped whole as
   `file_runs` maps them: **`SPACE_MAP`** from the image's handle, read or read-execute,
   with `MAP_NO_PAGER`. Everything else: **`SPACE_ALLOCATE`** read-write,
   **`SPACE_WRITE`** through a one-page buffer, then **`SPACE_PROTECT`** to the page's
   union. **An executable page is never copied (5726 (2)): one that cannot be mapped
   refuses the image, and so does a page whose union is W+X**, as the kernel's loader
   already refuses one (`load.rs`). The recorder test shows no `MAP_EXECUTE` on any
   `SPACE_ALLOCATE` or `SPACE_PROTECT`; xtask's image check holds each built image to it.
   The image's bound: `MAX_IMAGE_BYTES`, 16 MiB, `process_create`'s, and 16 segments.
4. The stack and its guards, at the same addresses as today (`STACK_SIZE`,
   `STACK_GUARD`, the guard to the user half's end), the constants moving to
   `ferrix-native-abi`, with a kernel `const` assertion that they agree with
   `exec.rs`'s. A guard needs a region with no access: **K2's `SPACE_ALLOCATE`
   gains protection 0** (an amendment to K2.md §2.3, `VmaFlags::NONE`, ceiling as
   ever, so `SPACE_PROTECT` by the same holder can lift it; W^X unaffected).
5. Close the space handle, so **the creator keeps nothing of the child's space**;
   answer the process, entry and stack. On any failure the process handle's drop
   kills the unstarted process, as today (`ProcessRef::created`, F-23's path).

**PIE base** as today: `pie_base(Native)` for `ET_DYN`, 0 for `ET_EXEC`.

**Who pays (5726 (9)).** Copied pages and the bookkeeping of a by-handle region: the
child's job, by K2's owner slot (`charging_owner`, now around `allocate_by_handle` and
`map_by_handle` too), as today's `set_current_group(job)`. A job at its limit:
`SPACE_WRITE` answers `NO_MEMORY`, the build fails and the process is killed, as
today's refused load. **Mapped text and read-only data are the image VMO's frames,
charged to whoever filled the VMO, outside the child's limit, and shared by every
process run from it; the maker's job stays charged while any child maps them.** A
driver's text is devmgr's memory, or the kernel's for a kernel-made image VMO. It is
bounded by the image's size, not by anything the child does, and it is what K14's
sealed VMOs need. Tables and text faults come at run time, so a job at its limit may
build a process that then ends at its first fault (a case of L.object.294).

**Why text is mapped, not copied.** K14: "a process's executable mappings come only
from sealed, measured VMOs, through K2's EXECUTE right". A copy would be an
executable private mapping K14 must then forbid. K14's seal goes into `Image::new`
and nothing else moves. `DEVMGR.md` §5's "a driver never faults on the disk it
serves" holds: an image VMO is anonymous and committed by its writer, and
`MAP_NO_PAGER` refuses a pager-backed one (`WRONG_TYPE`) at the map.

### 2.4 The one kernel loader: `first_image`

`src/kernel/src/discovery/first_image.rs`, **item** (`user/**` is core, 5726 (4)(a)).
It serves exactly: the kernel's start of devmgr and, for §5, the partition manager and
`linuxd`; `DEVMGR_START` in the hybrid shapes; and the in-kernel checks. In a
`personality=user` build no path from a system call's bytes reaches it: **its only
sources are `ReadFile` of an initramfs path** and check-file constants. **In `present`
and `desktop`, under `ferrix.devmgr=init`, the first `DEVMGR_START` still parses what
pid 1 left at `/sbin/devmgr`, as those shapes always have** (`read_from_root`), named in
`ITEM.md` §5 and `VULNERABILITY-ANALYSIS.md` (5726 (6), 5782 (a)). So H.MEM.26 is scoped
to `personality=user` and H.MEM.27 holds on every profile.

`load(space, bytes) -> Result<Start, Refused>`: `ferrix-elf`'s parse, machine and
class of the running kernel only, no `PT_INTERP`, no file mapping: every page
anonymous, copied (`uaccess`), permissions applied per page, no page W+X (refused,
never unioned), then the stack and guards. Every failure answers `Refused` and the
caller's start refuses; a malformed first image is a console line and a refused
start, as a missing one is today, never a panic. Fallible allocation (F-23), no
`unsafe`.

The Linux loader (`load.rs`, `exec.rs`) is untouched: it is `execve`'s, load ring,
and leaves with the load at M5. A Linux program started by init still comes through
it.

**`ferrix-elf`'s ring** (5726 (4)). The item already depends on it
(`syscall/program.rs`), and the core names it (`arch::*::image_abi`, core check files),
so into `item` would be an upward edge; the crate is classed **core**, the review's
second choice, and both `unclassified_deps` entries leave, closing F-76 for it.
`symbols.rs` and `fixups.rs` are the boot loaders' and xtask's: no kernel file names
them (`ITEM.md` §2). The ring is the customer's to overrule (morning question; ledger
4923's text).

### 2.5 Every starter moves

| Starter | Change |
|---|---|
| `devmgr` `main.rs` (4 sites), `usb.rs` | `Image` per image handle, kept in `Drivers`; `build`, `run` |
| `init/init/src/directory.rs` (`make_native`, and its helper) | `vmo::create`, write, `Image::new`, `build`, `run`; init holds no space handle |
| Intel `keeper/link.rs`, `ipc-bench`, `ipc-equiv`, `pipe-bench` | the same |
| `ferrix_native::pending::create_process`, `Process::start` | removed, with their host tests; `PROCESS_MAKE`/`PROCESS_RUN` wrappers added |
| `linuxd` (mk-lift, M5) | is written against the library; K15's API is on this branch from its first commit |

A process that keeps a handle to its image for a restart holds `Image`, not a
writable VMO handle. The kernel hands devmgr its images with `READ` and no
`WRITE` or `DUPLICATE` (`discovery/devmgr.rs`, F-note at `read_files`), a handle
`VMO_EXECUTABLE` cannot take. K15 hands them as `IMAGE_RIGHTS = READ | MAP |
EXECUTE | TRANSFER`, what `VMO_EXECUTABLE` would answer: `Image::of_executable`
wraps such a handle and `Image::new` makes one from an ordinary VMO. Still no
`WRITE`, no `DUPLICATE`, and the kernel's fingerprint over them stands.

* **Q4** The name of the new calls, and retiring 0x1030/0x1031 rather than changing
  their arguments in place. Recommendation: new numbers: a stale binary then gets
  `ENOSYS`, not a wrong-register start.

  unsealed memory before K14? Recommendation: no; K2's Q3 answer stands: minting

## 5. Rules and requirements

**H.OBJ.27**: *A native process made by `process_make` shall begin with an empty address
space and run only what its creator mapped, entered at an entry point and on a stack the
kernel has checked lie in user space. In a kernel built with `personality=user` the
kernel shall parse no image on any call a program can make.* Parents: O.VALIDATE, O.ISOLATE.

**H.MEM.26** (`personality=user`): *the kernel's one loader shall load only images read
from the initramfs, for the processes the kernel itself starts, and constants of the
in-kernel checks.* Parent: O.VALIDATE; see L.init.2.

**H.MEM.27** (every profile): *that loader shall leave no page both writable and
executable, and refuse a malformed image and never panic; what a refused devmgr then does is
stage 10's stated fatal* (`main.rs`'s `STAGE10_DEVMGR`, ledger 6162 N2). Parents: O.WXN, ASR-2.

## 6. The checks

`discovery/first_image_check.rs` (item, not raised: kernel objects alone) and
`syscall/build_check.rs` (item, raised into the load's crate until the check host,
through the native dispatcher), `stages_check::check_build`, `FX-0930`, stage 9 after
`space`, on every boot: three architectures, four boots. The stub the child
runs is mapped with `SPACE_MAP` from a VMO through `VMO_EXECUTABLE`, as the library
does. Boot line:

```
  build    N processes made empty, run at a checked entry and stack; R refusals;
           first image: 6 malformed refused, 0 W+X of L leaves
```

The library itself runs on every boot under devmgr: the boot's driver starts are its
end-to-end check, `test-boot`, `test-shell`, `test-net`, `test-restart` its rows. In
`xtask`, a check over each built native image: no W+X page, no `PT_INTERP`.

Host: `ferrix-process-builder`: the call sequence for a three-segment image against
the recorder; refusals; a `.bss` tail; the handle closed; failure paths kill. Miri.
Fuzz: `process_builder` target in `src/tests/fuzz`.
