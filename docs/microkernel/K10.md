# K10: timer objects

`docs/MICROKERNEL.md` §3, row K10: *a deadline object signalled to a port,
with slack*, so that `linuxd` can build Linux's timers on it after the lift
(M5). Stage M1. Ids: H.OBJ.21, L.object.213-220 (reserved by the product
owner, 2026-10-19). Native calls 0x1071-0x1073. Panic code FX-0913. One
`stages_check` slot, `check_timers`. No audit numbers.

## 1. What there is today

| Linux timer | Where it lives | How it fires |
|---|---|---|
| `timerfd_create`/`_settime`/`_gettime` | `fs/timerfd.rs`, `syscall/timerfd.rs` (load ring) | a kernel thread, `timerfds`, sleeps to the earliest deadline over every timerfd, counts expirations, wakes the fd's queue |
| `setitimer(ITIMER_REAL)`, `alarm` | `syscall/kill.rs`, `syscall/signal.rs` (load) | a second kernel thread, `itimers`, walks every live process each pass, raises `SIGALRM` |
| `nanosleep`, `clock_nanosleep` | `syscall/time.rs` (load) | the calling task's own sleep deadline (`sched::sleep_until`) |
| `timer_create` (POSIX timers) | not built: `ENOSYS` | -- |
| `ITIMER_VIRTUAL`, `ITIMER_PROF` | refused (`EINVAL`), nothing counts CPU time per process | -- |

The core's deadline machinery (`timer.rs`, `sched/queue.rs`) is one thing:
each processor's `CpuQueue` holds a `Timeline` of sleeping tasks keyed by
their wake instant, each filed in a sleep slot the task owns (filing
allocates nothing, F-23); `CpuQueue::arm_timer` arms the processor's one
hardware one-shot for the earliest of the first sleeper, the slice end and
the `cpu.max` cut; `choose_next` wakes due sleepers at every decision.
`OBJECT_WAIT_ONE`'s and `PORT_WAIT`'s deadlines, `nanosleep`, and K5's
futex timeouts (PO relay from K5, 2026-10-19) all ride on it.

The two load threads are each a second and third deadline mechanism, their
CPU time charged to no job, and their passes walk every timer or every
process under no bound the item states. They are what K10 replaces after
the lift; K10 does not touch them now (no load-ring file changes, and
nothing in K10 names a load-ring module).

## 2. The mechanism

A **timer** is a kernel object (`Object::Timer`, `src/kernel/src/object/timer.rs`,
core ring) holding at most one armed **one-shot** deadline on a counter
clock, with a **slack**. When the deadline passes the timer asserts
`READABLE`, and everything waiting on that signal learns it through the
existing object machinery:

* a port, through `OBJECT_WAIT_ASYNC` on the timer: an `Observer`
  (one-shot, its port's room promised when registered, `object::port`),
  which queues a `PACKET_SIGNAL` with the registration's key. **This is the
  "signalled to a port"**: no new packet kind, no new promise accounting.
* a thread, through `OBJECT_WAIT_ONE` on the timer.

`READABLE` on a timer means "its deadline has passed since it was last
set"; `TIMER_SET` and `TIMER_CANCEL` clear it. (Zircon calls it
`ZX_TIMER_SIGNALED`; a new signal bit would change `Signals::ALL`, an ABI
change K10 does not need.)

### 2.1 One queue

Timers are filed **on the same per-processor `Timeline` as sleeping tasks**
(the consultant's pre-read, ledger 2458; K5's note). The timeline's payload
becomes

```rust
enum Due { Wake(Arc<Task>), Fire(Arc<TimerCore>, u64 /* generation */, u64 /* earliest */) }
```

and a task's sleep slot becomes a `Slot<Due>`. `arm_timer` is unchanged: it
arms for the timeline's first key whatever kind it is. So there is still one
hardware one-shot per processor and one place that decides when it fires.

### 2.2 Where a timer fires: the timer interrupt only

`choose_next` holds its run queue's lock across the switch, so it cannot
deliver to a port (a port's wake takes run queue locks). So:

1. **The wake pass** (`CpuQueue::wake_sleepers`, called from `choose_next`
   and, new, from the timer interrupt) pops due entries in key order. A
   `Wake` is woken as today. A `Fire` is moved, still holding its slot, into
   the queue's **fired buffer**, a fixed array of `FIRE_BATCH` (16) entries
   inside `CpuQueue`, made with the queue (no allocation at fire time). If
   the buffer is full the pass stops at that entry, leaving it filed.
2. **The timer interrupt** (`timer::on_tick` -> `sched::timer_expired`) takes
   this processor's queue lock (interrupts are masked), runs the wake pass,
   moves the fired buffer's entries onto its stack, lets the lock go, and
   **fires** each (§2.5). Then it asks for the decision as now.
3. If a decision outside the interrupt left entries in the fired buffer,
   `arm_timer` arms for `MIN_ARM_NS` (20 µs), so the next interrupt delivers
   them. A timer is never fired from `choose_next`, a system call's return
   or another processor.

**Fire work per interrupt is bounded**: at most `FIRE_BATCH` timers; each
takes its own interrupt-safe lock, triggers at most `TIMER_OBSERVERS` (4)
registrations, queues their packets on their ports (each port's
interrupt-safe lock, no allocation), and wakes the timer's and those ports'
wait queues. The rest wait for the next interrupt, which `arm_timer` arms at
once. The time is charged to the task the interrupt cut, as every
interrupt's is (K9 owns changing that). `MEMORY-AND-TIMING.md` §2.2 gets
these bounds.

### 2.3 Clocks

`TIMER_CREATE` takes a clock: `TIMER_CLOCK_MONOTONIC` (0) or
`TIMER_CLOCK_BOOT` (1). Both are `timer::now_nanos()`, the free-running
counter, because nothing suspends (`fs/timerfd.rs` says the same). The
distinction is kept in the ABI so that a suspend, if it ever comes, changes
the kernel and not `linuxd`; until then both file on the same timeline with
no conversion. Any other clock is `INVALID_ARGS`.

**`CLOCK_REALTIME` is `linuxd`'s.** The wall-clock offset is the Linux
personality's state (`syscall/time.rs`'s `realtime_offset`), and a clock
set must move every absolute real-time timer and end the
`TFD_TIMER_CANCEL_ON_SET` ones. `linuxd` converts a real-time deadline to
the counter when it sets a timer and re-sets its real-time timers when the
clock is set, as `fs/timerfd.rs`'s thread does today.

### 2.4 Absolute and relative; slack and coalescing

`TIMER_SET(timer, deadline, slack, options)`:

* `options & TIMER_RELATIVE` clear: `deadline` is an instant on the timer's
  clock. Set: `deadline` is a delay, added to the clock read **once, inside
  the call, under the timer's lock** (saturating). A relative timer is
  never early by the time the caller spent before the call; it may be late
  by it, which POSIX allows.
* A deadline at or before the clock's reading at the call **fires in the
  call itself** (task context, §2.5), so "already past" never waits for an
  interrupt.
* `slack` widens the window to `[deadline, deadline + slack]` (saturating).
  The entry is filed keyed by `latest = deadline + slack`, so the hardware is
  armed for the earliest *latest* of everything filed. The wake pass pops an
  entry when its key is due, **and also, while the first entry is a `Fire`
  whose `earliest` has passed, pops that too**: a timer whose window has
  opened is fired by any interrupt or decision that arrives inside it.
  That is the coalescing: one interrupt serves every timer at the head whose
  window it falls in. (Linux's hrtimer soft/hard expiry, the same shape.) It
  is a prefix, not a search: an open window behind a closed one waits for
  its own `latest`, never later.
* **Never early.** No timer fires before its `deadline` on the counter.
* **Late by at most** its slack plus the processor's interrupt latency plus
  `MIN_ARM_NS` when a decision outside an interrupt found it due, plus one
  interrupt per `FIRE_BATCH` timers due ahead of it on that processor.

`linuxd` maps `timerslack_ns` (Linux's default 50 µs) to `slack`; a
`timerfd` or POSIX timer passes its process's slack, `nanosleep` keeps using
the thread's own sleep deadline and needs no timer object.

### 2.5 Firing, re-arm and cancel against a fire in flight

`TimerCore`'s state, under one interrupt-safe lock:

| field | meaning |
|---|---|
| `generation: u64` | bumped by every `TIMER_SET` and `TIMER_CANCEL` |
| `armed: Option<(earliest, latest)>` | the current arm |
| `filed: Option<(cpu, latest)>` | where its entry is filed, and its key |
| `slot: Option<Slot<Due>>` | home when not filed and not in flight |
| `signalled: bool` | `READABLE` |
| `observers: Observers` | capacity `TIMER_OBSERVERS` listed and firing, reserved at creation |

The id an entry is filed under is the timer's serial with the top bit set,
so it never ties with a task id.

**Lock order: timer lock, then a run queue's lock.** The fire path lets the
run queue's lock go before it takes a timer's.

* **Set**: lock the timer; `generation += 1`; clear `signalled`; if `filed`,
  lock that processor's queue and remove the entry by its key (O(log n),
  `Timeline::remove_at(latest, id)`, new: the existing `remove(id)` walks the
  timeline). If the entry was there the slot is home. Record `armed`. If the
  slot is home, file it on **this** processor's queue keyed by `latest` and
  re-arm that processor's timer if it is now first. If the slot is not home
  (the entry was popped and is in a fired buffer or being fired), leave it:
  the fire in flight will see the generation changed and file it (below).
* **Cancel**: as set, with `armed = None`, nothing filed.
* **Fire** (an entry `(core, generation g)` and its slot, from the interrupt
  or from set): lock the timer; put the slot home. If `g` is not the
  current generation the entry is stale: it signals nothing, and if the
  timer is `armed` and not filed, file it now on this processor (the set
  that could not). Otherwise: `armed = None`, `signalled = true`, move the
  observers that want `READABLE` to `firing`. Let the lock go; deliver the
  fired observers one at a time (`port::deliver`, as a channel's do); wake
  the timer's wait queue.

So: **a timer fires at most once per set; nothing a set or cancel has
superseded ever signals, wherever its old entry was when the call ran; and
a timer set again while its old entry is in flight is filed exactly once**,
by whichever of the two holds the slot.

### 2.6 One-shot only; periodic is `linuxd`'s

The kernel has no interval. A periodic Linux timer is `linuxd` setting the
next deadline when it takes the packet: `next = previous_deadline + k *
interval` for the smallest `k` that puts it in the future, `k - 1` being the
overrun count `timer_getoverrun` and a timerfd's read report. Reasons:

* Overrun counting and its reset rules (`timerfd` counts, POSIX timers
  report overruns per signal, `ITIMER_REAL` coalesces into a pending
  `SIGALRM`) are three Linux semantics; the kernel would carry the union.
* `fs/timerfd.rs`'s own rule, "an expiration nobody has read stops the
  timer announcing more", is exactly what a one-shot re-armed on read gives,
  so a periodic timer nobody reads costs one interrupt, not one per period.
* Periodic re-arming from the interrupt would add a re-file to every fire,
  and a period shorter than the interrupt latency would be a storm the
  kernel then has to bound.

Drift: `linuxd` re-arms from the deadline, not from when it ran, so the
period does not accumulate latency (the same rule `timer.rs`'s periodic tick
keeps).

### 2.7 Charging (F-35, F-37)

`TIMER_CREATE` charges the creating thread's job, both fallibly, before the
handle exists:

* one unit of `Resource::Objects` (`Charge::running`, F-35), as a port does;
* the timer's kernel heap -- `TimerCore`, its slot's tree node and its two
  observer vectors -- as kernel memory (`ferrix_kmem::Charge::bytes`, as
  `user/vmo.rs` charges its mapper heap; F-37's rule extended to a core
  object).

At either limit the call is refused (`NO_MEMORY`) and nothing is made. Both
charges are held by the handle-side `Timer` and go back when it drops.
Every allocation is fallible (`fallible::try_arc`, `try_reserve`), and none
happens under the timer's lock or in the interrupt: the slot and both
observer vectors are made at creation, `OBJECT_WAIT_ASYNC`'s `Observer`
promises its port's room before the timer's lock is taken, and a timer
holding `TIMER_OBSERVERS` registrations refuses another (`NO_MEMORY`, as
`MAX_OBSERVERS` does for other objects).

### 2.8 Destruction while armed

`Object::Timer` holds an `Arc<Timer>`; `Timer` holds the charges and an
`Arc<TimerCore>`; a filed or in-flight entry holds another
`Arc<TimerCore>`. `Drop for Timer` (task context: handle close,
`object::dispose`, a dying process's table) **cancels**: the generation
bump makes any in-flight entry stale and a filed entry is removed, so
**nothing signals after the last handle closes**. Observers still listed
are dropped there, giving their ports' promises back.

A stale in-flight entry's `Arc<TimerCore>` may be the last, and then
`TimerCore` is freed by the timer interrupt: heap only (the slot node and
two vectors; the charges were the `Timer`'s and are already back). The
heap's locks mask interrupts (`mm.rs`), and the interrupt object's handler
already drops a port reference there (`object::interrupt::Line::fire`).
The same holds for the `Arc<Port>` an `Observer` upgrades while firing.
`Timer` is in `drops_at_once`: it holds no object.

### 2.9 Placement and migration

A timer is filed on the processor that set it. A thread that moves leaves
its timers where they were filed; they fire there, which is right for a
port any processor waits on. No processor goes offline in this kernel; if
one ever does, its timeline's timers move with its sleepers.

## 3. The native ABI

From `src/lib/proto/native-abi/src/nr.rs`, allotted by the product owner:

| Number | Call | Arguments | Returns |
|---|---|---|---|
| 0x1071 | `TIMER_CREATE` | `clock`, `options` (must be 0) | a timer handle with `Rights::TIMER` = DUPLICATE, TRANSFER, WAIT, WRITE |
| 0x1072 | `TIMER_SET` | `timer` (WRITE), `spec_at`: a pointer to a `TimerSpec { deadline: u64, slack: u64 }` (16 bytes, read as two native-endian `u64`s, so ARMv7-A carries both whole, as `OBJECT_WAIT_ONE`'s deadline travels), `options` (`TIMER_RELATIVE` = 1; other bits `INVALID_ARGS`) | 0 |
| 0x1073 | `TIMER_CANCEL` | `timer` (WRITE) | 0 |

`OBJECT_WAIT_ASYNC` and `OBJECT_WAIT_ONE` accept a timer (WAIT right);
`object_wait_async`'s refusal list loses it. Refusals: a handle that is not
a timer `WRONG_TYPE`, missing right `ACCESS_DENIED`, unknown clock or option
bit `INVALID_ARGS`, a refused charge or allocation `NO_MEMORY`. The host
tests in `native-abi` cover the numbers' decode and `Rights::TIMER`.

## 5. The boot check (`present` in the reference configuration)

`stages_check::check_timers`, run in stage 9's native-objects step on every
boot of the reference configuration (x86-64 KVM and TCG, AArch64, ARMv7-A
at `--smp 2` and four), prints `stage 9  timers ...` with its counts, and
stops the boot with FX-0913 on any failure. It drives the calls through the
native dispatch from a check process, as the other stage 9 checks do:

| Case | What it requires | Ids |
|---|---|---|
| a. fires | relative 2 ms, slack 0, registered on a port: the packet's key arrives, `fired_at >= deadline` (read at the fire, kept for the check), READABLE set | 214, 216 |
| b. cancel | set 2 ms, cancel at once: after 6 ms no packet, READABLE clear | 215 |
| c. stale in flight | set, pop its entry into the fired buffer by the check seam, set again later, fire the old entry: it signals nothing; the new arm fires once at its own deadline; the timer is filed exactly once (timeline count) | 219, 218 |
| d. coalescing | A: deadline t, slack 0; B: deadline t - 1 ms, slack 3 ms: both fire in the same interrupt (the same fire-batch serial) | 217 |
| e. past deadline | absolute deadline 0: READABLE set when the call returns | 214 |
| f. batch bound | `FIRE_BATCH + 4` timers due together: the first interrupt fires `FIRE_BATCH`, the rest the next, none lost | 216, 218 |
| g. destruction | close an armed, registered timer: no packet ever, the port's promised count back where it was | 220 |
| h. charging | the job's object count and kernel bytes rise by 1 and the stated size at create and fall back at close; in a job whose object limit equals its use, create is `NO_MEMORY` | 213 |

## 9. The review's conditions (OK IF, ledger 2538)

1. **Frees in the interrupt.** A `TimerCore` the interrupt frees holds no
   object: `Drop for Timer` empties both observer lists first, and
   `TimerCore`'s drop `debug_assert`s it. An `Arc<Port>` upgraded while
   firing that turns out to be the last is not dropped in the interrupt:
   the fire path delivers through `port::deliver` only from the interrupt
   when it can show the port is held elsewhere, and otherwise parks the
   reference on a per-processor list a task-context pass drops (decided in
   code, stated in the diff check). `MEMORY-AND-TIMING.md` §2.2r names the
   heap frees in interrupt context beside the heap's interrupt-masking lock.
2. **Removal by key is its own requirement**, L.sched.84: a task records
   the key it was filed under (written under the queue lock in
   `file_sleeper`); `remove_sleeper` removes by that key
   (`Timeline::remove_at`). Case j: an early wake removes exactly its own
   entry (the timeline's count before and after). Control N8: `remove_at`
   given a wrong key leaves the entry, and case j fails. `Timeline::remove(id)`
   stays only if a caller is left (`unfile_sleeper`, check-only), else goes.
   ABAB round trip against `main`, fast path off and on, before the code
   review: a ratio over 1.01 (fast) or 1.02 (general) goes back to the
   consultant.
3. **Timers never delay a task's wake.** A `Fire` that finds the fired
   buffer full is re-filed under the queue lock at `now + MIN_ARM_NS` (its
   filed key is an atomic written only under the lock of the queue it is
   filed on, so a set's `remove_at` always reads the current key), and the
   pass goes on to the `Wake`s behind it. At most `FIRE_BATCH` re-files a
   pass; past that the pass stops, and that residual delay to sleepers is
   stated. §2.4's lateness is stated in `MEMORY-AND-TIMING.md` as
   interference between jobs on one processor, owned by K9; H.OBJ.21's
   "stated latency" points there.
4. **ARMv7-A**: `TIMER_SET` reads deadline and slack through `spec_at`
   (§3). The ABI crate's host tests cover the numbers and the spec's layout;
   case a also runs with an absolute deadline above 2^32 ns on every boot.
5. **Lock order**, in `object/timer.rs`'s module documentation and §2.2r:
   a timer's lock, then a run queue's lock; the fire path lets the queue
   lock go before it takes a timer's; port locks only after the timer's is
   let go. Timer timeline ids carry the top bit; task ids are counted up
   from 1 by one counter, and a `debug_assert` where they are made holds
   them below 2^63.
6. **Controls** N1-N8 through `gate.sh control --expect`, each FIRED
   (panic) on its case's sentence, x86_64 under KVM at least. "Allocates
   nothing in the interrupt" is argued in TRACEABILITY if no guard exists.
7. Ids and numbers as reserved and allotted; the code landing releases the
   reservation.
8. For the code review: the `timers` line on all five boots, check and
   release PASSED, coverage carried after the final rebase, (2)'s figures.

Lesser (not owed): the `timerfds` and `itimers` threads stay uncharged and
unbounded until M5, which K10 lets retire (§1); `CLOCK_BOOT` equals
`CLOCK_MONOTONIC` while nothing suspends (§2.3, and the ABI's doc).
