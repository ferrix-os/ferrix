# K6: kernel-attested sender identity on a channel message

**Design for the certification consultant, 2026-10-19, mk-k6.** Written
against `main` `8cb1dc24a` on branch `mk/k6`. `docs/MICROKERNEL.md` §3
row K6, and `docs/OPAQUE-KERNEL.md` §2 point 4: *the job and process
written by the kernel, never taken from the body*. The ids are allotted by
the product owner: H.OBJ.19, L.object.197-202; native numbers 0x100A and
0x1014; no panic code, audit number or `stages_check` slot. No code is
written before this design's OK or OK IF.

**Reviewed 2026-10-19**: OK IF (1) to (9), ledger line 2485
(`~/.local/share/ferrix/cert-consultant/reviews.md` on nazuna, the

## 1. What K6 gives, and to whom

A server that reads a message can ask the kernel who wrote it: which
process, and which job that process was in when it wrote. The answer is
written by the kernel at the write, from the writer's own kernel state, and
is never read from the message's bytes or from anything the writer passes.
It is what §2.5's "masquerade" fault needs (ISO 26262-6 Annex D: the
kernel covers masquerade) and what K7's charging token is issued against
(the consultant's pre-read, ledger 2458: K6 lands first).

## 2. The identity

```
struct Sender { process: u64, job: u64 }      // 16 bytes, both little-endian words
```

* **`process` is a process id**, new in this landing: a 64-bit number
  taken from one kernel-wide counter (`object::process::NEXT_ID`, starting
  at 1, `fetch_add(1, Relaxed)`) as the core `Process` is made, kept in its
  `Exit` record (the part a process handle holds, and which outlives the
  process), and copied into `Process` for the write's load. **Never
  reused**: the counter only grows, and at a billion processes a second it
  wraps after 584 years; the argument is the job ids' own (`object::job`
  `NEXT_ID`, the same shape, cgroupfs's `job-<id>`). **Not the pid**: a pid
  is a `u32` from `object::process::allocate`, reused once freed, so a
  server keyed on pids would take a new process for an old client. The
  process id is unchanged by `execve` (the core `Process` is kept across
  it, as the pid is) and new for every `fork`, `clone` without
  `CLONE_THREAD`, and `process_create`. Threads of one process share it.
  *Answer to "what is a koid here"*: Ferrix has no kernel object ids yet;
  this is one, for processes only, and jobs already have theirs.
* **`job` is the writer's job id at the write**: `Job::id`, unique for the
  kernel's life and never zero (the counter starts at 1, so the root job is
  1). A process moves between jobs (`cgroup.procs`, `process_create`'s move
  into its job), so the write reads a mirror of it, `Process::job_id`, an
  `AtomicU64` written under `membership` beside `slot` in every place
  `membership` changes (`Process::new`, `move_charged`) and read with
  `Acquire` without the lock. A write racing a move gets the job before or
  after it, each of which was the writer's job during the write.
* **The kernel's own messages** carry `Sender::KERNEL`, `{0, 0}`. Zero is
  neither a process id nor a job id, so no program can be taken for the
  kernel and the kernel for no program. **`{0, 0}` attests that the kernel
  wrote the message, not that its content is the kernel's own** (condition
  2). A control channel may pass on bytes a program gave it. H.OBJ.19,
  L.object.197 and the ABI's documentation of 0x1014 say so. Until M5 the
  load ring writes these in ring 0 with `KERNEL`; M5 retires those sites
  along with their calls (§3, *Retired calls*). The 25 product sites,
  counted by the compiler when `Endpoint::write` took the sender:

  | File:line (at `f9dba5907`) | Ring | What it writes | Bytes from a program? |

* **An identity, not credentials** (condition 4). A process keeps its id
  across `execve`, a set-id `execve` included. So a server must never cache
  a privilege by process id across an exec. The stamp attests the writer,
  not its credentials. OPAQUE-KERNEL §2 point 4's credentials stay with
  `linuxd` after the lift. The ABI's documentation of 0x1014 says this in
  one sentence.

## 3. Where it is written

At the write, under the peer's inbox lock, beside the message:

* **A queued message.** `ferrix_objects::message::Message` gains a field
  `sender: Sender`. Every construction must name one, so the compiler
  refuses a message without a stamp; the queue never changes it
  (`push`, `pop_fitting`, `unpop`, `drain` move it whole).
* **The slot, fail closed by construction** (condition 1, ledger 2524).
  The slot becomes `small: Option<(Small, Sender)>`. `put_small` sets it
  whole, and `pop_fitting`, `unpop` and `pop_small` take it whole, so a
  slot message without a stamp cannot be represented. There is no `{0, 0}`
  fallback and no internal-error path. `Small` keeps what
  `channel_write_read`'s read copies. `pop_small` drops the stamp, so
  0x1013 answers none.
* **`Sender`'s shape** (condition 1). It has no `Default`. Its fields are
  private to `object::channel`. Its only constructors are
  `Sender::of(&Process)` and `Sender::KERNEL`, and it is read through
  `process()` and `job()`.
* **Who writes.** `Endpoint::write` and `Endpoint::write_small` take the
  `Sender` as their first argument. The two program-side callers,
  `channel_write` (native.rs:664) and `channel_write_read`'s `send_words`
  (native.rs:939), pass `Sender::of(process)`, made from the calling
  process's core record (the one `with_handles` already holds), never from
  an argument register. The kernel's 25 product sites pass `Sender::KERNEL`. The
  stamp is the writer's, so a message's sender never depends on which end
  it went through, who made the channel, or who holds the end now.

*Rejected:* reading the current task at the write inside `Endpoint`. A
kernel ring writes in a program's context (an answer on a program's call),
and would then stamp that program; the sender has to be stated by the code
that knows who is writing.

## 4. How a server reads it: a separate out-parameter

**0x1014 `CHANNEL_READ_ATTESTED`** `(channel, bytes, byte_capacity, handles:
*u32, handle_capacity, actual: *ReadAttested)`: exactly `channel_read`
(0x1012), the same rights (`READ`), the same refusals in the same order,
the same topology rule, the same put-back on a failed delivery, with a
larger record in place of `ReadActual`:

```
#[repr(C)] struct ReadAttested { bytes: u32, handles: u32, process: u64, job: u64 }   // 24 bytes
```

written last, as `ReadActual` is, after the bytes and handles: a delivery
whose record cannot be written is taken back and the message requeued with
its stamp. On `BUFFER_TOO_SMALL` only `bytes` and `handles` are written and
the identity fields are left as they were, so nothing about a message not
taken is told. Six arguments, as `channel_read` has, so the call is the
same shape on x86-64, AArch64 and ARMv7-A. `channel_read` itself and
`ReadActual` are unchanged, so no existing program or driver changes.

*Why not a header word in the body:* the body is the writer's, and a server
that reads identity from the same buffer as data invites the confusion K6
is there to remove; and `channel_write_read`'s three words have no room.
*Why not a sticky "last sender" per end:* two reader threads on one end
would read each other's.

**0x100A `OBJECT_ID`** `(handle, out: *u64)`: writes the process id of a
process handle or the job id of a job handle, so a server can compare an
attested sender with the processes it started (`process_create`'s handle)
and the jobs it holds (`job_create`, `job_for_cgroup`). Any rights: an id
grants nothing. `WRONG_TYPE` for any other object, `BAD_HANDLE`, `FAULT`
for `out`. A process handle answers after the process has ended, from its
`Exit`, so a server can still match a dead client's queued messages.

## 5. The round trip and the fast path

* **`channel_write_read` (0x1013) reveals no identity**, on either path.
  Its answer is the three registers, unchanged. **The limit, stated**
  (condition 3): a server that answers and waits through 0x1013 receives
  its next request with no identity, on the fast path and the general path
  alike. So a server that decides by sender reads with 0x1014 until K7.
  L.object.202 says the same. Identity on the register
  path is left to **K7**, whose token is "tied to one outstanding forwarded
  request, issued with the attested identity, valid until the reply"
  (OPAQUE-KERNEL §2 point 5): the token and the register-path identity are
  one design, and doing half of it here would put a second per-thread
  record on the hot path before K7 knows what it needs.
* **Register-path identity is K7's** (`docs/microkernel/K7.md` §2.2,
  ledger 2525 (1)). A client puts a K7 ticket id in one of 0x1013's words.
  The server's `CHARGE_TICKET` ADOPT answers the ticket's issuer, which is
  the K6 `Sender` recorded at ISSUE (`Sender::of` on the issuing process).
  So 0x1013 itself stays without identity. K6 gives K7
  `object::channel::Sender::of(&Process)` and the two ids through
  `Sender::process()` and `Sender::job()`, all `pub(crate)`. A `Sender` is
  still built only by `of` and `KERNEL`.
* **The fast path (`Endpoint::send_direct`, step 4) is not changed.** Its
  commit hands three words to a reader parked in `channel_write_read`, the
  only reader that can be parked (`Inbox::parked`, set only by
  `park_for_reply`); that reader has no way to read a sender, so the commit
  carries none. The message never enters an inbox, so no
  `channel_read_attested` can meet it unstamped. The tested equivalence
  (`ipc-equiv`, fast path off and on) is unaffected: the sender is not an
  observable of 0x1013 on either path. L.object.202 states this, and a
  boot case checks it (§6, case 8).
* **The general path's cost**, the only change on the round trip with
  `ipc_fastpath=off` (`present`, `max`): `send_words` makes `Sender::of`
  (two loads from the calling `Process`, one `Acquire`, no lock) and
  `write_small` stores 16 bytes into the inbox under the lock it already
  holds. *Guessed* at under 5 ns a direction. **Measured** before the code
  review, ABAB on nazuna against `main`, `bench-ipc --release --accel kvm
  --smp 1 --arch x86_64 --alternate <main> --rounds 5 --record`, once with
  `--kernel-option ferrix.fastpath=off` (the gated configuration of
  `present`) and once with it on (expected inside the A/A band, 1%,
  since the fast path does not change), run through `gate.sh run`'s warm
  slots; cycles and instructions per trip where the perf scripts allow.
  The figures, ratios, spread, rounds and load go into §8 and the record
  under `docs/hotpaths/results/ipc-round-trip/`. A ratio above 1.01 on the
  fast path, or above 1.02 on the general path, goes back to the consultant
  before the code review.
* `channel_write` and `channel_read`: one more 16-byte field per queued
  message, and 16 more bytes written to user memory by 0x1014 only.

## 6. The boot check (stage 9, every boot, `present`)

`src/kernel/src/object/sender_check.rs`, run from `object::check::run`
after `write_read_check`, every call through the architecture's own entry
(`arch::drive_native_words`, by threads of check processes as
`write_read_check` makes them). It prints one line:
`  sender   N messages read with their writer's process and job: ...`.
Its cases, each `Err` with its own text:

1. **The writer, not the body.** Process A writes through `channel_write`
   a body holding B's process id and job id; B reads it with 0x1014 and
   gets A's ids, which equal `OBJECT_ID` on B's handle to A and to A's job.
2. **The slot.** A writes through `channel_write_read` (the slot) and
   blocks; B reads with 0x1014 and gets A's ids.
3. **Handle transfer.** A writes m1, then sends its end to C; C writes m2
   through it; B reads m1 as A's and m2 as C's. And m1 carried in a message
   as a queued endpoint's inbox keeps its stamp when read later.
4. **Exit.** A writes and ends; B reads after A's `Exit` is terminated and
   still gets A's ids; `OBJECT_ID` on the dead A answers the same id.
   **And across `execve`** (condition 5): stage 8's `fs::exec_check` gives
   its fork a channel end before the fork's real `execve` of
   `/proc/self/exe`. After it, the fork writes an empty message and ends.
   The message, read once the fork has ended, carries the fork's id from
   before the `execve`, and the fork's id read after the `execve` is the
   same.
5. **Never reused.** Every process the check makes has an id above every
   id seen before it in the boot (the check keeps the highest), and none
   is zero. That covers a plain process, **a forked child and a
   `process_create` child** (condition 5; `object::check`'s `Spawner`).
   A process made after A ended does not get A's id, though it may get
   A's pid (the check records whether it did). Case 5 runs first, so that
   C5 fires on its sentence.
6. **The job at the write.** A writes m1, is moved to another job, writes
   m2; m1 carries the first job's id and m2 the second's.
7. **The kernel.** A message the kernel writes on a check channel
   (`Endpoint::write` with `Sender::KERNEL`) reads as `{0, 0}`.
8. **0x1013 reveals none.** After cases 1 and 2, the words and count
   `channel_write_read` answers are exactly the general path's
   (`write_read_check`'s own expectations): no identity leaks into
   registers 2 to 4.
9. **The calls' refusals.** 0x1014 without `READ` (`ACCESS_DENIED`, nothing
   taken); `BUFFER_TOO_SMALL` writes sizes and leaves the identity fields
   as they were; a bad `actual` requeues the message with its stamp, read
   again whole; `OBJECT_ID` on a channel is `WRONG_TYPE`, on a closed
   handle `BAD_HANDLE`, to a bad `out` `FAULT`.

The four boots: x86-64 under KVM and TCG, AArch64, ARMv7-A (and ARMv7-A at
`--smp 2`, as the memory note asks for this board's checks), all `present`,
`ipc_fastpath=off`. The fast-path boot (`ferrix.fastpath=on`, the
`ipc-equiv` row) runs too, since case 8 and the commit's claim are about it.

## 7. Negative controls

Each one ran through `gate.sh control <ref> <tag> <file> <old> <new>
--expect <sentence> -- test-boot --arch x86_64 --accel kvm`, on mk/k6 at
`2f6a2bc0e`, whose code is the landing's. The verdicts are in
`logs/queue/INDEX` on nazuna:

| Control | The sabotage (one exact-text replacement) | Verdict |
|---|---|---|
| C1, the body | `Endpoint::write` stamps the message with a sender made from its first byte. Outside `object::channel` a `Sender` cannot be built from numbers at all, so the sabotage sits inside it | `k6-c1-body2`: FIRED (panic), stage 8, "sender case 4: a message written after an execve did not read as the process's id" |
| C2, the kernel's stamp on a program's write | `channel_write` passes `Sender::KERNEL` in place of `Sender::of(process)` | `k6-c2-kernel2`: FIRED (panic), the same case 4 sentence |

| C4, the end's first writer | `channel_write`'s sender becomes the first one seen through that endpoint. | C5, ids reused | the counter's `fetch_add(1, Relaxed)` becomes `load(Relaxed)` | `k6-c5-reused`: FIRED (panic), "sender case 5: a process was given an id not above every id before it" |

**C1 and C2 fire on case 4, not case 1.** Both break `channel_write`. The
first `channel_write` a K6 check makes is the `execve` half of case 4, in
stage 8's `fs::exec_check`, which runs before stage 9's cases. Their first
runs expected case 1's sentence and read DID NOT FIRE (`k6-c1-body`,
`k6-c2-kernel`). Each log shows the case 4 panic, and that the boot never
reached stage 9. So the sabotage is caught by the first K6 check that meets
it. Case 1 catches it too (the sabotage makes a program's stamp its first
byte, or zero), but a control can make only one replacement, so case 1's
own firing is argued here, not shown.

## 9. Requirements

* **H.OBJ.19** (high level, under the item's object requirements): every
  channel message shall carry the identity of the process and job that
  wrote it, written by the kernel at the write and never taken from the
  message or the writer's arguments, readable by its reader with the
  message; the process identity shall never be reused while the kernel
  runs.
* **L.object.197**: every write stamps the message with its writer's
  `Sender`: a program's write with its process id and its job id at the
  write, the kernel's with `{0, 0}`; queued and slot messages alike; the
  stamp is carried unchanged through queueing, put-back and the transfer of
  the end it was written through.
* **L.object.198**: a process id is given once, as the core process is
  made, from a counter that only grows, starting at 1; it is kept across
  `execve`, held by the process's `Exit`, and never given again.
* **L.object.199**: `channel_read_attested` (0x1014) answers as
  `channel_read`, and writes `ReadAttested` with the message's stamp last;
  on `BUFFER_TOO_SMALL` it writes the sizes only. The record is written
  byte by byte through the user copy, so `actual` needs no alignment
  (condition 7). The check reads every record from an address one past
  an 8-byte boundary.
* **L.object.200**: `object_id` (0x100A) writes the id of a process or job
  handle, a process's also after it has ended; `WRONG_TYPE`, `BAD_HANDLE`,
  `FAULT` otherwise.
* **L.object.201**: the job in a stamp is the writer's job at the write,
  read from a mirror written under the membership lock at every move.
* **L.object.202**: `channel_write_read` answers no identity on either
  path; the fast path's commit carries none and puts no message in an
  inbox.

**SFR** (condition 6): H.OBJ.19 traces to FDP_ACF.1. In this landing's
docs part, the Security Target's FDP_ACF.1 names the sender identity among
the subject security attributes. A wider restatement waits for M7.

**ARMv7-A** (condition 7): the process-id counter is the same lock-free
`AtomicU64` shape as `Job`'s (`ldrexd`/`strexd`).

## 10. Questions for the consultant

1. Is a process id held in `Exit` and a job id at the write the right pair,
   or should the stamp carry the job *chain* (or the top-level partition
   job) so a server can decide by partition without walking?
2. Is leaving identity off 0x1013 until K7 acceptable for K6's row, given
   §5's argument, or must K6 carry it in registers now?
3. `OBJECT_ID` with no right needed: acceptable, or should it need `WAIT`
   (or a new `INSPECT`)?
4. The kernel's sites keep `Endpoint::write` with an explicit
   `Sender::KERNEL` argument (25 one-argument product edits in load-ring and
   discovery files, coverage carried): acceptable, or should the kernel
   write keep its signature and the program write become a second
   function, with C2 as the only guard against a program stamped as the
   kernel?
5. Which SFR the ST cites for the attribution (§9).
6. ARMv7-A: the ids are 64-bit on a 32-bit machine; written to user
   memory as two words, never in registers. Any objection?
