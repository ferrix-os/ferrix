How it fits together:

* **The link.** nvrm is linked first, with a build-id and a zeroed
  `.nvrm_core_sha256`.
  * `nv-kernel.o` is then linked alone at 0x4000_0000. Each of its 406
    imports is bound to nvrm's address for it by a generated script
    assignment. Full `--just-symbols` is not used, because nvrm's own
    `rm_*` stubs would clash.
  * The core carries an export header: magic `NVRMCORE`, version 1, the
    count, nvrm's build-id, then the addresses, data first (`pNVRM_ID`),
    then the functions nvrm's objects call. There are 17 today, computed
    per build.
  * The core's sha256 is then written into nvrm with
    `objcopy --update-section`. The build refuses the result if any section
    header or symbol moved.
* **RM's one privileged instruction.** In all of RM's code, only
  `osNv_rdcr4` (`mov %cr4,%rax`) faults in ring 3.
  * A linker-script assignment overrides the object's own definition, so
    all three of its call sites reach nvrm's `nvos_rdcr4` (`os/nvos/src/cpu.rs`).
    That function returns OSFXSR, and OSXSAVE as CPUID.1:ECX bit 27 shows it.
  * `core-link.py` scans `nv-kernel.o` and refuses the build on any other
    privileged instruction.
* **Results on nazuna.**
  * `cargo xtask test-nvrm-link` passes on the host and on Ferrix under KVM.
    The good run shows `NVRM: loading … 580.173.02`, a root client,
    `NV01_DEVICE_0` refused (status 0x40), then `passed` with exit 0.
  * The seven controls each refuse with their own line and status: flipped
    byte 25, unpinned 20, other build 35, segment past 2 GiB 30, writable
    and executable segment 29, bad magic 32, rwx mapping 41.
  * `cargo xtask test-nvrm` passes all three boots; in the handed-over boot,
    nvrm waits for the volume and prints its `nvos: core loaded: …` line.
* **Build directories.** xtask builds nvrm in the worktree's `target/nvrm`.
  The by-hand build directory is `~/.local/share/ferrix/target-nvidia-n1c`.
  NVIDIA's release is `~/.local/share/ferrix/nvidia/580.173.02`, or
  `$FERRIX_NVIDIA/580.173.02`.
